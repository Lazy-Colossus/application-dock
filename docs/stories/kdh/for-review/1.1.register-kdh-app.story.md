# Story 1.1: Register KDH in the Application Dock shell

## Status

Ready for Review

## Story

**As** a user of the Application Dock,
**I want** KDH to appear as a card on the landing page and open at its own route,
**so that** I can reach it the same way I reach every other app.

## Acceptance Criteria

1. **Shell card.** Given the dock landing page, when it renders the app registry, then a KDH card appears (label `KDH`, icon `event_available`) alongside the existing apps, and selecting it routes to `/kdh`. Rendered by the generic `AppCard` — no shell changes beyond the registry entry. (FR-1, AR-1)

2. **Backend registry.** Given `GET /api/apps`, when called, then the response includes a KDH `AppDescriptor` (`id: "kdh"`, `label: "KDH"`, `icon: "event_available"`, `route: "/kdh"`).

3. **Routes.** Given the router, when a logged-in user visits `/kdh`, then `KdhHomePage.vue` renders (lazy-loaded, `meta: { title: "KDH", requiresAuth: true }`); `/kdh/c/:calendarId` is also registered and renders a placeholder `CalendarPage.vue` that reads `:calendarId`. Both are **minimal page shells** that later stories fill in — this story references no work not yet done. (FR-1, FR-7)

4. **App module skeleton.** Given the new app, when the project is set up, then `frontend/src/apps/kdh/` exists and is self-contained (the shell imports it only via `registry.ts`), and a backend `routers/kdh.py` is mounted under `/api/kdh` behind `Depends(get_current_user)` — even if it exposes nothing until Story 1.3. (FR-1, FR-2, AR-1)

5. **Auth contract established.** Given `backend/app/routers/kdh.py`, when it is created, then it declares `Depends(get_current_user)` as the pattern every route will carry, and a module docstring records that the username is used for the **admin check only** — never to select a file. The router carries **no routes yet**, so the first live `401` assertion lands in Story 1.3 with the first real endpoint; do not invent a placeholder endpoint here purely to test it. (FR-2)

6. **Story folders.** Given the docs tree, when the app is registered, then `docs/stories/kdh/for-review/` and `docs/stories/kdh/done/` exist. (AR-1)

7. **No regressions.** Given the existing suites, when this story lands, then `pytest` and `npm test` stay green and `black` / `ruff` / ESLint / Prettier are clean on touched files.

## Dev Notes

**Two-file change.** Adding an app is meant to be registry + routes; `HomePage` iterates the registry and `AppCard` is generic — no other shell changes. [Source: CLAUDE.md#Adding a new app]

**⚠️ KDH is NOT per-user — do not copy Listies' scoping.** Listies, Context-Switch and Hotaru all scope one JSON file per username. KDH's six voters share a single dock login, so the username selects **nothing**: calendars are global to the deployment and files are chosen by calendar id. Every route still sits behind `Depends(get_current_user)` — the username is used for the **admin check** (Story 1.3), never to pick a file. This is the single easiest thing to get wrong by pattern-matching the previous app. [Source: docs/superpowers/specs/2026-09-02-kdh-design.md#NFR-2, FR-2]

**⚠️ `registry.ts` and `_APPS` have already drifted — do not "fix" it.** `shell.py` still lists archery's icon as `sports_score` while `registry.ts` says `adjust`, and `registry.spec.ts` asserts the latter. This duplication is a known, accepted v1 limitation: `/api/apps` is informational and **not consumed by the frontend shell**. Add the KDH entry to both, keep them consistent *with each other for KDH*, and leave the archery discrepancy alone. [Source: docs/implementation-artifacts/deferred-work.md:56]

**Icon.** `event_available` (Material Icons). Note KDH is an initialism carrying no imagery of its own, so the icon does all the "this is a calendar" work — the other apps use single thematic glyphs (`adjust`, `school`, `swap_horiz`, `table_chart`).

**Route shape.** `/kdh/c/:calendarId` — deliberately short, because this is the URL an admin copies and pastes to the group (FR-7). Do not lengthen it to `/kdh/calendars/:id`.

**Scope discipline.** No data model, no schemas, no repository, **no endpoints at all**, no calendar UI. Pages are placeholders. The data layer and its write locking are Story 1.2; the first real endpoints — and with them the first live auth test — are Story 1.3. An empty router is correct here and matches how `routers/listies.py` began; adding a throwaway health endpoint would violate CLAUDE.md's no-dead-code rule.
