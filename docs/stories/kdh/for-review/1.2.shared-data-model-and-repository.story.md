# Story 1.2: Shared data model, repository & per-calendar write serialization

## Status

Ready for Review

## Story

**As** the platform,
**I want** calendars stored as one JSON file each, with every read-modify-write on a calendar serialized against concurrent writers,
**so that** six people voting on the same evening never silently erase each other's votes.

## Acceptance Criteria

1. **Schemas.** Given `backend/app/schemas/kdh.py`, when models are defined, then Pydantic v2 models exist for `Invitee` (`id`, `name`, `color`, `order`, `removed_at`), a `VoteStatus` literal (`"yes" | "if_needed"`), and `Calendar` (`schema_version`, `id`, `name`, `created_at`, `created_by`, `updated_at`, `invitees`, `votes` keyed date → invitee id → status, `chosen_dates`). (AR-3, AR-4)

2. **One file per calendar, no index.** Given `backend/app/repositories/kdh_repo.py`, when it reads and writes, then it is the only module touching the filesystem, stores each calendar at `DATA_DIR/kdh/calendars/{calendar_id}.json`, `mkdir(parents=True, exist_ok=True)` on write, routes every write through the shared `core.storage.atomic_write_json`, and lists calendars by **scanning the directory** — no index file to become a second contention point. (NFR-2, NFR-3, AR-3)

3. **Shared, not per-user.** Given any repo function, when it resolves a path, then the path is derived from the **calendar id only**. No function takes a username for file selection; a caller cannot scope storage by user even by mistake. (FR-2, NFR-2)

4. **Path traversal is impossible.** Given a calendar id containing a path separator, a parent reference, or leading/trailing whitespace, when the repo derives a path from it, then it raises `ValueError` rather than writing outside `calendars/`. (NFR-2)

5. **Transactions consume the platform lock.** Given platform Story 1.8 has landed, when the repo serializes a mutation, then it uses `core.locks.key_lock` via a `calendar_transaction(calendar_id)` context manager that holds the lock across read→write and writes nothing if the block raises — it does **not** define a KDH-local lock. (NFR-1)

6. **Concurrent mutations of one calendar all survive.** Given N threads mutating the same calendar, when they interleave on the threadpool, then every mutation is applied and none is lost; and given mutations of **different** calendars, then they are not serialized against each other. Both are asserted by tests that are verified to fail with the lock disabled. (NFR-1)

7. **Ids and timestamps.** Given a calendar or invitee is created, when it is stamped, then it carries a stable id (`cal-` / `inv-` + 8 hex chars) unique within the document, and ISO-8601 UTC timestamps. (AR-3)

8. **Dates are calendar dates.** Given any date in the document, when stored or compared, then it is a `YYYY-MM-DD` string with no timezone, and "today" is resolved **server-side** by a single helper the later stories share. (NFR-5)

9. **Layering holds.** Given `backend/app/services/kdh_service.py`, when it operates on a document, then it raises stdlib exceptions only — `FileNotFoundError` (missing calendar/invitee), `ValueError` (invalid input), `PermissionError` (non-admin) — and never `HTTPException`. (NFR-4)

10. **No regressions.** Given the existing suites, when this story lands, then `pytest` stays green and `black` / `ruff` are clean. Frontend untouched.

## Dev Notes

**Story 1.8 has landed — consume it, do not rebuild it.** `app/core/locks.py` provides
`key_lock(key)` (reentrant) and `app/core/storage.py` provides `atomic_write_json` (unique temp
file, fsync, atomic replace). AC 5's fallback branch is now dead: there is no reason to define a
KDH-local lock. [Source: `docs/stories/application-dock-general/for-review/1.8...story.md`]

**⚠️ The storage shape is the opposite of every other app.** `listies_repo` and
`context_switch_repo` are the closest patterns to copy — but they key files by **username**, and
KDH must key by **calendar id**. The six voters share one dock login, so the username selects
nothing. Copy `listies_repo`'s structure (validation helper, `migrate`, transaction context
manager) and change what the key *is*. [Source: spec NFR-2, FR-2]

**Validation mirrors `_validate_username`.** `listies_repo._validate_username` rejects empty,
whitespace-padded, and separator-bearing names. `_validate_calendar_id` should do the same — the id
is generated server-side, but it arrives back from the URL path, so it is untrusted input.

**No index file.** `list_calendars` scans `calendars/*.json`. This is deliberate (NFR-2): an index
would be a second file every calendar creation must write, making it the contention point the
per-file locking is designed to avoid. The precedent is archery's `list_sessions`.

**`today()` belongs here, not in the routers.** Story 3.5 and Story 4.2 both decide past-vs-future,
and Story 3.2 rejects votes on past dates. All three must agree, and none may trust the client's
clock (NFR-5). One helper in the service, used everywhere.

**Scope discipline.** No endpoints, no admin allowlist, no CRUD operations — Story 1.3 adds all
three. This story is the data layer and the shared helpers only. Resist writing `create_calendar`
here: it needs the admin gate, which needs `settings.kdh_admins`, which is Story 1.3's.

### Completion Notes

- **Consumed Story 1.8, built nothing local.** `calendar_transaction(calendar_id)` wraps the
  platform `core.locks.key_lock`, and `write_calendar` goes through `core.storage.atomic_write_json`.
  AC 5's fallback branch (implement a KDH-local lock) was dead on arrival, as expected.
- **Keyed by calendar id, not username.** No repo function accepts a username at all, so the
  per-user scoping every other app uses cannot be reintroduced by accident (AC 3). The structure
  otherwise mirrors `listies_repo` — validation helper, `migrate`, transaction context manager.
- **`list_calendars` scans the directory** and sorts by `created_at` descending. No index file, so
  calendar creation stays a single write and there is no second contention point (AC 2).
- **The id is treated as untrusted** even though the server mints it, because it round-trips
  through the URL path. Nine unsafe forms are rejected by parametrized test, plus an explicit
  assertion that `../../_auth` neither reads nor creates anything outside `calendars/`.
- **`today()` lives in the service as the single source of the past/future boundary** (AC 8).
  Stories 3.2, 3.5 and 4.2 all decide past-versus-future and must agree; `is_past` treats today
  itself as *not* past, since today is still votable.
- **Concurrency tests verified non-vacuous.** With `kdh_repo.key_lock` monkeypatched to a no-op,
  both lost-update tests fail; the other two (different calendars not blocking each other, a
  raising transaction writing nothing) correctly pass without it, because neither is about lost
  updates. Harness removed afterwards.
- **AC 9 is only partly exercised.** The service raises `ValueError` from `is_past` on a malformed
  date, and the layering is established, but `FileNotFoundError` for a missing invitee and
  `PermissionError` for a non-admin have no code paths until Story 1.3 adds the operations that
  raise them. Nothing is missing from this story — the assertion simply cannot be made yet, and
  Story 1.3 must carry it.
- **Scope held.** No endpoints, no admin allowlist, no CRUD. `routers/kdh.py` is untouched and
  still carries no routes; Story 1.3 adds all three.
- **Suites:** backend **822** passed (was 789). `black` and `ruff` clean. Frontend untouched.
