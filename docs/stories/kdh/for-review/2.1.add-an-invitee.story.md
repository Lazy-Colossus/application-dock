# Story 2.1: Add an invitee, with a colour of their own

## Status

Ready for Review

## Story

**As** an admin,
**I want** to add someone to a calendar and have them get a distinct colour,
**so that** a latecomer can join in and be told apart from everyone else at a glance.

## Acceptance Criteria

1. **Add.** Given an admin posts `{ name }` to `POST /api/kdh/calendars/{id}/invitees`, when accepted, then an invitee is appended with an `inv-{uuid8}` id, the next free palette colour, `order` after the current highest, and `removed_at: null`; the updated calendar is returned with `201`. (FR-8, FR-9, AR-3)

2. **Colours account for tombstones.** Given a calendar holding removed invitees who still carry past votes, when a new invitee is added, then the assigned colour is free of **every** invitee's colour, tombstoned included — a removed person's colour stays theirs while their name still renders on past days. (FR-9, AR-7)

3. **Palette exhaustion.** Given every palette colour is taken, when an admin adds another invitee, then `422` with a `{detail}` naming the limit, and nothing is written.

4. **Name validation.** Given a blank, whitespace-only, or duplicate name, when submitted, then `422` and nothing is written. Duplicates are compared case- and whitespace-insensitively **against active invitees only** — a removed person's name may be reused, since "they're back" is a real case. The name is stored as typed, trimmed.

5. **Order survives removals.** Given invitees have been removed, when a new one is added, then `order` is `max(order) + 1` across **all** records, never `len(invitees)`, so a gap left by a removal cannot collide.

6. **Guests cannot.** Given a guest posts to the endpoint, then `403` and nothing is written. (FR-3)

7. **Serialized.** Given the add, when it runs, then the whole read-modify-write is inside `repo.calendar_transaction` — two admins adding at once must not lose one of the invitees. (NFR-1)

8. **Roster UI.** Given an admin opens **Manage invitees** from the calendar's header menu, when the dialog renders, then it lists active invitees in `order`, each as a chip in their own colour, with a field to add another; submit is disabled for a blank or duplicate name. A guest has no route to this dialog at all. (FR-3, FR-9)

9. **No regressions.** `pytest` and `npm test` green; `black` / `ruff` / ESLint / Prettier / `vue-tsc` clean.

## Dev Notes

**Duplicate names are checked against *active* invitees only.** A tombstoned
person's name is reusable because "they came back" is a real case; their colour is
not, because their name still renders on past days in it (AR-7). That asymmetry is
deliberate — do not "fix" it by checking either both or neither.

**`order` is `max(order) + 1`, never `len(invitees)`.** Removals leave gaps, so
counting would collide with a survivor. Same bug the Listies column code already
carries a comment about.

**Where this lives.** The roster **for admins** is a *Manage invitees* dialog on
the calendar header menu (built in 1.4). The roster **for everyone** is the name
dropdown, which is Story 2.3 — do not build that here.
[Source: `ux-designs/ux-kdh-2026-09-03/EXPERIENCE.md#Information Architecture`]

**Palette is now eight pastels**, not the twelve hues the story was first written
against — the UX session replaced them. Exhaustion is therefore reachable at nine
people, which is plausible for a big group, so the `422` message must be helpful.
