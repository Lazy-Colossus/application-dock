# Story 1.3: Create a calendar with invitees, and see the list

## Status

Ready for Review

## Story

**As** an admin,
**I want** to create a calendar by naming it and listing who is invited, and to see all calendars,
**so that** each occasion gets its own place and I can find it again.

## Acceptance Criteria

1. **Guest configuration.** Given `settings.kdh_guests`, when the API boots with no `KDH_GUESTS` env var set, then it defaults to the single guest account `players`; the value parses as a comma-separated list, ignoring blanks and surrounding whitespace. (AR-2)

2. **Admins are everyone else.** Given an authenticated caller, when `GET /api/kdh/me` is called, then it returns `{ username, is_admin }`, where `is_admin` is false only for a username in the guest list. (FR-3, AR-2)

3. **Unauthenticated is rejected.** Given any `/api/kdh/*` route, when it is called without a valid token, then it returns `401` — deferred here from Story 1.1, which had no endpoint to assert it against. (FR-2)

4. **Guests cannot administer.** Given an authenticated guest, when they call `POST /api/kdh/calendars`, then it is rejected with `403` and a `{detail}` body, and nothing is written. (FR-3)

5. **Create.** Given an admin posts `{ name, invitee_names }`, when it is accepted, then a calendar is persisted with a `cal-{uuid8}` id, `created_by` set to the caller, an `Invitee` per name carrying an `inv-{uuid8}` id, a **distinct palette colour** and ascending `order`, and empty `votes` and `chosen_dates`; the created calendar is returned with `201`. (FR-4, AR-3)

6. **Create validation.** Given a create request with a blank calendar name, zero invitees, a blank invitee name, duplicate invitee names (case- and whitespace-insensitive), or more invitees than the palette holds, when it is submitted, then the API rejects it with `422` and a `{detail}` naming the problem, and no file is written. (FR-4)

7. **List.** Given `GET /api/kdh/calendars`, when called by anyone authenticated, then it returns a summary per calendar — id, name, invitee count — newest first, identical for admins and guests because the data is shared, not per-user. (FR-2, FR-5)

8. **Read one.** Given `GET /api/kdh/calendars/{id}`, when the id is known then the full calendar document is returned; when it is unknown then `404` with a `{detail}`; when it is malformed (a path separator or `..`) then `422`, never a filesystem error. (FR-5, NFR-2)

9. **The home lists calendars.** Given `/kdh`, when it loads, then it calls `GET /api/kdh/calendars` and renders each calendar with its name and invitee count, newest first, and selecting one navigates to `/kdh/c/:calendarId`. (FR-5, FR-7)

10. **Empty states differ by role.** Given no calendars exist, when the home renders for an admin then it shows a calm empty state prompting the first calendar; for a guest it says to ask an admin, with **no disabled create control** shown at all. (FR-3, FR-5)

11. **Create dialog.** Given an admin on the home, when they open the create dialog, enter a name and one or more invitee names and submit, then the calendar is created and they land on `/kdh/c/:calendarId`. Submit is disabled client-side for a blank name, zero invitees, or a duplicate invitee name — the `422` is a backstop, not the first line of defence. (FR-4)

12. **Store contract.** Given `useKdhStore`, when any action runs, then `loading` is set in a `try/finally` and errors are routed into `error.value` — never a bare `console.error`. All HTTP goes through `useApi`. (NFR-4)

13. **No regressions.** Given the existing suites, when this story lands, then `pytest` and `npm test` stay green and `black` / `ruff` / ESLint / Prettier / `vue-tsc` are clean.

## Dev Notes

**⚠️ The guest rule is inverted from the usual allowlist — read AR-2 before writing the check.**
`is_admin = username not in settings.kdh_guests`. There is no admin list. A misconfigured
`KDH_GUESTS` grants the shared account admin rights rather than locking the owners out; that
direction is deliberate and documented, so do not "harden" it into an allowlist.
[Source: `docs/superpowers/specs/2026-09-02-kdh-design.md#AR-2`]

**`KDH_GUESTS` must be a `str` field, not `list[str]`.** pydantic-settings treats a complex-typed
field as JSON in the environment, so `list[str]` would make `KDH_GUESTS=players,guest` a boot
error. Declare `str` and split it. The Google Maps keys next to it are plain strings for
unrelated reasons; follow the same shape here for a considered one.

**Story 1.2 built the layer — use it.** `kdh_repo.read_calendar` / `write_calendar` /
`list_calendars` / `calendar_transaction`, and `kdh_service.now_iso` / `today` / `new_id` all
exist. Creating a calendar is a plain `write_calendar` (there is no existing document to
read-modify-write), so it does **not** need `calendar_transaction`; the transaction is for
mutating an existing calendar, which starts in Story 1.4.

**Duplicate invitee names are compared normalized.** "Dani" and " dani " are the same person to a
human reading the roster, so reject them as duplicates — but **store the name as typed**, since it
is what renders in every day cell.

**The `403` must be enforced server-side, not just hidden in the UI.** AC 10 hides the control, but
AC 4 is the one that matters: a guest posting directly must be refused, and nothing written.

**Scope discipline.** No rename, no delete, no share-link copy — Story 1.4. No invitee management
after creation — Story 2.1/2.2. No month grid — Epic 3. The calendar page stays the placeholder
from Story 1.1; this story only needs it to exist so navigation lands somewhere.

### Completion Notes

- **The guest rule is a denylist.** `is_admin(username) = username not in settings.kdh_guest_usernames`.
  A test asserts the documented fail-open direction explicitly (empty guest list → everyone is an
  admin) so it can never drift into an allowlist unnoticed.
- **`KDH_GUESTS` is a `str` field, split by a property.** Verified against a real environment
  variable end-to-end: `KDH_GUESTS="players, visitors ,"` parses to `["players", "visitors"]`.
  A `list[str]` field would have made that a boot error, since pydantic-settings reads a
  complex-typed field as JSON.
- **Colour palette lives server-side** (12 hues) so a colour is decided once, at assignment, and
  every client renders the same person identically. `assign_colour` skips gaps, which matters from
  Story 2.2 onward: a removed invitee keeps their colour reserved while they still hold past votes.
- **Duplicate invitee names are compared case- and whitespace-insensitively but stored as typed** —
  "Dani" and " dani " are one person to anyone reading the roster, but the name as typed is what
  renders in every day cell. The dialog applies the same rule client-side, so it never submits
  something the server will reject.
- **Two bugs found and fixed during the work, neither in the story:**
  1. **Listing order was filesystem-dependent.** `created_at` has second precision, so calendars
     created in the same second compared equal and a stable sort fell back to `glob` order, which
     varies by filesystem. Now sorted by `(created_at, id)` — ordering within one second is
     arbitrary either way, but it is the same arbitrary order everywhere. Covered by a test that
     asserts repeated listings agree.
  2. **The `docker-compose.yml` passthrough I added was wrong on the first pass.**
     `KDH_GUESTS: ${KDH_GUESTS:-}` passes an *empty string* when the var is unset, which overrides
     the app's `players` default and silently promotes the shared account to admin — the exact
     fail-open risk AR-2 accepts in principle but should never hit through the normal deploy path.
     The fallback now mirrors the app default (`${KDH_GUESTS:-players}`). Verified by running the
     app with `KDH_GUESTS=""` and watching `players` come back as an admin.
- **The `401` test needed two things undone to test anything.** `conftest` overrides the auth
  dependency for every file but `test_auth.py`, and `get_current_user` deliberately returns a dev
  user when no `JWT_SECRET_KEY` is set — which is the default in this environment. Without setting
  a secret the route answers `200` and the assertion proves nothing; the test now sets one and says
  why. This closes the criterion deferred from Story 1.1.
- **AC 9 from Story 1.2 is now discharged.** `PermissionError` (guest → 403) and `FileNotFoundError`
  (unknown calendar → 404) have code paths and tests; the service still raises no `HTTPException`.
- **Frontend follows the house patterns.** All HTTP through `useApi`; the store sets `loading` in a
  `try/finally` and routes errors into `error.value`; `createCalendar` rethrows so a failed create
  does not navigate. Page specs use local Quasar stubs, as the Context-Switch specs do, rather than
  widening the shared global stub set.
- **Scope held.** No rename, delete or share-link copy (Story 1.4); no invitee management after
  creation (Epic 2); no month grid (Epic 3). The calendar page is still Story 1.1's placeholder.
- **Suites:** backend **863** passed (was 822), frontend **1131** passed across 86 files (was 1118).
  `black`, `ruff`, ESLint, Prettier and `vue-tsc` all clean.
