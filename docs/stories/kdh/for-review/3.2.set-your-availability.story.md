# Story 3.2: Set your availability on a day

## Status

Ready for Review

## Story

**As** an invitee who has claimed a name,
**I want** to say I am free, or free if needed, and to take it back,
**so that** I can offer my availability in one gesture and change my mind just as easily.

## Acceptance Criteria

1. **A narrow endpoint.** `PUT /api/kdh/calendars/{id}/votes` takes `{ invitee_id, date, status }` and writes exactly that one entry; `none` clears it, and a date left empty is pruned. Nothing else in the document is touched. (FR-15, AR-4, AR-5)
2. **Idempotent.** Re-sending the status a day already has changes nothing; clearing a vote never set is harmless.
3. **Optimistic.** The cell moves before the server answers; on failure the whole vote map is restored exactly and the message is surfaced. (FR-15, NFR-4)
4. **Today is votable, the past is not.** A vote on a date before the server's today is `422`, and nothing is written. (FR-16, NFR-5)
5. **Rejections.** Malformed date, unknown status, removed invitee → `422`; unknown invitee → `404`.
6. **Guests may vote** — it is what they are here to do. (FR-3, AR-6)
7. **Concurrent votes all survive**, per the per-calendar transaction. (NFR-1)
8. **An unclaimed tap opens the name dropdown** rather than being refused. (FR-11)

### Completion Notes

- The endpoint is deliberately not admin-gated: voting is the guest's whole
  purpose, and the claim naming *which* invitee you are was never a security
  boundary.
- `Me` gains `today` — the client must never decide "past" from its own clock, and
  `/me` is the request every page already makes, so the boundary rides along
  rather than costing a second round trip.
- The optimistic path snapshots the entire `votes` map, not the single day, so a
  rollback restores exactly what was there. A half-applied grid is worse than no
  change.
- A concurrency test fires six people at one day simultaneously — the case the
  whole platform was serialized for in Story 1.8.
