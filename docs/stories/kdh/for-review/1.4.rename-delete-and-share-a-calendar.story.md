# Story 1.4: Rename, delete, and share a calendar

## Status

Ready for Review

## Story

**As** an admin,
**I want** to rename a calendar, delete one that is finished, and copy its link,
**so that** I can keep the list tidy and get the right people to the right calendar.

## Acceptance Criteria

1. **The calendar page loads a real calendar.** Given `/kdh/c/:calendarId`, when it loads, then it fetches that calendar and shows its **name** as the page heading; an unknown id shows a plain "Calendar not found" state with a way back to the list, not a crash or an empty page. (FR-5, FR-7)

2. **Rename.** Given an admin on a calendar page, when they rename it, then `PUT /api/kdh/calendars/{id}` persists the new name, `updated_at` is refreshed, `created_at`/`created_by`/`invitees`/`votes`/`chosen_dates` are untouched, and the heading updates in place without a reload. (FR-6)

3. **Rename validation.** Given a rename to a blank or whitespace-only name, when submitted, then the client disables submit and the API rejects it with `422` and a `{detail}`; the stored name is unchanged. Leading/trailing whitespace on an otherwise valid name is trimmed. (FR-6)

4. **Delete.** Given an admin chooses delete, when the confirmation appears, then it **names the calendar** and says the votes go with it; on confirming, `DELETE /api/kdh/calendars/{id}` removes the file and the admin lands back on `/kdh` with the calendar gone from the list. Cancelling writes nothing. (FR-6)

5. **Share.** Given any admin on a calendar page, when they use the share control, then the **absolute** `/kdh/c/:calendarId` URL is copied to the clipboard and a confirmation appears. Opening that URL in a fresh session lands on that calendar after login. (FR-7)

6. **Guests see none of it.** Given a guest viewing a calendar, when the page renders, then no rename, delete or share control is present at all — not disabled, **absent**. (FR-3)

7. **Guest enforcement is server-side.** Given a guest calls `PUT` or `DELETE` on a calendar directly, when it reaches the API, then it is rejected with `403` and nothing is written. (FR-3)

8. **Unknown and malformed ids.** Given `PUT` or `DELETE` for an unknown calendar, then `404`; for a malformed id (path separator, `..`), then `422` — never a filesystem error. (NFR-2)

9. **Store contract.** Given `useKdhStore`, when rename or delete runs, then `loading` is set in a `try/finally`, errors route into `error.value`, and the cached `calendars` list stays consistent with what the server now holds — a rename updates the summary in place, a delete drops it. (NFR-4)

10. **No regressions.** Given the existing suites, when this story lands, then `pytest` and `npm test` stay green and `black` / `ruff` / ESLint / Prettier / `vue-tsc` are clean.

## Dev Notes

**⚠️ This is the first story to mutate an existing calendar, so it is the first to
need `repo.calendar_transaction`.** Story 1.3's `create_calendar` writes a brand-new
document, so a plain `write_calendar` was correct there. Rename reads-then-writes,
which is exactly the lost-update shape Story 1.8 exists to prevent — put the whole
read-modify-write inside the transaction, not just the write.
[Source: `backend/app/repositories/kdh_repo.py`, `docs/stories/application-dock-general/for-review/1.8...story.md`]

**The UX session settled where these controls live.** Admin actions are a **header
menu** that only admins see — not a bar, not inline buttons. Phone-only, one layout;
there is no wide variant to design.
[Source: `docs/planning-artifacts/ux-designs/ux-kdh-2026-09-03/EXPERIENCE.md#Component Patterns`]

**Absent, not disabled.** A guest must not see a greyed-out Delete. This is stated
twice in the spines because it is the easy thing to get wrong when the data is
shared and everyone sees the same calendar.

**Delete is destructive and unrecoverable** — there is no archive and no undo. The
confirmation must name the calendar and say the votes go with it, so a mis-tap on a
phone cannot quietly destroy a campaign's history.

**`DELETE` returns `204`.** `useApi.del` exists and the platform contract is direct
serialization with no envelope; a `204` returns `undefined as T`, which the store
must not try to read. (This cast is a known sharp edge —
`deferred-work.md` logs it.)

**Share copies an absolute URL.** `route.path` alone is useless in a group chat.
Use `window.location.origin + route.path`. `navigator.clipboard` needs a secure
context; on plain HTTP over a LAN it is undefined, so fall back to selecting the
text rather than throwing.

**Scope discipline.** No month grid, no invitee management, no chosen days. The
calendar page gets a real header and nothing below it — Epic 3 fills the body.

### Completion Notes

- **First real read-modify-write in KDH, so the first use of the transaction.**
  `rename_calendar` runs inside `repo.calendar_transaction`, not a bare
  `write_calendar` — a rename that read outside the lock could be undone by a vote
  landing between the read and the write. `create_calendar` stays a plain write,
  correctly: there is no prior document to lose.
- **Admin markup is absent from a guest's DOM, not merely unreachable.** The first
  pass rendered the menu and its dialogs unconditionally and relied on the
  admin-only trigger to keep them closed — which the spec test caught. All three
  dialogs are now inside one `v-if="isAdmin"`, so a guest's page contains no
  admin control at all. The server-side `403` is still the thing that enforces it.
- **Copy feedback got its own channel.** It was initially written through
  `store.error`, which both mislabelled a success and clobbered any real error
  sitting there. It is now a local `copyNotice`.
- **A 404 shows one thing, not two.** The error banner is suppressed when the
  not-found state is showing, so a missing calendar reads as a state rather than
  as a state plus a stack-adjacent error line.
- **The clipboard fallback is real, not theoretical.** `navigator.clipboard` is
  undefined outside a secure context, which is exactly how this dock is reached on
  a LAN over plain HTTP. On failure the page shows the URL to copy by hand; both
  paths are tested.
- **One weak assertion caught and fixed.** `updated_at >= created_at` passes
  trivially at second precision. The test now drives `now_iso` and asserts the
  exact new stamp, plus that it differs from the original.
- **Two self-inflicted test-authoring slips**, both from patching a file Prettier
  had already reformatted: a silent no-op `str.replace` (it does not raise on a
  miss) that left a duplicate helper, and an appended block that landed after the
  `describe` close. Both fixed; noted because the failure mode is quiet.
- **Scope held.** The calendar page is a header and nothing else — Epic 3 fills the
  body. No invitee management, no month, no chosen days.
- **Suites:** backend **877** passed (was 863), frontend **1146** across 86 files
  (was 1131). `black`, `ruff`, ESLint, Prettier and `vue-tsc` clean.
