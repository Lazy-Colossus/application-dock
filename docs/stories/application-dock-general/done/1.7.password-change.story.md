# Story 1.7: Password Change from Settings

## Status

done

## Story

**As a** user,
**I want** to change my password from the Settings page,
**so that** I can replace the temporary password I was given — or rotate my credentials — without needing anyone else's help.

## Acceptance Criteria

1. **Given** the user is on the Settings page, **When** the page loads, **Then** a **SECURITY** section is visible containing a "Change password" form with three fields: *Current password*, *New password*, *Confirm new password*, and a **Change password** button.
2. **Given** the user fills in all three fields, **When** they click **Change password**, **Then** the frontend validates that *New password* and *Confirm new password* match before sending any request. If they do not match, an inline error message appears and no request is sent.
3. **Given** the three fields are valid and matching, **When** the request reaches the backend, **Then** the backend verifies *Current password* against the stored hash for the authenticated user. On success it updates the hash and returns `200 { "detail": "Password changed" }`.
4. **Given** the current password is wrong, **When** the backend processes the request, **Then** it returns `400 Bad Request` with `{ "detail": "Current password is incorrect" }` and the frontend surfaces this as an error banner without clearing any field.
5. **Given** the password change succeeds, **When** the frontend receives the `200`, **Then** it clears all three fields and shows a non-blocking success banner: `Password changed successfully.`
6. **Given** the *New password* field, **When** the user types, **Then** the field enforces a minimum length of 8 characters (client-side only — the backend does not re-validate length, trusting the UI).

## Dev Notes

### Current password is always required
Even though the user is already authenticated via JWT, requiring the current password prevents a hijacked session (unlocked screen, stolen token) from silently changing credentials. Do not add a bypass.

### No minimum length enforcement on backend
AC 6 scopes the 8-character minimum to the client. The backend trusts the UI for length validation — consistent with the project's single-operator, trusted-network context. Do not add backend length validation in this story.

### `write_user` semantics after Story 1.6
After Story 1.6, `auth_repo.write_user(record)` replaces the existing entry for that username in the list (preserving all other users). `change_password` calls it to update only the hash — no other fields change.
