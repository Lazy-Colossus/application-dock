# Story 1.6: Multi-User Management — Create Users from Settings

## Status

done

## Story

**As an** operator,
**I want** to create additional user accounts from the Settings page,
**so that** I can give other people access to the app without dropping to a host shell or re-running the setup script.

## Acceptance Criteria

1. **Given** the operator is on the Settings page, **When** the page loads, **Then** a **USERS** section appears listing all existing usernames (no password hashes — usernames only).
2. **Given** the USERS section is visible, **When** the operator types a username into the "New username" field and clicks **Add user**, **Then** the backend creates the account with the temporary password `tmp123`, the new username appears in the list, and a non-blocking success banner reads: `User created. Temporary password: tmp123 — ask them to change it after first login.`
3. **Given** the operator submits a username that already exists, **When** the backend processes the request, **Then** a `409 Conflict` is returned with `{ "detail": "Username already exists" }` and the frontend surfaces it as an error banner without clearing the input field.
4. **Given** the operator submits an empty or whitespace-only username, **When** the frontend validates the field, **Then** the Add button is disabled (client-side guard — no request sent).
5. **Given** the existing single-user `_auth.json` format (`{ "username": "…", "password_hash": "…" }`), **When** the backend boots after this story lands, **Then** the old single-object file is transparently migrated to the new list format (`[{ "username": "…", "password_hash": "…" }]`) on first read. No manual migration step is required from the operator.

## Dev Notes

### Data model change
`_auth.json` moves from a single object to a JSON array. The migration in `read_users()` is the **only** migration path — no separate script, no downtime. The atomic write after migration ensures the old format is never read twice.

Old format:
```json
{ "username": "admin", "password_hash": "$2b$12$..." }
```
New format:
```json
[{ "username": "admin", "password_hash": "$2b$12$..." }]
```

### Fixed temporary password
The temporary password `tmp123` is a **hardcoded constant** in `auth_service.create_user()` — do not make it configurable or env-driven. It is deliberately weak and short-lived; its sole purpose is to give the new user something to log in with before they change it (Story 1.7). The UI banner explicitly prompts the admin to tell the new user to change it.

### `read_user` signature change
The existing `read_user() -> UserRecord | None` signature (no argument) changes to `read_user(username: str) -> UserRecord | None`. Update all call sites: `auth_service.verify_login` and `backend/scripts/setup_auth.py`. The `setup_auth.py` call currently passes no argument — update it to pass the entered username.

### Security
Any authenticated user can create a new account (there is no admin/user role distinction in v1). This is acceptable for the project's single-operator household context. Do **not** add role-based access control in this story.

- Role / permission levels.

- Admin-only access to the create-user endpoint.
- Email or display name fields.
