# Story 1.8: Concurrency-safe JSON persistence (lost-update hardening)

## Status

Ready for Review

## Story

**As** the platform,
**I want** every read-modify-write of a JSON document serialized per file,
**so that** two concurrent requests from the same user can never silently clobber each other's changes (a lost update).

## Context

Every app persists state as JSON files with no database. Each mutation is an
unguarded read-modify-write in the service layer:

```python
doc = repo.read_doc(username)   # read
doc.lists.append(...)           # mutate in memory
repo.write_doc(username, doc)   # write whole doc back
```

`_atomic_write_json` (write-`.tmp`-then-`os.replace`) only guarantees a reader
never sees a *torn* file — it does **nothing** to prevent two writers from
interleaving. The production container runs a **single** uvicorn process with
**sync** (`def`) route handlers, which Starlette dispatches on a threadpool, so
same-user requests genuinely execute concurrently on different threads.

Two concrete lost-update paths already logged in `deferred-work.md`:
- **Whole-doc clobber (context-switch, this epic; archery; hotaru).** Request A
  and B both read `{lists: […]}`; A appends a list and writes; B (holding the
  stale read) writes its own change and erases A's. Newly likely in
  Context-Switch because drag-reorder + the updates log make simultaneous writes
  common (double-click "New list", two tabs, a drag racing an add).
- **Deterministic `.tmp` collision (`session_repo._atomic_write_json`).** The temp
  path is `path + ".tmp"`, so two concurrent writers to the *same* file also
  clobber each other's temp payload before the rename.

This is a platform-wide persistence limitation, not an app bug. The fix belongs
in the shared persistence layer so every app inherits it.

## Acceptance Criteria

1. **Per-file serialized transactions.** Given two concurrent same-user mutations of the same document, when both run, then their read-modify-write sequences are serialized (one fully completes before the other reads), so neither update is lost. The serialization key is the target file path, so mutations to *different* files (different users, different apps) still run concurrently. (NFR-3)

2. **Repo-level transaction API.** Given a service needs to mutate a document, when it does so, then it goes through a single repo helper that acquires the per-file lock, reads the current document, applies the caller's mutation, and writes atomically — the read and the write are never separable by the caller. Services no longer call `read_doc` + `write_doc` as two separate steps for a mutation. (Layering: locking lives in the repositories, the only FS layer.)

3. **Unique temp file per write.** Given two concurrent writes to the same path, when each stages its `.tmp`, then each uses a unique temp filename (so one writer's temp payload can never overwrite the other's) before the atomic `os.replace`. A crash still leaves the previous `path` intact.

4. **Context-Switch adopts the transaction API.** Given `context_switch_service`'s mutating operations (`create_list`, `update_list`, `delete_list`, `add_todo`, `update_todo`, `delete_todo`, `add_update`, `reorder_todos`), when each runs, then it uses the new transaction helper — read-only operations (`list_lists`, `get_list`, `list_archived`) may keep the plain read.

5. **Archery, Hotaru, Auth — and Listies — adopt the transaction API.** (Listies was written after this story was drafted and carries the identical bug; it is in scope.) Given the other persistence modules' mutating operations (archery session save/finalise/discard/label-pick, hotaru word add/edit, auth `write_user` / `change_password` / user management), when each runs, then it uses the same per-file transaction helper. Any label/id-generation that reads then writes (e.g. archery's finalise-label pick) runs inside the transaction so it cannot assign a duplicate.

6. **Concurrency is tested.** Given the transaction helper, when N threads issue conflicting same-key mutations, then a test asserts all N are applied (no lost update); and a test asserts different keys are not serialized against each other (they can overlap). At least one test drives it through the real API with a threaded client for Context-Switch (e.g. many concurrent `POST /lists` for one user → all persisted).

7. **No new runtime dependency; single-process scope is explicit.** Given the fix, when reviewed, then it uses only the standard library (in-process `threading` locks — correct for the single-uvicorn-process deployment) and a code comment documents that a multi-worker/multi-process deployment would require an OS-level file lock instead. (No `filelock`/`fcntl` dependency added in this story.)

## Dev Notes

### Why in-process locks are sufficient (and where they aren't)
Production is a single container running `uvicorn app.main:app` with **no `--workers`** → one process, one interpreter. Sync route handlers run on Starlette's AnyIO threadpool, so the only concurrency is threads sharing memory — a `threading.Lock` registry fully serializes them. **If** the deployment ever moves to multiple uvicorn workers or multiple containers sharing the volume, in-process locks stop working and an OS-level file lock (advisory `fcntl.flock` on POSIX, `msvcrt.locking` on Windows, or the `filelock` package) is required. Call this out in a comment so a future scaling change doesn't silently reintroduce the race.

### The lock must span read→write, not just the write
Locking only inside `write_doc` does not fix anything — both writers would still have read a stale doc. The lock has to be held across the whole read-modify-write, which is why the transaction helper (AC 2) exists and why services must stop doing `read_doc` + `write_doc` as two separate public calls for a mutation.

### Keep the exception/HTTP contract intact
Validation still raises stdlib exceptions (`ValueError` → 422, `FileNotFoundError` → 404) from *inside* the mutator. Ensure the helper does not swallow them and does not write when the mutator raises (no partial writes on a rejected request — matching today's `reorder_todos` "validate before mutate" guarantee).

### Completion Notes

**Two new core modules.**
- `app/core/locks.py` — `key_lock(key)` over a registry of locks. **Reentrant (`RLock`) on
  purpose:** Hotaru services legitimately hold an aggregate's lock across a read-modify-write
  while calling repo helpers that lock the same aggregate; a plain `Lock` self-deadlocks there.
  The trade-off (nesting is permitted rather than rejected) is documented at the call site.
- `app/core/storage.py` — the single `atomic_write_json`. Stages via `tempfile.mkstemp`, flushes
  and `fsync`s, then `os.replace`, and unlinks the temp file if anything raises.

**Three duplicate writers became one.** `session_repo._atomic_write_json`,
`auth_repo._atomic_write_json` and the Hotaru `_storage.atomic_write_json` had drifted apart while
sharing the same deterministic-`.tmp` flaw. All now delegate to `core.storage`, closing the
long-standing "extract to a shared util" cleanup.

**Transaction shape: a context manager, not `mutate_doc(key, mutator)`.** The story's Task 3
suggested a callback helper. `with repo.doc_transaction(username) as doc:` gives the identical
contract — lock held across read→write, no write when the block raises — while changing two lines
per service function instead of restructuring each into a closure. Twenty-two service functions
adopted it this way.

**Adoption.** Context-Switch (9 mutators), Listies (13), Archery (create / update / finalise /
discard / recurring players), Hotaru (vocab, progress, notes, topics — at the repo helpers plus the
two services that compose them), Auth (swapped its private `_auth_lock` for the shared primitive).

**Archery needed a coarse key.** A session's label is allocated by reading every existing label
across many files, so a per-file lock would let two concurrent creates pick the same one.
`sessions_transaction()` uses one key for the archery session space; the same reasoning gave
Hotaru's notes and vocab aggregates one key each, since notes and words move between the shared and
private files. Documented at each definition.

**Scope correction: Listies was missing from the story.** It was written after this story was
drafted and had the identical unguarded read-modify-write. Left out, it would have been the only
app still losing updates. Added to AC 5.

**Every concurrency test was verified non-vacuous.** A throwaway `conftest` replaced `key_lock`
with a no-op and the suite was re-run: 10 of 13 failed. The three that passed were the two that
*should* pass without locking (different keys not blocking each other; a failed mutation writing
nothing) — and one that was genuinely vacuous:
`test_concurrent_finalises_on_one_day_get_distinct_labels` could not collide, because
`create_session` already hands out distinct preferred labels so neither finalise ever reached the
suffix search. It was rewritten to build the colliding state directly (two finalised files already
occupying both preferred labels), and now reproduces the real defect — unguarded, both finalises
claim `2026-09-03-3`. The harness was removed afterwards.

**One test expectation was wrong, not the code.** `add` racing `reorder_todos` does not make the
reorder succeed: `reorder_todos` requires an exact permutation of the active ids, so when the add
lands first the reorder is correctly *rejected* rather than writing a stale order over the new
todo. The test now asserts the honest outcome — either resolution is fine, no todo is lost, and the
board order stays a clean `0..n-1` sequence.

**Behavioural change worth flagging: data files are now `0600`, not `0644`.** `mkstemp` creates the
staged file `0600` and the mode survives `os.replace`. This closes the world-readable-tmp deferred
item and is correct for the single-user container, but it is a real change to on-disk permissions.

**Superseded tests.** Three `test_session_repo.py` tests targeted `session_repo._atomic_write_json`,
which no longer exists there. Their coverage moved to `tests/test_core_storage.py`, extended with
the concurrent-write and cleanup cases they never had.

**Seven deferred-work items closed** (marked in `deferred-work.md`): the private cross-module
import, world-readable temp permissions, the archery label race, the deterministic `.tmp` path,
`_pick_finalise_label` duplicate labels, `update_in_progress` TOCTOU, and the Context-Switch
unguarded-mutation entry.

**Suites:** backend **789** passed (was 781 before this story, 767 before Story 1.1). `black` and
`ruff` clean. Frontend untouched, as the story predicted.

**Still out of scope, as drafted:** multi-worker / multi-container OS file locking (documented in
`core/locks.py`, not implemented), moving off JSON files, and client-facing optimistic concurrency.
