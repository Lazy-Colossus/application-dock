# Story 1.3: Shared per-day data model, repository & per-day write serialization

## Status

Draft

## Story

**As** the platform,
**I want** each day stored as one JSON file keyed by date, with every read-modify-write on a day
serialized against concurrent writers,
**so that** many people answering the same question at once never erase each other's answers.

## Acceptance Criteria

1. **Schemas.** Given `backend/app/schemas/qotd.py`, when models are defined, then Pydantic v2
   models exist for `Answer` (`text: str | None`, `rating: int | None`, `created_at`, `updated_at`)
   and `Day` (`schema_version`, `date`, `question_id`, `answers: dict[str, Answer]`), with a
   model-level rule that an answer sets **exactly one** of `text` / `rating`. (AR-5)

2. **One file per day, no index.** Given `backend/app/repositories/qotd_repo.py`, when it reads and
   writes, then it is the only module touching the filesystem, stores each day at
   `DATA_DIR/qotd/days/{date}.json`, `mkdir(parents=True, exist_ok=True)` on write, routes every
   write through `core.storage.atomic_write_json`, returns a fresh empty `Day` for a date with no
   file yet, and lists days by **scanning the directory** — no index file to become a second
   contention point. (NFR-2, NFR-3, AR-2)

3. **Shared, not per-user.** Given any repo function, when it resolves a path, then the path is
   derived from the **date only**. No function takes a username for file selection; the username
   only decides *whose* answer *within* a day. (FR-2, NFR-2)

4. **Date validation blocks traversal.** Given a date value that is not a canonical `YYYY-MM-DD`
   (separators, `..`, padding, wrong shape), when the repo derives a path from it, then it raises
   `ValueError` rather than reading or writing outside `days/`. (NFR-2)

5. **Transactions consume the platform lock.** Given platform Story 1.8 has landed, when the repo
   serializes a mutation, then it uses `core.locks.key_lock` via a `day_transaction(date)` context
   manager that holds the lock across read→write and writes nothing if the block raises — it does
   **not** define a QotD-local lock. (NFR-1)

6. **Concurrent answers all survive.** Given N threads upserting answers on the **same** day, when
   they interleave on the threadpool, then every answer is applied and none is lost; and given
   mutations of **different** days, then they are not serialized against each other. Both are
   asserted by tests verified to fail with the lock disabled. (NFR-1)

7. **Server-side clock helper.** Given `backend/app/services/qotd_service.py`, when it decides
   "today" or past-vs-present, then it does so through a single helper (`today()` / `now_iso()`)
   that every later story shares, and `today` itself counts as still-writable. (NFR-5)

8. **Layering holds.** Given the service, when it operates on a document, then it raises stdlib
   exceptions only — `FileNotFoundError`, `ValueError` — and never `HTTPException`. (NFR-4)

9. **No regressions.** Given the existing suites, when this story lands, then `pytest` stays green
   and `black` / `ruff` are clean. Frontend untouched.

## Dev Notes

**Story 1.8 has landed — consume it, do not rebuild it.** `app/core/locks.py` provides `key_lock(key)`
(reentrant) and `app/core/storage.py` provides `atomic_write_json`. There is no reason to define a
QotD-local lock. [Source: `docs/stories/application-dock-general/for-review/1.8...story.md`]

**⚠️ Keyed by date, like KDH — not by username.** `kdh_repo` is the closest pattern to copy: it keys
files by calendar id and takes no username for file selection. QotD keys by **date**; the username
only picks a slot in `answers`. Copy `kdh_repo`'s structure (validation helper, `migrate`,
transaction context manager) and change the key to the date. [Source: FR-2, NFR-2]

**Validate the date as untrusted.** The date arrives from the URL in later stories (Story 3.3), so
`_validate_date` must reject anything that is not a canonical `YYYY-MM-DD` — mirror
`kdh_repo._validate_calendar_id`. A `datetime.date.fromisoformat` round-trip plus an exact-shape
check is a good belt-and-braces.

**No index file.** `list_days` scans `days/*.json` (NFR-2/AR-2). An index would be a second file
every answer write must touch — the contention point per-file locking exists to avoid. Precedent:
KDH `list_calendars`, archery `list_sessions`.

**`today()` belongs here.** Stories 2.3 (edit/lock), 3.1 (reveal), 3.2/3.3 (history) all decide
past-vs-present and must agree, and none may trust the client clock (NFR-5). One helper, used
everywhere; `today` is not past (today is still answerable).

**Scope discipline.** No endpoints, no answer upsert, no reveal/lock rules — those are Stories 1.4,
2.1, 2.3, 3.1. This story is the data layer and the shared helpers only.
