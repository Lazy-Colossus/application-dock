# Story 2.1: Add a todo as a colored pill

Status: Draft

## Story

As a user,
I want a plus button that adds a todo with a header, text, and a color,
so that it appears as a big colored pill block on my board.

## Acceptance Criteria

1. **Board loads a list's active todos.** Given a list board (`/context-switch/lists/:listId`), when it loads, then it fetches the list with its active todos (`GET /api/context-switch/lists/{list_id}`) and renders each active todo as a large **pill block** showing its header and body text. (FR-6)

2. **Plus button adds a todo.** Given the board, when I click the **plus** button and enter a header and body text, then `POST /api/context-switch/lists/{list_id}/todos` with `{ header, body, color }` creates the todo (`status: "active"`, `order` = end of the active list) and it appears as a new pill. (FR-6)

3. **Color choice — preset or custom.** Given the add form, when I choose a color, then I can pick from a **preset palette** (fixed swatches) or set a **custom** color; the created pill renders in that color. (FR-7)

4. **Readable contrast.** Given a chosen pill color, when the pill renders, then its header/body text uses a foreground that stays readable against that background (e.g. compute light/dark text from the color's luminance). (FR-7, NFR-1)

5. **Header required.** Given a submission with an empty/whitespace header, when submitted, then it is rejected — the client disables submit and the API backstops with a `422` `{detail}`. Body may be empty.

6. **Persisted & isolated.** Given a created todo, when the board reloads (or another device logs in as me), then the todo is still there; another user never sees it. (FR-2)

## Dev Notes

**Pill = the core visual.** The "big pill block" is the app's signature UI. Keep `TodoPill` a dumb presentational component (`defineProps<{ todo: Todo }>()`); the contrast/text-color helper is a small pure function (unit-test it directly).

**Color model.** Store the color as a hex string on the todo. Preset swatches and the custom picker both resolve to the same `#rrggbb` field — no separate "preset vs custom" flag needed (YAGNI). Validate hex server-side.

**Ordering.** New todos append at the end of the active order; a numeric `order` field on each todo is the source of truth (drag reorder in Story 2.3 rewrites it). Archived todos are excluded from the active-order sequence.

**Coding standards.** `<script setup lang="ts">`, `defineProps<{}>()`/`defineEmits<{}>()`, `interface` for object shapes, no `any` without justification; all HTTP via `useApi`; store exposes `loading`/`error`. [Source: CLAUDE.md#Conventions/Frontend]
