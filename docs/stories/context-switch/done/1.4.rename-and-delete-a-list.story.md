# Story 1.4: Rename and delete a list

Status: Done

## Story

As a user,
I want to rename a list or delete one I no longer need,
so that I can keep my set of boards tidy.

## Acceptance Criteria

1. **Rename a list.** Given a list, when I rename it (`PATCH /api/context-switch/lists/{list_id}` with `{ name }`), then the name updates in my file and everywhere it is shown; a blank name is rejected with a `422`/`400` `{detail}` error. (FR-5)

2. **Delete a list (with confirm).** Given a list, when I choose delete and confirm, then `DELETE /api/context-switch/lists/{list_id}` removes the whole list (and all its todos) from my file and it disappears from the picker; the UI requires an explicit confirmation before sending the request. (FR-5)

3. **Unknown / not-mine list → 404.** Given a rename/delete for a `list_id` not present in my file, when requested, then the API returns `404` with a `{detail}` message. Because the file is chosen from the token, a user can never rename/delete another user's list. (FR-2)

4. **State stays consistent.** Given the picker after a rename or delete, when it re-renders, then it reflects the change without a manual refresh (store updates locally or refetches).

## Dev Notes

**404 vs isolation.** "Not mine" and "doesn't exist" collapse to the same `404` on purpose — the service only ever looks inside the caller's own document, so another user's list id is simply "not found." This is the correct, leak-free behavior. [Source: Story 1.2 Dev Notes]

**Confirm before destructive action.** Deleting a list discards its todos. Require an explicit confirm dialog (Quasar `$q.dialog` or a small confirm component) — mirror any existing destructive-confirm pattern in the app (e.g. archery discard/finalise flows).

**PATCH is shared.** `PATCH /lists/{list_id}` handles name here and will also handle `grid` in Story 2.2 — design the request schema so fields are optional (only-provided fields update).
