# Story 2.3: Reorder todos by drag

Status: Done

## Story

As a user,
I want to drag todos to reorder them,
so that I can arrange my board by priority.

## Acceptance Criteria

1. **Drag to reorder.** Given a board with several active todos, when I drag a pill to a new position, then the pills visually re-sequence to the new order. (FR-9)

2. **Order persists.** Given a completed drag, when the new order is committed (`POST /api/context-switch/lists/{list_id}/todos/reorder` with the new ordered active-todo ids), then each todo's `order` is rewritten and the new order is intact after a reload. (FR-9)

3. **Active-only, validated.** Given a reorder request, when processed, then it must reference exactly the list's current active todo ids; an id set that adds/omits/duplicates ids, or references an archived/unknown id, is rejected with a `422` `{detail}` and no partial write.

4. **Interacts with pagination.** Given the C×R paginated grid (Story 2.2), when I reorder, then the resulting order is coherent across pages (order is a single sequence over all active todos, independent of the current page).

### Completion Notes

- **Backend:** `service.reorder_todos` validates first, mutates second — a duplicate id, a wrong-sized set, or any id that is not a currently-active todo of *this* list raises `ValueError` before a single `order` is touched, so a rejected request can never be a partial write (AC 3). Valid input assigns `order` by index and writes once through the atomic repo. Router: `POST /lists/{list_id}/todos/reorder`, `FileNotFoundError` → 404, `ValueError` → 422. Returns the reordered board so a caller can resync without a second GET.
- **No new dependency (YAGNI).** The stack ships no DnD library, so this uses **native HTML5 drag events**. The dragged id lives in a component ref (`dataTransfer` is also populated with `text/plain` purely because Firefox refuses to start a drag otherwise). Pills sit in a `.cs-slot` wrapper that carries `draggable`, the handlers, and the drag affordance, which keeps `TodoPill` a dumb presentational component.
- **Reorder math is a pure function,** `apps/context-switch/reorder.ts#moveId` — move-to-target semantics over an id list, returning the input unchanged on a no-op. Unit-tested directly (forward, backward, permutation preserved, no-ops, no mutation).
- **Pagination interaction (AC 4):** the drop handler builds the id list from `store.activeTodos` — the **whole** active sequence — not from the visible page, so `order` stays one coherent sequence regardless of which page the drag started on. Covered by a test that drags on page 2 of a 2×1 grid and asserts the posted sequence spans all four todos.
- **Optimistic with rollback:** `reorderTodos` snapshots each todo's `order` into a `Map`, applies the new indices immediately, then POSTs. On failure it restores every snapshotted order, routes the message into `error`, and rethrows. A test drives this through a deliberately unresolved promise to prove the reorder is visible *before* the request settles.
- **Tests:** backend +11 (permutation rewrites and persists across a reload; missing/extra/duplicate/unknown/other-list ids → 422 with the order untouched; a reorder naming an archived todo → 422; archived todos excluded from the sequence; empty list no-op; unknown list → 404; cross-user 404). The two archived-todo cases set their fixture by flipping `status` on disk through the repo, since archiving itself lands in Story 2.6. Frontend +11 across `reorder`, the store, and the board. Full suites: backend **408**, frontend **436** — no regressions.

## Dev Notes

**Order is one sequence over active todos.** `order` is a per-todo integer; the reorder endpoint takes the full ordered id list and rewrites indices. Sending the complete set (not a single from/to) makes validation trivial (permutation check) and avoids drift. Archived todos are not part of the sequence.

**Optimistic UX.** Reorder should feel instant — update the local store immediately, POST in the background, and roll back to the previous order if the request fails (surface via `error`). Mirror the optimistic pattern used elsewhere in the codebase.

**Dependency prudence (YAGNI).** Prefer native drag events. Only add a DnD library if the codebase already includes one; note the choice in the Dev Agent Record when implementing.

**Scope.** This story does not touch archived todos or editing — just reordering active pills.
