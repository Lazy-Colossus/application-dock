# Story 2.7: Archive view — browse and permanently delete

Status: Done

## Story

As a user,
I want to see a list's archived todos and delete them for good,
so that I can review finished work and clear it out.

## Acceptance Criteria

> **Superseded by Story 2.8:** the `body`/`text` field was removed. Where AC1 says archived todos show "header, text, color", the archive now shows the header, color, `archived_at`, and the latest updates-log entry as a preview — there is no standalone `text`/`body`. The code is coherent with 2.8; this AC text is retained for history.

1. **Browse the archive.** Given a list, when I open its archive view (`GET /api/context-switch/lists/{list_id}?include=archived`, or a dedicated archived read), then I see the archived todos (header, text, color, `archived_at`) separated from the active board. (FR-13)

2. **Permanent delete.** Given an archived todo, when I delete it (`DELETE /api/context-switch/lists/{list_id}/todos/{todo_id}`), then it is permanently removed from my file and disappears from the archive. (FR-13)

3. **Terminal — no reopen.** Given the archive view, when rendered, then it offers view + delete only; there is no reopen-to-active affordance in v1. (FR-13)

4. **Delete guarded + scoped.** Given a delete, when triggered, then the UI confirms first; a delete for a `todo_id` not in my file returns `404`; a user can only delete todos in their own file. (FR-2, FR-13)

5. **Active board unaffected.** Given a delete from the archive, when it completes, then the active board is unchanged (delete only ever targets an archived record here).

### Completion Notes

- **Backend:** two new service functions — `list_archived(username, list_id) -> list[Todo]` (archived todos, sorted `archived_at` desc) and `delete_todo(username, list_id, todo_id) -> None` (drops the record from the array, `FileNotFoundError` if absent). Two routes: `GET /lists/{list_id}/archived` (dedicated read, chosen over an `?include=archived` flag so the board's `TodoList` response model stays untouched) and `DELETE /lists/{list_id}/todos/{todo_id}` (204). Both map `FileNotFoundError → 404`, so an unknown id and another user's list are indistinguishable 404s (per-user scoping).
- **Delete is status-agnostic in the service** but reached only from the archive view in v1 — the door stays open for a future direct active-delete without a new function (per the story). Active reads still go through `_board_view`, so deleting an archived todo never disturbs the board (AC 5, tested).
- **`ArchiveDrawer.vue`** (new): a dialog listing archived todos (header, body, color as a left border, formatted `archived_at`), each with a trash button that flips to an inline **"Delete for good?" Yes/No** confirm — the same inline-confirm pattern as list delete (Story 1.4), not a second modal. There is deliberately **no reopen control** (terminal by design, AC 3). It emits `delete` only after the confirm; the parent owns the store call.
- **Board wiring:** an archive icon button (`inventory_2`) in the header opens the drawer and calls `store.fetchArchived`; `onDeleteArchived` calls `store.deleteTodo`, which drops the row from `store.archived` on success so it disappears from the drawer immediately.
- **Store:** new `archived` ref plus `fetchArchived(listId)` and `deleteTodo(listId, todoId)`, both `loading`/`error` managed; `deleteTodo` rethrows on failure (keeping the row) while `fetchArchived` surfaces the error and clears the local list.
- **Tests:** backend +9 (archived read returns only archived with all fields; empty when none; ordered `archived_at` desc; unknown list 404; cross-user 404; delete removes the record; delete leaves the active board intact; unknown todo 404; unknown list 404; cross-user delete 404). Frontend +11 (`ArchiveDrawer` 5: empty state, item render, no-reopen, confirm-before-delete, cancel; store 4: fetch, fetch-error, delete-drops-row, delete-error-keeps-row; board 2: open drawer loads archived, delete from drawer). Full suites: backend **449**, frontend **473** — no regressions.
- **Pre-existing, untouched:** the two `QNotifyCreateOptions` `vue-tsc` errors in `src/pages/SettingsPage.vue`; ESLint/prettier remain unconfigured project-wide. None relate to this story.

## Dev Notes

**Delete lives only in the archive.** Per the user's management choices, permanent delete of a todo is reached from the archive view — there is no "delete active todo" path (an active todo is closed as done first, then optionally deleted). If a direct active-delete is ever wanted, it reuses `delete_todo` with a different entry point. [Source: user decisions — "delete archived todos"; no "delete individual (active) todos"]

**Archived read = the counterpart to the active filter (Story 2.6).** Both read the same file; centralize the active/archived split in the service so this view and the board stay consistent.

**Confirm before permanent loss.** Deletion is irreversible (no reopen, no undo in v1) — always confirm. Reuse the confirm pattern from list delete (Story 1.4).
