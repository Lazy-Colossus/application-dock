# Story 2.5: Add timestamped updates to a todo

Status: Done

## Story

As a user,
I want to append dated updates to a todo without changing its original text,
so that I keep a running history of progress.

## Acceptance Criteria

1. **Append an update.** Given an open todo, when I add an update entry (`POST /api/context-switch/lists/{list_id}/todos/{todo_id}/updates` with `{ text }`), then a new `u-{uuid8}` entry with the text and an ISO-8601 `created_at` is appended to the todo's `updates`, and the todo's original header/body are unchanged. (FR-11)

2. **Log renders in order.** Given a todo with updates, when the detail view renders, then all update entries display in chronological order with their timestamps. (FR-11)

3. **Empty update rejected.** Given an empty/whitespace update text, when submitted, then it is rejected (client-disabled + `422` backstop).

4. **Append-only.** Given the updates log, when viewed, then updates cannot be edited or deleted in v1 — they are an append-only history. (FR-11)

5. **Unknown ids → 404.** Given an update POST for a `list_id`/`todo_id` not in my file, when requested, then the API returns `404`.

### Completion Notes

- **Backend:** `service.add_update` mints a `u-` id, appends a `TodoUpdate(text=trimmed, created_at=now)` to `todo.updates`, and persists — it never touches `header`/`body` and, deliberately, does **not** bump `updated_at` (that field tracks edits to the todo itself; a log entry is not an edit). Blank/whitespace text raises `ValueError` → 422; an absent list *or* todo raises `FileNotFoundError` → 404 via the existing `_find_list`/`_find_todo` helpers.
- **Endpoint:** `POST /lists/{list_id}/todos/{todo_id}/updates` with `AddUpdateRequest{ text }`. It sits alongside the fixed-segment `…/todos/reorder` route without collision (different path depth), and the append-only design means there is no PUT/DELETE for individual entries (AC 4 — YAGNI).
- **Frontend flow mirrors edit:** the dialog emits `add-update` with trimmed text; `BoardPage.onAddUpdate` calls `store.addUpdate`, which POSTs and replaces the local todo in `currentList.todos` with the response (carrying the new entry). Because the board tracks the open todo **by id** (`openTodoItem` computed), the dialog's `todo` prop updates reactively and the log re-renders with the new entry — no manual refresh.
- **Dialog:** existing entries render read-only (text + `formatAt(created_at)` local date-time, chronological/insertion order = oldest→newest as a progress diary). The add-update input's button is disabled on blank/whitespace; the input clears after adding and is reset when the dialog reseeds onto a different todo. Adding an update does **not** close the dialog (distinct from Save).
- **Tests:** backend +9 (`add_update` appends and leaves header/body intact; persists; multiple appends preserve order; trims text; blank → 422 with log untouched; does not bump `updated_at`; unknown todo → 404; unknown list → 404; cross-user 404). Frontend +7 (store `addUpdate` posts + replaces todo, and error path leaves it untouched + rethrows; dialog chronological render, no edit/delete affordance, add disabled until non-blank, disabled on whitespace, emits trimmed text + clears input). Full suites: backend **429**, frontend **459** — no regressions.

## Dev Notes

**Distinct from editing (Story 2.4).** Editing changes header/body in place (mutates the current text); an **update** is an immutable, timestamped log entry that never alters the original. Both live on the same todo; the detail dialog shows editable header/body at top and the append-only update log below. [Source: user decision — "Editable notes + log"]

**Timestamps.** Use the service's `now` helper (server-side ISO-8601). Format for display on the frontend; store raw ISO. Chronological order = insertion order (append to the end); render oldest→newest or newest→oldest consistently (pick one; oldest→newest reads as a progress diary).

**Append-only (YAGNI).** No edit/delete of individual updates in v1. Don't build those controls.
