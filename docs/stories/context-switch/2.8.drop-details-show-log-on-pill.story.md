# Story 2.8: Drop the details field; show the updates log on the pill

Status: In Progress

## Story

As a user,
I want a todo to be just a header plus its running updates log — no separate "details" field —
and I want the pill to show my two most recent updates,
so that the pill itself is the live progress view and I stop maintaining two overlapping text fields.

## Why this change (rationale)

Stories 2.1/2.4 gave a todo a **header + body ("details")**, and Story 2.5 added an **append-only
updates log**. In practice these two overlap: the body is a static blob you overwrite, while the log
is the thing you actually keep current. Maintaining both is redundant, and the body took the pill
space that the *live* information (the latest updates) should occupy. So we remove the body entirely
and let the log be the todo's content, surfaced directly on the pill.

**This deliberately supersedes FR-6 and FR-10** ("header **and body**"): a todo is now **header +
color + updates log**. FR-11 (the log) is unchanged and becomes the single content channel.

[Source: user decision, 2026-08-14 — "remove the details section… I don't want the details field
any more… in the pill space where details displayed, show the logs, most recent on top and the one
before under it at 50% opacity."]

## Acceptance Criteria

1. **No body field anywhere.** Given the todo model, when a todo is created or read, then it has no
   `body` field — it is removed from the backend schema, the create/update request bodies, the
   service, and all frontend types. (supersedes FR-6/FR-10)

2. **Add = header + color + optional first update.** Given the "Add todo" dialog, when I create a
   todo, then I set a header and color and *may* type an optional first update; on submit
   (`POST …/lists/{list_id}/todos` with `{ header, color, update? }`) the todo is created and, if the
   first-update text is non-blank, a `u-…` entry is appended to its log. A blank/absent first update
   just creates a todo with an empty log. (FR-6 amended, FR-11)

3. **Edit = header + color only.** Given an open todo, when I edit it, then the detail dialog exposes
   the header, color, the updates log, and the add-update input — but no body field; saving PUTs only
   header/color changes. (FR-10 amended)

4. **Pill shows the two most recent updates.** Given a todo with updates, when its pill renders, then
   below the header it shows the **most recent** update at full opacity and, beneath it, the
   **previous** update at 50% opacity. With one update only the latest shows; with none the pill shows
   just the header. (FR-11)

5. **Existing body data is dropped, not migrated.** Given a todo already on disk that carries a
   `body`, when it is next read/written, then the `body` key is ignored and dropped on the next write
   (no migration into an update) — accepted per the user's "full removal" decision.

6. **No regressions to the rest of the board.** Given archive, reorder, grid, and updates behaviour,
   when this change lands, then all of it still works — only body is gone and the pill's secondary
   content is now the log.

## Dev Notes

**Single content channel.** After this story the todo's content lives only in the append-only log
(FR-11). The pill is the live view of that log (latest two entries); the detail dialog is where you
read the full log and append to it. Header + color are the only other editable fields.

**No body migration (YAGNI + user decision).** We are not converting existing `body` text into a
first update — the user accepted losing it. Pydantic ignores the extra key on read and it disappears
on the next write. If preserving old bodies ever matters, a one-off `migrate()` could fold `body`
into a `u-…` entry, but we ship nothing for it now.

**Pill ordering.** `updates` is stored oldest→newest (append at the end), so "latest" is the last
element and "previous" is the second-to-last. The pill renders newest-on-top; the detail log keeps
its oldest→newest progress-diary order.

**Coding standards.** `defineProps<{}>()`/`defineEmits<{}>()`, no `any`; HTTP via `useApi`; store
`loading`/`error`. [Source: CLAUDE.md#Conventions]
