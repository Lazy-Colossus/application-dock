# Story 2.2: Choose the grid — columns and rows

Status: Draft

## Story

As a user,
I want to choose how many columns and rows the board shows,
so that I can size the grid to my screen and how much I want to see at once.

## Acceptance Criteria

1. **Columns/rows control on the board.** Given the list board, when I set the number of **columns** and **rows**, then the active todos render in that fixed **C×R** grid of pills. (FR-8)

2. **Overflow paginates.** Given more active todos than fit in one C×R page, when the board renders, then the extra todos are reachable via pagination (page controls / next-prev), and no active todo is silently hidden. (FR-8)

3. **Saved per list.** Given I change the grid, when I set it, then it persists for that list (`PATCH /api/context-switch/lists/{list_id}` with `{ grid: { columns, rows } }`) and is still in effect when I reopen the list later. (FR-8)

4. **Sane bounds.** Given the control, when I pick values, then `columns` and `rows` are bounded (each `>= 1`, with a reasonable max) and invalid values are rejected (`422`).

5. **Graceful narrow-screen fallback.** Given a screen too narrow for the chosen column count, when the board renders, then it degrades to fewer columns rather than overflowing horizontally (desktop-first, not broken on smaller screens). (NFR-1)

## Dev Notes

**"Rows" = page height, not a hard cap on how many todos exist.** The grid is a *view* over the active todos: page size = `columns * rows`; todos beyond the current page paginate. Adding more todos never deletes or hides them — it just adds pages. [Source: user decision — "Columns + rows = fixed grid"]

**Grid persists on the list, not per user.** The `grid` field lives on each `TodoList` (see data model), so different lists can have different shapes. [Source: user decision — saved per list]

**Reuse the shared PATCH.** Story 1.4 introduced `PATCH /lists/{list_id}` with optional fields; add `grid` as another optional field rather than a new endpoint.

**Desktop-first (NFR-1).** Honor the chosen columns on wide screens; clamp down gracefully on narrow ones. Don't build a separate mobile layout — just prevent horizontal overflow.
