# Story 2.5: Add timestamped updates to a todo

Status: Draft

## Story

As a user,
I want to append dated updates to a todo without changing its original text,
so that I keep a running history of progress.

## Acceptance Criteria

1. **Append an update.** Given an open todo, when I add an update entry (`POST /api/context-switch/lists/{list_id}/todos/{todo_id}/updates` with `{ text }`), then a new `u-{uuid8}` entry with the text and an ISO-8601 `created_at` is appended to the todo's `updates`, and the todo's original header/body are unchanged. (FR-11)

2. **Log renders in order.** Given a todo with updates, when the detail view renders, then all update entries display in chronological order with their timestamps. (FR-11)

3. **Empty update rejected.** Given an empty/whitespace update text, when submitted, then it is rejected (client-disabled + `422` backstop).

4. **Append-only.** Given the updates log, when viewed, then updates cannot be edited or deleted in v1 — they are an append-only history. (FR-11)

5. **Unknown ids → 404.** Given an update POST for a `list_id`/`todo_id` not in my file, when requested, then the API returns `404`.

## Dev Notes

**Distinct from editing (Story 2.4).** Editing changes header/body in place (mutates the current text); an **update** is an immutable, timestamped log entry that never alters the original. Both live on the same todo; the detail dialog shows editable header/body at top and the append-only update log below. [Source: user decision — "Editable notes + log"]

**Timestamps.** Use the service's `now` helper (server-side ISO-8601). Format for display on the frontend; store raw ISO. Chronological order = insertion order (append to the end); render oldest→newest or newest→oldest consistently (pick one; oldest→newest reads as a progress diary).

**Append-only (YAGNI).** No edit/delete of individual updates in v1. Don't build those controls.
