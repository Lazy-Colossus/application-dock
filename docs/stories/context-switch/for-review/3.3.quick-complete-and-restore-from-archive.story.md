# Story 3.3: Complete a todo from its pill, and restore one from the archive

Status: Ready for Review

## Story

As a user,
I want to tick a todo off straight from its pill, and to pull one back out of the archive if I tick it off by mistake,
so that finishing work costs one tap and is not a one-way door.

## Acceptance Criteria

1. **A complete control on every active pill.** Given an active todo on the board, when its pill renders, then it carries a small complete control (a check) in its top-right corner, always visible, with an accessible label. (FR-16)

2. **Confirm, then archive.** Given the complete control, when I use it, then it turns into a confirm ("Done?" / yes-no, mirroring the archive drawer's delete confirm); confirming archives the todo exactly as "close as done" does today — `status: "archived"`, `archived_at` stamped, the pill leaves the board, the record kept. Cancelling leaves the todo untouched. (FR-16, FR-12)

3. **It does not open the todo.** Given the complete control (or its confirm buttons), when I click it, then the detail dialog does not open — the pill's own click-to-open is suppressed for that click. (FR-16, FR-10)

4. **The pill still drags.** Given a pill carrying the control, when I drag it, then reorder (Story 2.3) and move-to-another-list (Story 3.2) behave exactly as before. (FR-9, FR-15)

5. **One pending confirm at a time.** Given a pill showing its confirm, when I start a confirm on another pill (or the todo leaves the board), then the first pill returns to its resting state — no pill is left stuck mid-confirm.

6. **Restore from the archive.** Given an archived todo in the archive view, when I restore it, then `status` returns to `"active"`, `archived_at` is cleared, and its header, color and full updates log are unchanged. (FR-17)

7. **It comes back last.** Given a restored todo, when the board renders, then it is the last of that list's active todos — it takes a fresh `order` rather than the (likely now-taken) one it held when archived, and no other todo's order changes. (FR-17, FR-9)

8. **Both views agree.** Given a restore, when it succeeds, then the todo disappears from the archive list and appears on the board without a manual reload, and the list's active count includes it again. (FR-17, FR-13)

9. **Failures are visible and safe.** Given a complete or a restore that the API rejects, when it fails, then the message surfaces via `store.error`, the todo stays where it was, and no half-applied state is left behind (no pill removed from the board, no row removed from the archive).

### Completion Notes

- **Backend is four lines.** `update_todo` now takes the list as well as the todo (`_find_list` result reused rather than discarded) and, when `status` transitions *into* `"active"` from something else, reassigns `order = max(active order) + 1` before flipping the status. The transition guard matters: a PUT of `status: "active"` on an already-active todo must not shuffle it to the end, which is its own test. No new route, no new schema — restore is the `PUT /todos/{id}` that Story 2.6 already left the door open for, and its docstring now says so.
- **The collision test earns its place.** Archiving all three todos, adding a fourth (which takes `order` 0), then restoring the first reproduced exactly the tie the story predicted — two todos at `order` 0, resolved by array position. It failed before the fix and pins the behaviour now.
- **`restoreTodo` is a separate store action, not `updateTodo`.** An archived todo is absent from `currentList.todos` entirely (the board read returns active todos only), so `updateTodo`'s index-replace would have silently done nothing. It drops the row from `archived`, pushes the server's copy onto the board guarded on `currentList.id === listId` (the Story 3.2 review's finding, applied up front here), and bumps the summary count.
- **Plain buttons on the pill, not `q-btn`.** The pill is a bespoke coloured surface; a Material button inside it fights the pill's own palette, and `TodoPill.spec.ts` mounts the component with no Quasar stubs. The controls are `<button>`s styled with `currentColor`, so they stay legible on both light and dark pill colours. All three (`✓`, `Done?`, `✕`) use `@click.stop` — the confirm needs it as much as the check does, since a bubbled confirm would archive the todo *and* open its dialog. A test asserts the dialog stays shut through the whole flow.
- **Confirm state lives in the pill** and resets on a `todo.id` change, so a recycled pill never renders mid-confirm (AC 5's "no pill stuck mid-confirm"). One pill at a time falls out of this naturally: each pill owns its own flag, and the board re-renders from the store.
- **Restore has no confirm** — it is the safe direction and is itself the undo for a mistaken complete. Delete keeps its confirm.
- **`ArchiveDrawer.spec.ts` lost a test on purpose:** "offers no reopen affordance (terminal — view + delete only)" encoded Story 2.7's v1 decision that FR-17 revises. It is replaced by two tests asserting the restore control exists and emits without a confirm.
- **Tests:** backend +7 (restored todo lands last; no collision with an order taken since; empty board → `order` 0; other todos' orders untouched; header/colour/updates/`archived_at` intact; back in the active count and out of the archive; an already-active PUT does not move it). Frontend +11 (3 store, 4 pill, 2 drawer, 3 board). Full suites: backend **475**, frontend **512** — no regressions.
- **Not verified in a browser.** AC 4 is covered at the slot level (a pill-to-pill drag still reorders with the control present), but jsdom cannot tell you whether *pressing the button itself* starts a drag on a touch device. Worth a manual pass along with the Story 3.2 drag check.

## Dev Notes

**Reuse the archive path, don't fork it.** Quick-complete is not a new lifecycle — it is the existing `status: "archived"` mutation with a cheaper trigger. `BoardPage.onCloseAsDone` already does exactly this from the detail dialog; the pill emits and the board calls the same store action. Resist adding a `/complete` endpoint.

**Restore reverses a documented v1 decision.** Story 2.7 states "this is terminal — there is no reopen in v1 (FR-13)". This story revises that for *archiving* only; permanent delete stays terminal. The epics file records the revision as FR-17 — keep the two documents in agreement.

**Why `order` must be reassigned.** `update_todo` currently leaves `order` alone when flipping status. A todo archived at `order: 2` restored into a board whose actives are `0..5` would tie with whatever holds `2` now, and `activeTodos` sorts by `order` alone — so the tie resolves by array position, i.e. arbitrarily. Appending (`max + 1`) is the same rule `move_todo` uses and keeps the sequence honest without a compaction pass.

**Click layering on the pill.** The whole pill is `role="button"` with `@click="emit('open')"`. Any control inside it must `@click.stop`, and the *confirm* and *cancel* buttons need it just as much as the check does — a confirm click that bubbles would archive the todo and open the dialog for it. Drag is unaffected (`dragstart` is a separate event on the wrapping `.cs-slot`), but check that pressing the button does not begin a drag on touch.

**No toast, no undo.** The archive is the undo path (that is half of this story), so there is no transient notification to build. The app does not use Quasar Notify anywhere yet — do not introduce it here.

**Concurrency.** Both mutations are the usual unguarded read-modify-write of the user document — the platform-wide defer (Story 1.8). Nothing story-specific to do.

**Scope.** No bulk complete, no multi-select, no "restore all", no reopen from anywhere but the archive view.
