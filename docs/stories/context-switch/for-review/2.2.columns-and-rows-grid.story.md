# Story 2.2: Choose the grid — columns and rows

Status: Ready for Review

## Story

As a user,
I want to choose how many columns and rows the board shows,
so that I can size the grid to my screen and how much I want to see at once.

## Acceptance Criteria

1. **Columns/rows control on the board.** Given the list board, when I set the number of **columns** and **rows**, then the active todos render in that fixed **C×R** grid of pills. (FR-8)

2. **Overflow paginates.** Given more active todos than fit in one C×R page, when the board renders, then the extra todos are reachable via pagination (page controls / next-prev), and no active todo is silently hidden. (FR-8)

3. **Saved per list.** Given I change the grid, when I set it, then it persists for that list (`PATCH /api/context-switch/lists/{list_id}` with `{ grid: { columns, rows } }`) and is still in effect when I reopen the list later. (FR-8)

4. **Sane bounds.** Given the control, when I pick values, then `columns` and `rows` are bounded (each `>= 1`, with a reasonable max) and invalid values are rejected (`422`).

5. **Graceful narrow-screen fallback.** Given a screen too narrow for the chosen column count, when the board renders, then it degrades to fewer columns rather than overflowing horizontally (desktop-first, not broken on smaller screens). (NFR-1)

### Completion Notes

- **Backend — folded into the existing update, as the story suggested.** `service.rename_list` became `service.update_list(username, list_id, *, name=None, grid=None)`: one read, apply whichever fields were provided, one write. `UpdateListRequest` gained `grid: Grid | None`, so bounds validation is the `Grid` schema's existing `ge=1, le=12` — an out-of-bounds grid is a 422 from FastAPI with no service branch. The router's "no updatable fields" guard now checks both fields. As in Story 1.4 the verb stays **PUT**, not PATCH (the `useApi` boundary has no `patch`).
- **Consistency fix while here:** `create_list`/`update_list` now return the same active-only projection as `get_list` via a shared `_board_view` helper. Before this, `PUT /lists/{id}` would have returned archived todos too while `GET` filtered them — a trap for any caller that assigned the whole response into the board.
- **Grid math is a pure module,** `apps/context-switch/grid.ts`: `clampGridValue`, `pageSize`, `pageCount`, `pageSlice`, plus the bounds mirroring the backend. Unit-tested directly, including the AC-2 invariant that walking every page yields every todo in order — nothing is silently hidden.
- **`GridControl`** is two bounded number inputs emitting the whole `Grid`; it clamps before emitting and stays silent when the value did not actually change (so a no-op blur does not fire a PUT).
- **Layout (AC 1 + 5):** the board sets `--cs-cols` inline and uses `repeat(var(--cs-cols), minmax(0, 1fr))`. The `minmax(0, 1fr)` is what makes horizontal overflow impossible — columns shrink instead. Two media queries then drop the column count outright (`auto-fit` under 900px, single column under 480px) so pills stay usable rather than merely non-overflowing.
- **Stranded-page guard:** shrinking the board or growing the grid can leave the viewer past the last page, so `BoardPage` watches `totalPages` and pulls `page` back to the final one instead of rendering an empty board.
- **Tests:** backend +11 (grid persists and reloads, grid-only update leaves the name alone, name+grid together, empty body → 422, five out-of-bounds cases parametrized, and an explicit check that a 1×1 grid does not cap how many todos exist). Frontend +18 across `grid`, `GridControl`, store, and board (column count, single page with no pager, overflow paging with every todo reachable, persisted grid change, stranded-page recovery). Full suites: backend **397**, frontend **425** — no regressions.

## Dev Notes

**"Rows" = page height, not a hard cap on how many todos exist.** The grid is a *view* over the active todos: page size = `columns * rows`; todos beyond the current page paginate. Adding more todos never deletes or hides them — it just adds pages. [Source: user decision — "Columns + rows = fixed grid"]

**Grid persists on the list, not per user.** The `grid` field lives on each `TodoList` (see data model), so different lists can have different shapes. [Source: user decision — saved per list]

**Reuse the shared PATCH.** Story 1.4 introduced `PATCH /lists/{list_id}` with optional fields; add `grid` as another optional field rather than a new endpoint.

**Desktop-first (NFR-1).** Honor the chosen columns on wide screens; clamp down gracefully on narrow ones. Don't build a separate mobile layout — just prevent horizontal overflow.
