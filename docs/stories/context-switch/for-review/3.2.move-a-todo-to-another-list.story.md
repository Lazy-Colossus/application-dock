# Story 3.2: Move a todo to another list by dragging it onto the list name

Status: Ready for Review

## Story

As a user,
I want to drag a todo onto the list name and drop it into one of my other lists,
so that I can move work between contexts without retyping it.

## Acceptance Criteria

1. **Hovering the name mid-drag opens the list popup.** Given I am dragging a todo pill, when I hold it over the list name for a short dwell (~600 ms), then a popup opens anchored under the name listing my other lists as drop targets; the list I am on is not among them. (FR-15)

2. **Drop moves the todo.** Given the popup is open mid-drag, when I drop the pill onto one of the lists, then `POST /api/context-switch/lists/{list_id}/todos/{todo_id}/move` with `{ target_list_id }` moves it, the pill leaves this board, and it is present when I open the destination list. (FR-15)

3. **Everything about the todo survives.** Given a moved todo, when I open it in its new list, then its id, header text, color, status, and its entire `updates` log are unchanged — a move is not a copy-and-recreate. (FR-15, FR-11)

4. **It lands last, and no order is disturbed.** Given a move, when both boards render, then the todo is last among the destination list's active todos, the destination's existing todos keep their relative order, and the source list's remaining todos stay in their order with no gap-induced reshuffle. (FR-15, FR-9)

5. **Counts follow.** Given a completed move, when I go back to the picker, then the source list's active count is one lower and the destination's one higher, without a manual reload.

6. **Rejections are clean.** Given a move naming a list or todo that is not mine (or does not exist), when requested, then the API returns `404` `{detail}` and nothing is written. Given a move whose `target_list_id` is the source list, or which names an archived todo, then it is rejected with `422` `{detail}` and nothing is written. (FR-2)

7. **The popup gets out of the way.** Given the popup is open, when I drop, cancel the drag (`dragend`/Escape), or drag away from both the name and the popup, then it closes; a failed move closes it too and surfaces the message via `store.error`, leaving the pill on the board.

8. **Reordering still works.** Given the drag interaction, when I drop a pill on another pill, then it reorders as before (Story 2.3) — the list-name drop target does not capture ordinary reorder drags.

### Completion Notes

- **Backend:** `service.move_todo` resolves both lists and the todo, then rejects a same-list move (`ValueError`) or a non-active todo (`ValueError`) — all before any mutation, so a rejected move is never a partial write. It then detaches the todo from the source, sets `order` to `max(active order in target) + 1` (not `len(...)`, which would collide with a target whose orders have gaps), appends it, and writes the doc once. Router: `POST /lists/{list_id}/todos/{todo_id}/move`, `FileNotFoundError` → 404 "List or todo not found", `ValueError` → 422. Returns the moved `Todo`.
- **Store:** `moveTodo` is deliberately non-optimistic — it awaits the POST, then drops the todo from `currentList.todos` and shifts `active_count` between the two summaries. A rejection leaves the board untouched, sets `error`, and rethrows.
- **Popup: a plain absolutely-positioned panel, not `q-menu`.** Quasar's menu teleports its content out of the page subtree, which puts a detached node under a live native drag — the failure mode is browser-specific and untestable in jsdom. The panel lives inside a `position: relative` header wrapper, so it is one ordinary element the drag never leaves. No new dependency, consistent with Story 2.3.
- **Dwell, not hover.** `dragover` on the list name arms a single 600 ms timer (re-entrant `dragover` events do not stack another); `dragleave` clears a *pending* timer but does not close an already-open popup, so the pointer can travel from the name down into the panel. Cleared on unmount too.
- **AC 7 deviation, deliberate:** the popup closes on drop, on `dragend`, and on dragging back over the board — not on a generic "drag away". Native `dragleave` fires between sibling elements and would make the panel flicker shut mid-approach; `dragend` always fires when a drag ends (including Escape-cancel), so the popup can never outlive a drag.
- **Tests:** backend +14 (source loses / target gains the todo; persists across a reload; id, header, color, status and the full updates log survive; lands last in a populated target and at `order` 0 in an empty one; source order intact; both `active_count`s follow; same-list → 422; archived → 422; unknown source / target / todo → 404; cross-user → 404; a byte-for-byte comparison of the user's JSON file proving three rejected moves wrote nothing). Frontend +3 store, +7 board (dwell opens the popup; a short hover does not; no drag → no popup; drop posts the move and the pill leaves; a rejected move keeps the pill and shows the error; `dragend` closes the popup; pill-on-pill still reorders). Full suites: backend **468**, frontend **496** — no regressions.
- **Not verified in a browser.** jsdom drives `dragstart`/`dragover`/`drop` as plain events; it cannot prove real native HTML5 drag-and-drop feels right (dwell timing, the pointer path from name to panel). Worth one manual pass before this is called Done.

## Dev Notes

**One document, one write.** Both lists live in the same per-user JSON file, so a move is a single read-modify-write of that doc — no cross-file transaction to worry about. Keep it to one `write_doc` call at the end.

**Validate, then mutate.** Follow `reorder_todos`' shape (Story 2.3): every check raises before any field is touched, so a 404/422 can never leave the todo in both lists or in neither. This is what AC 6's "nothing is written" test asserts.

**Ordering.** `order` is a per-list sequence over *active* todos. The moved todo gets `len(active in target)` — i.e. appended. Nothing else needs renumbering: removing a todo from the source leaves a gap in the integer sequence, which is harmless because the board sorts by `order` and never assumes contiguity. Don't add a compaction pass for it.

**Active only.** v1 moves active todos. Archived ones are reachable only from the archive drawer, which has no drag affordance, so a request naming one is a client bug → 422 rather than a silently supported path.

**Native drag, again.** Story 2.3 chose native HTML5 drag events over a dependency; stay with them. The wrinkle: a popup opened *during* a drag must not cancel it, and elements only accept a drop if their `dragover` handler calls `preventDefault()`. If Quasar's menu teleporting breaks the drag in practice, fall back to a plain absolutely-positioned panel inside the page — and record which one you used and why.

**Concurrency.** Like every other mutation in this app, this is an unguarded read-modify-write of the user doc — two concurrent writes can still lose an update. That is the known platform-wide defer (Story 1.8), not something to solve here; don't invent per-request locking in this story.

**Scope.** Drag-and-drop only. No "Move to list" menu in `TodoDetailDialog`, no multi-select, no cross-user sharing.
