# Story 2.6: Close a todo as done (archive)

Status: Ready for Review

## Story

As a user,
I want to close a todo as done,
so that it leaves my active board once it's finished.

## Acceptance Criteria

1. **Close as done → archived.** Given an open todo, when I close it as done (`PATCH /api/context-switch/lists/{list_id}/todos/{todo_id}` with `{ status: "archived" }`), then it is set `status: "archived"` with an `archived_at` timestamp, and it is kept in my file (not deleted). (FR-12)

2. **Removed from the active board.** Given a todo just archived, when the board re-renders, then it no longer appears among the active pills; only active todos are laid out in the grid. (FR-12)

3. **Excluded from active order.** Given an archived todo, when the active order/grid is computed, then it is excluded from the active sequence (it does not occupy a grid slot or an `order` position). (FR-9, FR-12)

4. **Terminal in this story.** Given an archived todo, when viewing the active board, then there is no reopen affordance here — archived todos are reached and managed only via the archive view (Story 2.7). (FR-13)

5. **Unknown ids → 404.** Given the PATCH for ids not in my file, when requested, then the API returns `404`.

### Completion Notes

- **Backend:** `UpdateTodoRequest` gained one optional field, `status: TodoStatus | None`, so the shared `PUT …/todos/{todo_id}` carries archive without a new route (exactly the extension point Story 2.4 designed for — the `req.model_dump(exclude_unset=True)` guard needed no change). `service.update_todo` sets `todo.status` when provided and stamps `archived_at = now` for `"archived"` / clears it (`None`) for `"active"` — the reactivate path exists in the service but ships no UI (door left open per the story).
- **Active/archived split was already centralized** from Story 2.1/2.3: `_active_sorted`/`_board_view` drive every board read (`get_list`, create/update/reorder responses) and `_active_count` powers the list summary, so archiving a todo removes it from the board, the active order, and the count with no extra filtering code. The archive view (2.7) will add the only archived read.
- **No confirm on close** — archiving is soft and recoverable via the archive view, so "Close as done" acts immediately (confirm is reserved for the irreversible delete in 2.7). Invalid `status` values are a schema `Literal` 422; unknown list/todo stay 404.
- **Frontend:** the dialog gained a left-aligned "Close as done" button that emits `close-as-done` and closes; `BoardPage.onCloseAsDone` calls `store.updateTodo(..., { status: "archived" })`. The store's `updateTodo` already replaces the local todo with the response, and `activeTodos` already filters `status === "active"`, so the archived pill drops off the board and — because the board tracks the open todo by id — the now-absent `openTodoItem` unmounts the dialog. `TodoPatch` gained `status?: TodoStatus`.
- **Tests:** backend +10 (archive sets status + `archived_at`; record kept on disk; absent from board; excluded from `active_count`; reactivate clears `archived_at`; persists across reload; other fields untouched; invalid status → 422; unknown → 404; cross-user 404). Frontend +3 (store drops archived from `activeTodos`; dialog emits `close-as-done` + closes; board removes the pill on close). Full suites: backend **439**, frontend **462** — no regressions.

## Dev Notes

**Archive = soft, via the shared todo-PATCH.** Archiving is just `status: "archived"` on the existing `PATCH …/todos/{todo_id}` (Story 2.4) — not a separate endpoint and not a delete. The record stays in the file for the archive view. [Source: user decision — "Archived / hidden (recoverable via archive view)"]

**Terminal by design.** There is no "reopen" in v1 (user chose view + delete only for the archive). If reopen is wanted later, it is a one-line addition (`status` back to `active`, clear `archived_at`) — leave the door open in the service but ship no UI for it.

**Active vs archived is the core read split.** Every "board" read is active-only; the archive view (2.7) is the only archived read. Centralize the filter in the service so both stories share it.
