# Story 2.4: Open a todo and edit it

Status: Ready for Review

## Story

As a user,
I want to click a todo to open it and edit its header and body,
so that I can fix or expand what I wrote.

## Acceptance Criteria

1. **Click opens detail.** Given a pill on the board, when I click it, then a detail view opens showing the todo's header, body, color, and its updates log (log is populated in Story 2.5; here it may be empty). (FR-10)

2. **Edit header/body.** Given the detail view, when I edit the header and/or body and save, then `PATCH /api/context-switch/lists/{list_id}/todos/{todo_id}` with the changed fields updates them in place, bumps `updated_at`, and the pill on the board reflects the change. (FR-10)

3. **Change color here too.** Given the detail view, when I change the color, then it persists via the same PATCH and the pill re-renders in the new color. (FR-7)

4. **Header still required.** Given an edit that blanks the header, when saved, then it is rejected (client-disabled + `422` backstop); body may be blank.

5. **Unknown ids → 404.** Given a PATCH for a `list_id`/`todo_id` not in my file, when requested, then the API returns `404`.

### Completion Notes

- **Backend:** `service.update_todo` applies only the fields it was given, validates a provided header is non-blank (trimmed), bumps `updated_at`, and raises `FileNotFoundError` for an absent list *or* todo (new `_find_todo` helper mirroring `_find_list`). Color validity is the schema's `pattern` again, so a bad hex is a 422 with no service branch.
- **Verb — PUT, not PATCH (same deviation as Stories 1.4 / 2.2):** `useApi` exposes only `get/post/put/del`, so the endpoint is `PUT /lists/{list_id}/todos/{todo_id}`. It stays the single mutation surface for a todo's fields; `status` slots in for Story 2.6 by adding one optional schema field.
- **The empty-body guard is written as `req.model_dump(exclude_unset=True)`** rather than an explicit `x is None and y is None …` chain (which is what `update_list` uses). That is deliberate: when Story 2.6 adds `status` to `UpdateTodoRequest`, the router needs no change at all.
- **`TodoPill` stays dumb** — it gained only an `open` emit (click plus Enter, with `role="button"`/`tabindex`); the board decides what opening means. The pill sits inside the Story 2.3 drag slot, and native HTML5 DnD does not fire a click after a real drag, so the two interactions coexist.
- **`TodoDetailDialog`** seeds from the todo on open *and* when the todo id changes, and computes a **diff patch** — it emits only the fields that actually changed. That is why Save is disabled both on a blank header and when nothing has been edited: an empty patch would otherwise be a pointless 422 from the new guard. The updates-log section is rendered now (empty-state today, entries when `todo.updates` is non-empty), so Story 2.5 has a place to write into and AC 1 is satisfied.
- **Board tracks the open todo by id, not by value** (`openTodoItem` is a computed lookup into `store.activeTodos`), so after a save the dialog and pill both read the store's fresh copy instead of a stale snapshot.
- **Tests:** backend +12 (partial update touches only provided fields; `updated_at` bumps while `created_at` holds; persists across a reload; header trimmed; blank header → 422 with the old value intact; blank body allowed; bad color → 422; empty body → 422; `order`/`status` untouched; unknown todo → 404; unknown list → 404; cross-user 404). Frontend +16 across `TodoDetailDialog` (10), `TodoPill`, the store, and the board. Full suites: backend **420**, frontend **452** — no regressions.
- **Pre-existing, untouched:** `npx vue-tsc --noEmit` reports two `QNotifyCreateOptions` errors in `src/pages/SettingsPage.vue`, and `npm run lint` still fails for want of an ESLint v9 `eslint.config.js`. Neither is related to this story.

## Dev Notes

**One shared todo-PATCH endpoint.** `PATCH …/todos/{todo_id}` is the single mutation surface for a todo's fields: header/body/color here, `status` (archive) in Story 2.6. Keep the request schema all-optional so each story adds a field without a new route. Only fields present in the body are applied.

**Detail dialog grows across stories.** Build `TodoDetailDialog` here with room for the updates log (2.5) and the "close as done" control (2.6) — don't over-build those now, but structure the component so they drop in cleanly.

**Coding standards.** `defineProps<{}>()`/`defineEmits<{}>()`, no `any` without justification; HTTP via `useApi`; store `loading`/`error`. [Source: CLAUDE.md#Conventions]
