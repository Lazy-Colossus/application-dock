# Story 3.1: Switch lists from the board

Status: Ready for Review

## Story

As a user,
I want little arrows either side of the list name on the board,
so that I can flip between my lists without going back to the picker.

## Acceptance Criteria

1. **Arrows frame the list name.** Given a board and more than one list, when the header renders, then a left chevron and a right chevron sit either side of the list name, each with an accessible label naming the list it would take me to. (FR-14)

2. **Next / previous walks picker order.** Given I am on a board, when I press the right (or left) arrow, then I navigate to the next (or previous) list in the same order `GET /api/context-switch/lists` returns (the order the picker shows), and the URL becomes `/context-switch/lists/:nextId`. (FR-14, FR-4)

3. **Wrap-around.** Given I am on the last list, when I press the right arrow, then I land on the first list; from the first list the left arrow lands on the last. The arrows are never a dead end and are never disabled. (FR-14)

4. **Board content follows.** Given I switch lists, when the new board renders, then its name, todos, and grid are the new list's — the previous list's pills never linger — and the pager resets to page 1.

5. **Hidden with nothing to switch to.** Given I have one list (or the list sequence has not loaded), when the header renders, then no arrows are shown.

6. **Direct entry still works.** Given I open a board by URL (deep link, refresh, or back/forward), when it loads, then the arrows are correct for that list's position in the sequence, without a visit to the picker first.

### Completion Notes

- **The route-param trap was real.** `onMounted` is gone; the mount fetch and the switch fetch are the same `watch(listId, …, { immediate: true })`, which also resets `page` to 1 and closes `addOpen` / `detailOpen` / `openTodoId` / `archiveOpen`. Two tests pin this: one asserts the new list's pills and name replace the old ones after only the route param changes, another asserts an open detail dialog does not survive the switch.
- **Neighbours wrap in one helper.** `neighbour(step)` walks `store.lists` with `(index + step + count) % count` and returns `null` when there are fewer than two lists or the current id is not in the sequence (which is also what hides the arrows before the sequence loads). `prevList` / `nextList` are computeds over it, so the chevrons carry the destination's name in their `aria-label` for free.
- **The board fetches the sequence itself** when `store.lists` is empty — a deep-linked or refreshed board never passes through the picker. Guarded, so arriving from the picker does not refetch.
- **Test-harness change worth knowing:** `BoardPage.spec.ts` previously mocked `vue-router` with a frozen route object and stubbed `api.get` by call order. Switching lists needs a *reactive* route, and the board now reads two GET endpoints, so the mock route is a `reactive({ params })` the tests mutate, and `api.get` is dispatched by URL (`setBoard(list)` / `summaries` / `archivedTodos` / `boardError`) instead of by `mockResolvedValueOnce` sequencing. All pre-existing tests kept their assertions.
- **Tests:** +9 in `BoardPage.spec.ts` (sequence fetched on mount; arrows shown with several lists and hidden with one; next/prev push the right path; wrap in both directions; route-param change reloads the board; pager resets to page 1; open dialog closed). Full suites: frontend **496**, backend **468** — no regressions.

## Dev Notes

**No backend work.** Everything needed is already served by `GET /api/context-switch/lists` (Story 1.3) — this story is `BoardPage.vue` plus its spec.

**Order = picker order.** The sequence is `store.lists` exactly as the API returns it. Do not sort here; if the picker's order ever changes, the arrows follow it for free.

**The route-param trap.** `/context-switch/lists/:listId` → `/context-switch/lists/:otherId` does **not** remount `BoardPage`; `onMounted` will not fire again. Without the `watch(listId)` the header name changes while the old list's todos stay on screen — this is AC 4's real failure mode and the thing most worth a test.

**Stale UI on switch.** `openTodoId` points at a todo of the *old* list; leaving it set while the new list loads can flash a detail dialog for a todo that is no longer on the board. Clear the dialog state in the same watcher.

**Grid comes from the list.** `grid` is already `store.currentList?.grid ?? DEFAULT_GRID`, so a switch picks up the destination list's saved grid with no extra work — the `totalPages` watcher already pulls an over-range page back, but reset `page` explicitly so switching always starts at the first page rather than at whatever page number happened to be valid.

**Scope.** Navigation only. Moving todos between lists is Story 3.2; nothing about the picker home changes.
