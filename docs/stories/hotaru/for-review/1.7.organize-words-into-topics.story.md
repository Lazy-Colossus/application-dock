# Story 1.7: Organize words into Topics

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to group words into my own named topics and filter the library by them,
so that I can practise themes beyond the textbook's lesson order.

## Acceptance Criteria

1. **Create a topic; assign/unassign any word.** Given the library, when I create a named Topic and add or remove words, then the Topic and its membership persist in a shared `topics.json` and are visible to both users; a word may belong to **many** topics, and any word the user can see (seed, shared, or their own private) may be assigned (FR-6).

2. **Membership is stored on the topic and survives.** Given `topics.json` holds `{id, name, word_ids[]}`, when I assign a word, then its id is added to that topic's `word_ids` (idempotent — assigning twice is a no-op); when I unassign, then its id is removed (idempotent). Writes go through the repository via `_storage.atomic_write_json`.

3. **Filter the library by a Topic — privacy preserved.** Given the Library, when I filter by a Topic, then I see exactly that topic's words **that I can see** — a private word assigned by its owner never appears in the other user's topic view (FR-7 still holds because the topic view is the intersection of `word_ids` with the caller's visible master list). Given `GET /api/hotaru/words?topic={id}&user=<id>`, then it returns that intersection.

4. **API contract.** `GET /api/hotaru/topics` → `Topic[]`; `POST /api/hotaru/topics` `{name}` → the created `Topic` (201, empty `word_ids`); `POST /api/hotaru/topics/{id}/words/{word_id}` assigns (→ the updated `Topic`); `DELETE /api/hotaru/topics/{id}/words/{word_id}` unassigns (→ 204). A blank topic name → `422` + `{detail}`; an unknown topic id → `404`; assigning a `word_id` the caller can't see → `404`; an unknown `user` on the word-scoped calls → `404`. Direct serialization, snake_case, `{detail}` errors.

5. **Conventions + no regressions.** New backend layer follows the strict 3 layers — a new `topic_repo.py` is the only filesystem code for topics (never mutates the seed), the service raises stdlib errors, the router maps them to `HTTPException`. Frontend HTTP via `useApi`; the store exposes `loading`/`error` and sets `loading` in `try/finally`. `pytest` + `npm test` green; `black`/`ruff` + Prettier clean.

## Dev Notes

**Data model + endpoints are fixed by the architecture.** `topics.json` holds shared topics `{id, name, word_ids[]}`; a new `topic_repo.py` owns that file (repos are the ONLY filesystem code); topics logic lives in `hotaru_vocab_service`. [Source: architecture.md#Data Architecture "topics.json — shared topics {id, name, word_ids[]}"; #Source tree — `topic_repo.py`, `hotaru_vocab_service.py ← … topics`; #API `GET /topics · POST /topics · GET /words?topic=`]

**Deviation from the architecture's `PATCH /words/{id}/topics` — and why.** The shared `useApi` boundary exposes only `get/post/put/del` (no `patch`) — the same constraint that made Story 1.8 use `PUT` instead of `PATCH`. Rather than add a verb, membership uses **surgical, idempotent** endpoints `POST /topics/{id}/words/{word_id}` (assign) and `DELETE /topics/{id}/words/{word_id}` (unassign). This is *better* than a whole-`word_ids`-array replace: two users toggling different words in the same shared topic won't clobber each other's change (a full-array `PUT` would — and shared-file writes are last-write-wins, accepted but worth minimizing). [Source: frontend/src/composables/useApi.ts; docs/stories/hotaru/for-review/1.8… (PUT-not-PATCH precedent)]

**Privacy is preserved for free by intersection.** A topic is shared and stores raw `word_ids`. If Dani assigns her *private* word to a topic, that id sits in shared `topics.json`, but the topic **view** is `list_words(user).filter(id ∈ word_ids)` — Jake's `list_words` never contains Dani's private word, so it can't appear for him. Only a resolvable word id (a bare string he can't look up) is technically in the shared file; no private content leaks. Assign therefore checks the word is in the *caller's* visible set (so you can't inject arbitrary ids), and the filter does the rest. [Source: epics-hotaru.md#Story 1.7 "private words still follow FR-7 visibility"; architecture.md#Authentication & Security — path-as-privacy]
