# Story 2.5: Grade a card and update familiarity

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to record how I did on each card so the system learns what to show me next,
so that shaky words come back sooner and mastered ones rest.

## Acceptance Criteria

1. **Self-grade on reveal.** Given the drill in self-grade mode, when I reveal a card, then I choose one of three bare-label buttons — **Incorrect / Close / Correct** (no subtext) — and the card advances (FR-14, UX-DR5). The grade buttons replace the plain "Next" from Story 2.3.

2. **Optimistic advance + background batch sync.** Given I grade a card, when I tap a grade, then the UI advances **immediately** (never blocks on the network); grades accumulate and sync in a **batch** to `POST /api/hotaru/practice/grades?user=` in the background; the server applies `srs.next_review` per grade and writes `users/{user}/progress.json` (FR-15, NFR-6).

3. **Grading moves familiarity per the SRS rules.** Given a batch of grades, when the server applies them, then each word's `{tier, points, last_reviewed_at}` updates via the pure `srs.next_review` (Correct → +point / advance at threshold; Close → holds; Incorrect → drop a tier; `last_reviewed_at = now`), so the **next** session's queue re-orders weakest/most-due first. (Within a session the queue order is fixed — the calm/batch contract.)

4. **User-switch is a hard boundary.** Given I switch user mid-session, when the switch happens, then any pending grades are flushed **attributed to the prior user**, and the in-progress queue is discarded (the next user starts fresh) — one user's grades are never written to another's progress.

5. **Conventions + no regressions.** `POST /practice/grades` body is a batch array of `{word_id, grade}`; the server uses the pure `srs` with an **injected `now`** (in the practice service, not `srs.py`); the response carries no due-debt. HTTP via `useApi`; grade state lives in `useDrill`; the store exposes `loading`/`error`. `pytest` + `npm test` green; `black`/`ruff` + Prettier clean.

## Dev Notes

**This closes the SRS loop.** Story 2.1 built the engine (`srs.next_review`) and `progress_repo`; Story 2.3 built the queue that *orders by* stored familiarity. Neither moves familiarity — this story does: grade → `srs.next_review` → `progress.json`, so the **next** queue surfaces weak words first. That's the whole point of the "adjust order by score" behaviour. [Source: epics-hotaru.md#Story 2.5; architecture.md#Drill data flow]

**Scope carve-out — self-grade only; typed mode is deferred.** The epic's AC also describes a **typed mode** ("type kana, exact-match → Correct, else reveal + self-grade"), but that mode is **EN→JP only**, and EN→JP is the **direction toggle from Story 2.4**, which isn't built. So this story ships the **self-grade** path (the 3 buttons) plus the entire persistence/sync/user-switch loop. Typed mode is carved out and should be built with (or after) Story 2.4's EN→JP direction. Note this explicitly in the completion notes; don't attempt typed mode without EN→JP. [Source: epics-hotaru.md#Story 2.5 (typed = EN→JP only) + #Story 2.4]

**Optimistic = non-blocking advance, not a client familiarity cache (yet).** "Optimistic local update" here means the card advances the instant you grade — the UI never waits on `POST /grades`. There is no on-screen familiarity to mutate yet (the `FamiliarityIcon` is Story 2.6, and the drill card doesn't show a tier). So keep it simple: buffer grades in `useDrill`, advance immediately, and flush the batch in the background. When 2.6 lands, the same buffered grades can also nudge a local familiarity view. [Source: architecture.md#Optimistic grading; epics-hotaru.md#Story 2.6]

**Batch, background, never-blocking.** Grades submit as a batch array `[{word_id, grade}]` to `POST /practice/grades`. Flush the buffer when the session ends and on unmount (and on user-switch). `submitGrades` must NOT set the store's `loading` (a slow/failed sync can't freeze the drill) — route failures into `error` only. The card flip stays instant. [Source: architecture.md#Drill feel "batch-fetch once, grade optimistically, sync in background"; NFR-6]

**`now` injection stays the purity boundary.** `apply_grades` owns the clock (`datetime.now(UTC)` default, overridable in tests); it calls the pure `srs.next_review(entry, grade, now)`. Do NOT add a clock to `srs.py`. [Source: architecture.md#SRS service purity; Story 2.1]

**User-switch = hard boundary.** Flush pending grades attributed to the *prior* user, then discard the queue. Never replay one user's grades after a switch. Capture the drill's user at mount (`drillUser`) and always submit to it; a `watch` on `activeUserId` handles a mid-session change. [Source: architecture.md#User switch = hard session boundary]
