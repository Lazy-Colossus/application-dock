# Story 1.6: Mark a word shared or private

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to choose whether a word I add is shared with my partner or kept private, and to see at a glance which of my words are private,
so that I control what we co-build and can trust the privacy boundary.

## Acceptance Criteria

1. **Private words carry a visible mark; shared words don't.** Given the library list, when a word's `visibility` is `private`, then its row shows a 🔒 lock marker in the amber-private accent (`--hotaru-amber-private`) with an accessible label; when `visibility` is `shared`, then no marker is shown (shared is the implicit default). The marker appears wherever a private word is listed — both the Custom → Private subsection and any textbook lesson a private word was filed into. [UX-DR8; DESIGN.md — "Shared is implicit default (no badge). Private … show a 🔒 lock only."]

2. **Shared is communal; private is per-user (already enforced — locked down here by test).** Given a **shared** word, then it is present in the master list for both users (`vocab_shared.json`). Given a **private** word, then it is stored under `users/{owner}/words_private.json` and appears in the master list **only** for its owner (FR-7). This boundary is a path boundary in `vocab_repo`/`hotaru_vocab_service` (the service reads only the *active* user's private file), not a filter the caller can spoof.

3. **The other user's payload excludes my private words — proven by test.** Given `GET /api/hotaru/words?user=<other>`, when it loads, then my private words are **absent from the response payload** (not merely hidden client-side); private words never leak across users through the shared list, lesson filters, or Topic filters. Enforced at the repo path and verified by a dedicated backend test. [FR-7; architecture.md — path-as-privacy]

4. **Conventions + no regressions.** No new backend behavior is introduced unless a gap is found (the shared/private storage split was built in Story 1.5 and the visibility-move in Story 1.8); any change still routes writes through `_storage.atomic_write_json` and never mutates the seed. Frontend HTTP stays behind `useApi`; the store still exposes `loading`/`error`. `pytest` + `npm test` green; `black`/`ruff` + Prettier clean.

## Dev Notes

**Most of this story already works — 1.6 makes it *visible* and *proven*.** The shared/private split (storage chosen by `visibility`, private under `users/{user}/words_private.json`) shipped in Story 1.5's `create_word`, and Story 1.8's `update_word` moves a word between the shared and the owner's private file when visibility changes. `list_words(user)` already reads **only** the active user's private file, so the payload boundary exists. This story adds the **UI marker** users asked for and a **dedicated isolation test** so the FR-7 boundary can't silently regress. Do not re-plumb the backend. [Source: docs/stories/hotaru/done/1.5.add-word-manually.story.md; docs/stories/hotaru/for-review/1.8.edit-delete-custom-word.story.md]

**Privacy is a path boundary, not a filter.** `hotaru_vocab_service.list_words(lesson, user)` assembles `read_seed() + read_shared()` and appends `read_private(user)` **only for the active user**. Another user's private file is never read into the response, so there is nothing to leak — this is why AC-3 asserts on the *response payload* (ids returned by `GET /words?user=jake`), which is the real contract, rather than on a client-side filter. [Source: architecture.md#Authentication & Security — path-as-privacy; backend/app/services/hotaru_vocab_service.py]

**The private accent already exists.** `--hotaru-amber-private: #e0b27a` is defined in `apps/hotaru/css/hotaru.sass:27` and is already used for the Private toggle in `AddWordPage.vue`. Reuse it for the marker so the add-form toggle and the library marker read as the same concept. DESIGN pairs `lock` (Material icon) with this amber for private scope. [Source: DESIGN.md#Palette — "amber-private … 🔒 lock on private"; UX-DR8]

**Familiarity is NOT in this story.** UX-DR8 describes the WordRow as showing "familiarity + shared/private mark", but the familiarity tier/icon is FR-21 → **Epic 2**. Story 1.6 adds only the shared/private mark. Do not build a FamiliarityIcon here. [Source: epics-hotaru.md#FR Coverage Map — FR-21: Epic 2]

**Editable code to read before editing:**
- `components/WordRow.vue` — current row: primary JP (kanji||reading) / reading / optional romaji, meaning, a romaji toggle button, and (when `editable`) edit/delete buttons (added in 1.8). **Add** the private marker; leave the romaji toggle and edit/delete affordances intact. The marker is a plain status glyph — not a button, no emit.
- `components/WordRow.spec.ts` — has romaji-toggle and editable/edit/delete specs (uses `global: { stubs: { 'q-icon': {...} } }` for the icon buttons — reuse that stub for the new marker). **Add** private-mark specs.
- `services/hotaru_vocab_service.py` / `repositories/vocab_repo.py` — the read path (`list_words`, `read_shared`, `read_private`). **Read only**; change only if a leak is found.

**Placement / a11y.** Put the marker after the meaning column, before the romaji toggle, so the row reads: JP · meaning · 🔒 · [A] · (edit/delete). It's decorative-but-informative: give it an `aria-label`/`title="Private"` so it isn't colour-only (consistent with the project's "never colour alone" rule). In the Custom → Private subsection every row is private, so the marker repeats there — that's acceptable and consistent (private always = lock); its real payoff is distinguishing a private word filed into a shared textbook lesson. [Source: DESIGN.md#Word row]

**Scope (YAGNI).** Marker + isolation tests only. No shared badge, no familiarity, no per-row visibility *toggle* in the library (visibility is set in the add/edit form — Stories 1.5/1.8), no drill/detail-header marker (Epic 2/3).

**Coding standards.** Frontend `<script setup lang="ts">`, `defineProps<{}>()`, no `any`, scoped `.hotaru-app`/`word-row` styles, co-located `*.spec.ts`. Backend tests in `backend/tests/` as `test_*.py`; the autouse `conftest.py` fixture wipes `DATA_DIR/hotaru` between tests, so no manual cleanup. [Source: docs/architecture/coding-standards.md; CLAUDE.md]
