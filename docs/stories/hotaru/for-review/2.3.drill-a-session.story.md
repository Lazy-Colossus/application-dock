# Story 2.3: Drill a session

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to flip through a chosen scope's words one at a time,
so that I can review efficiently in a calm, bounded session.

## Acceptance Criteria

1. **Queue endpoint — weakest/due first, capped, no debt.** Given a chosen scope, when I start (`GET /api/hotaru/practice/queue?scope=&user=&direction=`), then the service returns an **ordered** queue of the most-worth-reviewing words (weakest first, then most-due), filtered to words whose `drill_caps` include the chosen `direction` (default `r2m`), **soft-capped to the session size (default 20)**, and the response schema carries **no** due-counts / overdue / `next_review_at` (FR-12, FR-19, FR-18, NFR-5).

2. **One card at a time: prompt → reveal.** Given the drill, when a card shows, then exactly **one** word is presented — the prompt side first (for the default JP→EN direction, the Japanese headword), and on reveal the reading + meaning appear. The practiced **Japanese glows cyan** (the neon drill treatment; the epic's "lamp-yellow" is superseded by the Neon Yūgure pivot — kanji cyan, kana lamp-yellow per DESIGN), on the glass drill card with fireflies drifting behind (dimmed over the card; static under `prefers-reduced-motion`) (UX-DR2/4).

3. **Advance, and a clean end.** Given a revealed card, when I advance, then the next card shows; when the queue is exhausted (or I stop), then the session ends cleanly — a simple "session complete" state with a way back to the library/home — **no penalty, no backlog wall, no due-count** (FR-18). An empty scope (0 eligible words) shows a graceful "nothing to practise here" state rather than an error.

4. **Launch from the picker.** Given the pre-session overview (Story 2.2), when I tap **"Let's practice ✦"**, then I land in the drill for the selected scope (this wires up the CTA that Story 2.2 deferred).

5. **Conventions + no regressions.** The queue is built in `hotaru_practice_service` from `srs` due-state (with an **injected `now`** — `srs.py` stays pure); the response model physically omits debt; HTTP via `useApi`; the practice store exposes `loading`/`error`. **No grading/persistence yet** (Story 2.5), **no direction toggle UI yet** (Story 2.4 — backend supports the `direction` param), **no familiarity icon on the card** (Story 2.6), **no notes** (Epic 3), **no summary page** (Story 2.7 — the clean end is a minimal inline state). `pytest` + `npm test` green; `black`/`ruff` + Prettier clean.

## Dev Notes

**This is the drill's spine — the queue API + the flip flow.** Grading and familiarity *movement* are Story 2.5; the direction *toggle* is 2.4; the familiarity *icon* on the card is 2.6; the *summary* is 2.7; *notes* on the card are Epic 3. Keep 2.3 to: fetch an ordered queue, flip prompt→reveal→next, end cleanly. Advancing here is a plain "Next" (no grade is recorded yet). [Source: epics-hotaru.md#Story 2.3; architecture.md#Requirements Overview F3/F4]

**Queue-not-debt is the governing contract (third endpoint under it).** `practice/queue` response models MUST NOT contain due-counts, overdue, or `next_review_at`. `QueueItem` holds only `word`. A test asserts the exact JSON key set, exactly as `test_overview_response_carries_no_due_debt` does for the overview. "Due" is used only to *order* the queue server-side; it never leaves the API. [Source: architecture.md#Queue-not-debt; #API `GET /practice/queue … NO due-counts/overdue`; NFR-5]

**`now` injection — the purity boundary.** Ordering needs "is this due?", which needs a clock. Put the clock in **`hotaru_practice_service.build_queue`** (default `now=datetime.now(UTC)`, overridable in tests), and call the pure `srs.is_due(entry, now)` / `srs.due_at(entry)`. Do **not** add a clock to `srs.py` — it stays pure/table-tested. [Source: architecture.md#SRS service purity; Story 2.1 `srs.py`]

**Ordering = "most-worth-reviewing", not "only due".** Take *all* scope words, order weakest→strongest (tier asc) then due-first, and take the top `limit` (default 20, tunable). This is deliberately NOT "only the due ones" — surfacing a debt list is exactly what the calm guardrail forbids. New words (tier 0, never reviewed) naturally lead. [Source: epics-hotaru.md#Story 2.3 "weakest/due first"; architecture.md#Drill data flow "soft-capped to a calm session size — default 20"]

**`drill_caps` gates the queue; direction defaults to `r2m`.** A direction is the `drill_cap` it needs: `r2m` (JP→EN, given reading/Japanese → recall meaning), `m2r` (EN→JP, given meaning → produce reading), `k2r` (given kanji → reading). `r2m`+`m2r` are the seed floor (every word), so they exclude nothing; `k2r` excludes kana-only words. Story 2.3 defaults to `r2m` and renders JP→EN; the backend already accepts `direction` so Story 2.4 is mostly the frontend toggle. The service **consumes** caps, never derives them. [Source: architecture.md#`drill_caps`; epics-hotaru.md#Story 2.4]

**Card colours (neon).** The drill card is the focal glass panel (DESIGN.md `drill-card`): dual cyan+violet ambient glow, the Japanese headword the brightest thing. Per the word-row/DESIGN rules locked this session: **kanji glow cyan `#38f0e6`, kana glow lamp-yellow `#ffd24a`** (the reading line is kana → lamp-yellow). The epic text says "lamp-yellow" for the whole word — that predates the neon pivot; follow DESIGN.md (cyan headword / yellow kana). [Source: DESIGN.md#Components drill-card + word-row; .working/neon-drill-and-picker.html; mockups/drill-and-picker.html]

**Frontend architecture (from the design).** The `useHotaruPracticeStore` owns fetching (`queue`), `useDrill` owns the in-session state machine (prompt→reveal→advance), `Flashcard` is presentational, `DrillPage` composes them. Story 2.5 will extend `useDrill` with optimistic grading + background batch sync — so keep its state shape clean and grade-ready (a `next()` today becomes "grade then next" later). [Source: architecture.md#Frontend F3 map; #Drill feel "batch-fetch once, grade optimistically, sync in background"]

**Scope passing.** The picker selects a `scope` string (`lesson:{id}` / `topic:{id}`); pass it to the drill via the route query (`/hotaru/drill?scope=…`) so the drill is deep-linkable and the picker stays the single place scopes are chosen. DrillPage reads `route.query.scope`.

**Scope (YAGNI).** Queue + flip + clean end + launch CTA only. No grade buttons, no typed mode, no direction toggle, no progress persistence, no familiarity icon, no notes, no summary screen. [Source: epics-hotaru.md#Epic 2 story split]

**Coding standards.** Backend type hints + `pathlib` + f-strings, stdlib errors in service (HTTPException only in router). Frontend `<script setup lang="ts">`, `defineProps<{}>()`, no `any`, `interface` shapes, scoped `.hotaru-app` theme, co-located `*.spec.ts`. Timezone-aware UTC datetimes. [Source: docs/architecture/coding-standards.md; CLAUDE.md]
