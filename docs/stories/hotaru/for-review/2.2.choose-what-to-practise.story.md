# Story 2.2: Choose what to practise

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to pick a lesson or topic and see how I'm doing on it before I start,
so that I can decide where to spend a session.

## Acceptance Criteria

1. **Pick exactly one scope (a Lesson or a Topic).** Given the practice picker, when I choose a scope — a single Lesson **or** a single Topic — then the app records that scope for the session; word-drill is the only activity in v1, so no activity choice is required (FR-10).

2. **Pre-session overview, calm.** Given a chosen scope, when the overview loads (`GET /api/hotaru/practice/overview?scope=&user=`), then it returns the **word count** and the **active user's familiarity distribution** (counts across the 5 tiers), and the response schema contains **no** due-counts / overdue / `next_review_at` (FR-11, NFR-5).

3. **Scope encoding + errors.** Given `scope` is `lesson:{lesson}` or `topic:{topicId}`, when the overview is requested, then words are the scope's slice of the active user's visible master list (private words counted only for their owner, per FR-7); a malformed scope (bad prefix) → `422` + `{detail}`; an unknown `user` → `404`; a scope that matches no words → `200` with `word_count: 0` and an all-zero distribution.

4. **Picker UI reaches the overview.** Given the Hotaru home "Practice" button, when I tap it, then I land on the practice picker; when I select a Lesson or Topic, then its overview (count + per-tier familiarity) renders. Familiarity is shown as label + count per tier for now (the polished icon/colour ramp is Story 2.6). The session-launch CTA ("Let's practice") is added in Story 2.3 when the drill exists.

5. **Conventions + no regressions.** New backend logic follows the 3 layers — `hotaru_practice_service` computes the overview from `hotaru_vocab_service.list_words` + `progress_repo`; the router validates `user` and maps stdlib errors to `HTTPException`; the response model physically omits due-debt. Frontend HTTP via `useApi`; the new `useHotaruPracticeStore` exposes `loading`/`error`. `pytest` + `npm test` green; `black`/`ruff` + Prettier clean.

## Dev Notes

**This story is the first slice of F3 (Practice) and the first practice endpoint.** It delivers the picker + the read-only pre-session overview. The queue/drill (2.3), direction (2.4), grading+sync (2.5), familiarity icon (2.6), and summary (2.7) come next. `srs.py` and `progress_repo` from Story 2.1 are the inputs — this story only *reads* progress, never writes it. [Source: architecture.md#Requirements Overview F3/F4; #Source tree — `hotaru_practice_service.py ← scope→queue, overview, grade application`]

**Queue-not-debt is a hard contract, and this is the first endpoint it governs.** `practice/overview` (and later `practice/queue`) response models MUST NOT contain due-counts, overdue, or `next_review_at`. `PracticeOverview` physically has only `{scope, word_count, familiarity}`. A test asserts the exact JSON key set so a future field can't silently leak debt. [Source: architecture.md#Queue-not-debt "response models MUST NOT contain due-counts…"; NFR-5]

**Familiarity distribution = per-tier counts, computed from `progress.json`.** For each scoped word, tier is `progress[word_id].tier` or `0` (New) when the user has never reviewed it. Read the whole progress map once (`progress_repo.read_progress(user)`) rather than per-word `get_entry`. The tier→label/colour/icon mapping is a **frontend** concern; 2.2 shows plain labels + counts, and Story 2.6 adds the `FamiliarityIcon` (icon + colour + label). Do NOT build `FamiliarityIcon` here. [Source: architecture.md "tier→colour/icon mapping is a frontend concern"; epics-hotaru.md#Story 2.6 / #UX-DR3]

**Scope encoding.** `scope = "lesson:{lesson}"` or `"topic:{topicId}"` — a single string expresses "exactly one scope". The service maps it onto the existing `list_words(lesson=…)` / `list_words(topic=…)` filters (built in Epic 1), so privacy (FR-7) and the topic-intersection behavior come for free. A `lesson` scope matches `w.lesson == value` across all sources (fine for the single-textbook v1). Exclude the empty lesson (`""`, used by un-filed custom words) from the picker's Lesson options. [Source: architecture.md#API `GET /practice/overview?scope=&user=`; epics-hotaru.md#Story 2.2]

**Editable/related code to read before editing:**
- `services/hotaru_vocab_service.py` — `list_words(lesson, user, topic)` is the scope source. **Read only.** Import it from the new practice service.
- `repositories/progress_repo.py` — `read_progress(user)` gives `{word_id: ProgressEntry}`. **Read only.**
- `routers/hotaru.py` — has `VALID_USER_IDS` + the user-validation / stdlib→HTTPException idiom. **Add** the `GET /practice/overview` route; reuse that idiom.
- `schemas/hotaru.py` — has `ProgressEntry`, `Grade`, `Word`, `Topic`. **Add** `PracticeOverview`.
- `pages/HotaruHomePage.vue` — the Practice button exists with `onPractice()` stubbed `TODO(Story 2.2)`. **Wire** it to `/hotaru/practice`.
- `stores/useHotaruLibraryStore.ts` — reuse `loadWords`/`loadTopics` + `lessons`/`topics` for the picker's scope options (don't duplicate that data in the practice store).
- `router/routes.ts` — lazy routes; add `hotaru/practice`.

**Store split.** Practice state lives in a **new** `useHotaruPracticeStore` (architecture lists it alongside `useHotaruUserStore`/`useHotaruLibraryStore`); it will also hold the queue + optimistic grades in 2.3/2.5. Keep library/topic data in the library store and read it from the page — don't copy words into the practice store. [Source: architecture.md#Source tree stores; #Component/Feature map F3]

**Scope (YAGNI).** Picker + overview only. No queue, no drill card, no direction toggle, no grading, no launch CTA, no `FamiliarityIcon`, no session-size logic. Activity is implicitly word-drill (grammar/kanji are Phase III). [Source: epics-hotaru.md#Story 2.2; #Epic 2 story split]

**Coding standards.** Backend type hints + `pathlib` + f-strings, stdlib errors in service (HTTPException only in the router). Frontend `<script setup lang="ts">`, `defineProps/Emits<{}>()`, no `any`, `interface` for shapes, scoped `.hotaru-app` theme, co-located `*.spec.ts`. `datetime` isn't needed here (no writes). [Source: docs/architecture/coding-standards.md; CLAUDE.md]
