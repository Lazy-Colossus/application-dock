# Story 1.8: Edit or delete a custom word

Status: Ready for Review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to edit or delete a word I added,
so that I can fix mistakes and remove words I no longer want.

## Acceptance Criteria

1. **Custom words are editable/deletable; seed words are not.** Given a word whose `source` is a user id (a custom word, living in a writable file), when I view it, then delete and edit affordances are available. Given a seeded (textbook) word, then no edit/delete affordance is shown, and any API attempt to mutate it is rejected (403).

2. **Delete a custom word.** Given `DELETE /api/hotaru/words/{id}?user=<id>`, when it targets a custom word the user can see, then the word is removed from its writable file (`vocab_shared.json` for shared, or the owner's `users/{user}/words_private.json` for private) and disappears from the library; response is `204`.

3. **Edit a custom word.** Given `PUT /api/hotaru/words/{id}?user=<id>` with the editable fields, when saved, then `reading`, `meaning`, `kanji`, `romaji`, `pos`, `lesson`, and `visibility` update in place; `id` and `source` are unchanged; `drill_caps` is recomputed from the new `kanji` (`r2m`+`m2r`; `k2r` iff kanji present); `kanji ""→null`. The updated `Word` is returned.

4. **Changing visibility moves the word between files.** Given I edit a custom word and change its `visibility`, when saved, then the word is removed from its old file and written to the new one (shared ↔ the owner's private file), so it appears under the correct Custom subsection.

5. **Ownership & privacy.** Given a **private** word, when a user who is not its owner targets it (delete or edit), then it is not found for them (they can't see it) → `404`. Given a **shared** custom word, either user may edit/delete it. Given an unknown `user`, then `404`. Given a blank `reading`/`meaning` on edit, then `422` + `{detail}`.

6. **Conventions + no regressions.** Writes go only through the repository layer via `_storage.atomic_write_json`; the seed file is never mutated; HTTP via `useApi`; the store exposes `loading`/`error`; `pytest` + `npm test` green; Prettier clean.

## Dev Notes

**This story was added post-hoc (2026-07-06), not from an original FR** — once users can add words (Story 1.5), they need to fix/remove their own. The seed stays read-only. It's the natural bookend to 1.5's writers and reuses them directly. [Source: epics-hotaru.md#Story 1.8]

**Custom vs seed is determined by location, enforced by the repo — not by trusting the id.** A word is mutable only if `find_word(user, id)` locates it in a *writable* file (`vocab_shared.json` or the caller's `words_private.json`). If it's not writable but IS in the seed → 403 (read-only). If nowhere the user can see → 404. This also gives privacy for free: another user's private word isn't in the caller's readable set → 404. [Source: architecture.md#Authentication & Security — path-as-privacy; #Data Architecture — read-only seed]

**Editable code from Stories 1.4/1.5 (read before editing):**
- `repositories/vocab_repo.py` — has `read_seed/read_shared/read_private/write_shared/write_private/textbook_sources`, `_SHARED_PATH`, `_private_path(user)`. **Add** `find_word`, `is_seed_word`, `remove_word`. Reuse existing readers/writers; keep them intact.
- `services/hotaru_vocab_service.py` — has `list_words`, `create_word`. **Add** `delete_word`, `update_word`. Note `create_word` mirrors the drill_caps rule — reuse the same expression (consider a private `_drill_caps(kanji)` helper to avoid duplication).
- `routers/hotaru.py` — has `GET /users`, `GET /words`, `POST /words`, `VALID_USER_IDS`. **Add** `DELETE` + `PUT /words/{word_id}`; reuse the user-validation + error-mapping pattern (translate stdlib errors → HTTPException here only).
- `schemas/hotaru.py` — has `Word`, `CreateWordRequest`, `DrillCap`, `Visibility`. **Add** `UpdateWordRequest` (editable fields, no `source`).
- `stores/useHotaruLibraryStore.ts` — has `createWord`, section helpers. **Add** `deleteWord`, `updateWord` (mirror `createWord`'s local-reflect + fire-and-forget reload — the review fix).
- `components/WordRow.vue` — add an `editable` prop + delete/edit affordances (default off → seed rows unchanged).
- `pages/LibraryPage.vue` — pass `editable` per row (custom iff source ∈ userIds), wire the delete confirm.
- `pages/AddWordPage.vue` — extend to edit mode, or extract a shared form component. `routes.ts` — add the edit route.

**HTTP verbs.** Use **PUT** for update (the existing `useApi` boundary exposes `get/post/put/del` — no `patch`; do NOT add one just for this). PUT here means "replace the editable fields" — `id`/`source` are server-preserved. `api.del` returns void (backend 204). [Source: frontend/src/composables/useApi.ts]

**Who can edit/delete.** Private words: only the owner (structural — nobody else can see them). Shared custom words: **either** user (they're communal); `source` records the original creator but does not restrict management. Seed words: nobody. [Source: epics-hotaru.md#Story 1.8 — "a private word can only be deleted by its owner"]

**Atomicity / LWW.** Same as 1.5 — read-modify-write in the service, atomic write in the repo; shared-file concurrent edits are last-write-wins (accepted). Never write the seed. [Source: architecture.md#Implementation Patterns]

**Frontend delete UX.** A trash control on custom rows; confirm before deleting (a destructive action) via `window.confirm` (consistent with the unsaved-changes guard) or a small q-dialog. After delete/edit, the library reflects the change (local update + reload). [Source: DESIGN.md; EXPERIENCE.md]

**Scope (YAGNI).** Edit/delete of user-added words only. No bulk delete, no undo, no edit of seed words, no `source` re-assignment (word stays in its section), no topics. Keep the edit form DRY by reusing the add form rather than duplicating fields.

**Coding standards.** Backend type hints + `pathlib`; frontend `<script setup lang="ts">`, `defineProps/Emits<{}>()`, `interface`, no `any`; co-located `*.spec.ts`; scoped `.hotaru-app` theme. [Source: docs/architecture/coding-standards.md]
