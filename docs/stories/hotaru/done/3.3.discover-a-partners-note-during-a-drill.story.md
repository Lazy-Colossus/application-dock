# Story 3.3: Discover a partner's note during a drill

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to see shared notes on a word while drilling it,
so that my partner's tip helps me right when I need it.

## Acceptance Criteria

1. **Notes ride along with the queue (no second fetch).** Given the drill queue payload (`GET /api/hotaru/practice/queue`), when a word is served, then each `QueueItem` carries that word's notes for the active user — **shared notes + the active user's own private notes**, privacy-filtered **server-side** — so the drill renders them without a follow-up request (FR-24, NFR-6). A partner's private notes are **absent** from the payload (NFR-2, path boundary).

2. **The note is visible on the card, on reveal.** Given a drill card whose word has a note, when I **reveal** it, then the note(s) show in the drill view — text + author attribution, 🔒 on a private note, the active user's own shown as "You" — consistent with the notes dialog. A word with no notes shows nothing extra (no empty box). Notes appear only on the reveal side (not on the prompt), so they never spoil a JP→EN answer.

3. **Ordering + privacy match the dialog.** Given a word's notes in the queue, when they render, then they are oldest→newest (same as `notes_service.list_for_word`) and contain only what the active user may see; switching user re-scopes the queue (a fresh `GET /practice/queue?user=` already happens per session), so notes re-filter for the new user.

4. **Queue-not-debt + no regressions.** Given the change, when the queue is built, then it still obeys SRS ordering, `drill_caps` direction filter, the session soft-cap, and carries **no** due/overdue/next_review_at (NFR-5) — `notes` is the only new field on `QueueItem`. Study mode (`/practice/study`, Story 2.8) and Quick Practice (2.9) are unaffected.

5. **Conventions + quality gate.** Backend: notes assembled in a **service** (privacy-filtered), the only file I/O in `notes_repo`, no HTTPException outside the router; batch the note reads (don't do O(N) per-word file reads — NFR-6). Frontend: `QueueItem.notes` typed; the drill card renders via the existing display logic (no raw `fetch`; nothing new hits `useApi`). `pytest` + `npm test` green; `black`/`ruff` + `vue-tsc` + Prettier clean.

**Privacy is server-side and already solved — reuse it, batched.** `notes_service.list_for_word` is the exact shared-plus-own-private, oldest-first, others'-private-never-read assembly (3.1).
