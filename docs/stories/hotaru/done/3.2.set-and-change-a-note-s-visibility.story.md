# Story 3.2: Set and change a note's visibility

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to choose shared or private for a note, and change my mind later,
so that I control what my partner sees.

## Acceptance Criteria

1. **Create shared or private (already delivered in 3.1 — must not regress).** Given I create a note, when I set **Shared** or **Private**, then it's stored accordingly — a shared note in `DATA_DIR/hotaru/notes_shared.json`, a private note in `DATA_DIR/hotaru/users/{me}/notes_private.json` (FR-23, path-as-privacy). _3.1 shipped this; 3.2 keeps it green and adds the flip below._

2. **Flip an authored note's visibility.** Given a note **I authored**, when I flip its visibility (`PATCH /api/hotaru/notes/{note_id}?user=`, body `{ visibility }`), then it **moves between files** — shared→private relocates it into my `notes_private.json` and out of `notes_shared.json`; private→shared relocates it into `notes_shared.json` and out of my `notes_private.json` — its `id`, `word_id`, `author`, `text`, and `created_at` are preserved, and the response is the updated `Note`. Flipping to the visibility it already has is an idempotent no-op (returns the note unchanged, no duplication).

3. **The partner's view updates accordingly.** Given a note I flip **shared→private**, when my partner reloads that word's notes, then the note is **absent** from their payload (it now lives only under my directory — never read for them, NFR-2). Given I flip **private→shared**, when my partner reloads, then the note now **appears** for them (attributed to me, no badge).

4. **Author-only (the one authorization rule here).** Given a note I did **not** author (a partner's shared note I can see), when I attempt to flip it, then the API rejects it (**403**) and nothing moves. Given an unknown/invisible note id (including a partner's private note, which is never read for me), when I PATCH it, then it's **404**. Unknown `user` → **404**.

5. **Flip it from the notes UI.** Given the `WordNotesDialog` note list, when a note is one **I authored**, then it exposes a visibility toggle (a 🔒 Private / Shared control on the row) that flips it via the store; a note authored by my partner shows **no** flip control (read-only to me). The 🔒 mark and attribution stay correct after a flip; calm, mobile-first, Neon-themed (hardcoded palette — the dialog teleports out of `.hotaru-app`).

6. **Conventions + no regressions.** Backend: the flip lives in `notes_repo` (the only notes file I/O — a move = remove-from-source + add-to-dest, both atomic) + `notes_service` (stdlib errors: `PermissionError` for non-author, `FileNotFoundError` for missing) + one router endpoint (HTTPException only in the router: `403`/`404`). Frontend: the notes store gains a flip action exposing `loading`/`error`, HTTP via `useApi`. `pytest` + `npm test` green; `black`/`ruff` + `vue-tsc` + Prettier clean.

## Dev Notes

**What 3.2 actually adds is the _flip_.** Per 3.1's documented scope split, creating a note with a shared/private choice (and the load-bearing NFR-2 privacy read) already shipped in 3.1. 3.2 is the clean, bounded follow-up: `PATCH /api/hotaru/notes/{id}` that **relocates** a note between the shared file and the author's private file, author-only, and the endpoint + store action + a per-row flip control to drive it. Do **not** rebuild the notes aggregate — extend it. [Source: docs/stories/hotaru/for-review/3.1.add-and-view-notes-on-a-word.story.md#Completion Notes ("flipping ... is 3.2"); epics-hotaru.md#Story 3.2]

**Visibility is encoded by _which file_ holds the note — so a flip is a move, not a field edit.** `notes_repo` has no single "notes table": a shared note lives in `notes_shared.json`, a private note under `users/{author}/notes_private.json` (NFR-2, path-as-privacy). Flipping therefore = remove from the source file + add to the destination file (two atomic `_storage` writes). There is deliberately no `visibility` mutation-in-place; the `Note.visibility` field just records which file it's in. Mirror `hotaru_vocab_service.update_word`'s visibility-change, which already moves a word between `vocab_shared.json` and the owner's `words_private.json` the same way. [Source: repositories/notes_repo.py (add/read/write split); services/hotaru_vocab_service.py update_word (visibility move); AR-3/AR-4; NFR-2]

**Author-only, and privacy makes it mostly self-enforcing.** The `GET` payload only ever contains shared notes + the caller's **own** private notes, so a private note the caller can flip is always their own. The one real authorization check is on a **shared** note authored by the partner: the caller can *see* it but must not flip it → `note.author != user` raises `PermissionError` → **403** in the router. A partner's **private** note is never even read for the caller (`find` only reads the caller's private file) → it's simply not found → **404**. Use the same exception→status idiom `update_word`/`delete_word` already establish: `PermissionError → 403`, `FileNotFoundError → 404`, unknown `user → 404`. [Source: routers/hotaru.py update_word/delete_word; services/notes_service.list_for_word; NFR-2]

**Idempotent no-op.** Flipping to the visibility a note already has must return it unchanged and **not** re-append (which would duplicate it in the file). Guard with `if note.visibility == visibility: return note` before any write. [Source: this story AC-2]

**The flip control is per-note and author-gated in the UI too.** `WordNotesDialog` currently renders each note read-only (text + 🔒-on-private + author). Add the toggle only where `n.author === activeUser`; partner-authored (shared) notes stay read-only. Reuse the `.wn-vis`/`.wn-vis__btn` pill styles already in the file for the add row — same look, no new palette work. After a flip the store replaces the note in `notesByWord`, so the 🔒 mark and the shared/private pill re-render from the fresh `visibility`. [Source: components/WordNotesDialog.vue (existing note row + .wn-vis styles)]

**Teleported dialog still hardcodes colors.** No change from 3.1: `q-dialog` teleports to `<body>` outside `.hotaru-app`, so `--hotaru-*` vars don't resolve. The flip control reuses the file's existing hardcoded Neon-dusk pill styles (`#38f0e6` on-state, `#b3aede` off) — don't introduce `var(--hotaru-*)`. [Source: WordNotesDialog.vue <style>; 3.1 Dev Notes "teleported dialogs must hardcode colors"]
