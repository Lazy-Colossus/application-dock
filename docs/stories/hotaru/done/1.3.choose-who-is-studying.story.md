# Story 1.3: Choose who's studying (identity + avatar switcher)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to pick whether I'm Dani or Jake on entry and switch later,
so that my progress and private content stay mine.

## Acceptance Criteria

1. **"Who's studying?" on entry.** Given Hotaru is opened and no active user is set, when I navigate into the app, then a "Who's studying?" screen offers the two users (Dani, Jake) as tappable avatars — no password/account (FR-2).

2. **Selecting sets the active user.** Given the "Who's studying?" screen, when I tap a user, then that user becomes the active user and I land on the Hotaru home; the choice persists across reloads (so I'm not re-prompted every visit).

3. **Avatar switcher in a top bar.** Given an active user, when any Hotaru page renders, then a top-bar shows the current user's avatar; opening its menu offers **Switch user** (to the other user) and **Settings**.

4. **Switching user.** Given the avatar menu, when I choose Switch user, then the other user becomes active (or I'm returned to the "Who's studying?" screen to choose), and the active-user state updates everywhere it's shown.

5. **Backend advertises the users.** Given `GET /api/hotaru/users`, when called, then it returns the two canonical users as `[{id, name}]` (direct array, no envelope) — the single source of truth the frontend consumes and later stories validate the `user` param against.

6. **No regressions / conventions.** Given the changes, when built, then existing tests pass; HTTP goes through `useApi`; the store exposes `loading`/`error`; Hotaru theme stays scoped; `pytest` + `npm test` green; Prettier clean.

## Dev Notes

**This is a mostly-frontend story.** Identity lives client-side in a Pinia store; the backend contributes only the canonical user list (`GET /api/hotaru/users`) as the single source of truth, which later stories use to validate the `user` query param on user-scoped endpoints. There are no user-scoped endpoints yet (they arrive in 1.4+), so no `user`-param plumbing is built here beyond exposing the list. [Source: architecture.md#Authentication & Security; #API & Communication Patterns]

**⚠️ USER-ID NAMING — decision needed (flagged as a question below).** The architecture's examples used `user1`/`user2` as user ids (and word `source`), while DESIGN.md's avatar tokens key off `dani`/`jake`. This story uses **`dani`/`jake` as the ids** (self-documenting; makes word `source` read as `dani`/`jake` and paths `users/dani/`; matches DESIGN tokens). If confirmed, the architecture's `user1`/`user2` example strings should be updated to `dani`/`jake` for consistency (a doc edit, no code impact yet). See the question at the end.

**No auth (NFR-3).** Two hardcoded users; picking one is identity, not authentication. No passwords, no sessions, no tokens.

**Store pattern (match archery).** Pinia **setup store** (`defineStore('hotaruUser', () => { ... })`) with `ref`s and `loading`/`error`, actions setting `loading` in `try/finally` and routing errors into `error.value` — exactly like `useArcheryHistoryStore.ts`. All HTTP via `import { api } from '@/composables/useApi'` (`api.get<HotaruUser[]>('/hotaru/users')`); never raw fetch. [Source: CLAUDE.md#Frontend; source-tree.md#Frontend boundary rules]

**Persistence.** `activeUserId` → `localStorage['hotaru.activeUser']`, hydrated on store creation; guard against a stale id not in the users list. This satisfies AC-2 "persists across reloads." (Note: user-switch being a *hard session boundary* for the drill is a Story 2.x concern — not in scope here; here it only changes whose identity is active.)

**Top bar placement — scope boundary.** The shell's `MainLayout` app bar is global chrome (title + back + home) and is Carbon-themed; do NOT add the Hotaru avatar to it (that would leak app-specific UI into the shell and break the boundary). Put `AvatarSwitcher` inside Hotaru's own page header (starting with `HotaruHomePage`). A dedicated Hotaru layout can come later if multiple pages need the same header; for this story, the home page hosts it. [Source: source-tree.md#Frontend boundary rules — apps are self-contained; MainLayout is shell chrome]

**Avatar visuals.** Circle with the user's initial; per-user soft colour from DESIGN.md avatar tokens (`bg-dani` = familiarity tier-2 `#eebf86`, `bg-jake` = tier-4 `#a6c87e`, text = `#22260f`), on the scoped `.hotaru-app` theme. Non-semantic (just distinguishes the two people). [Source: DESIGN.md components.avatar]

**Guard approach.** Keep it simple and testable: `HotaruHomePage` checks the store on mount and `router.replace('/hotaru/identity')` when no active user. (A router `beforeEnter` guard is an acceptable alternative, but the in-page check is easier to unit-test and sufficient for one entry page.)

**Scope discipline (YAGNI).** Build identity + switching + the users endpoint only. Do NOT build the Settings screen (menu item is a placeholder/no-op), any user-scoped data endpoints, or drill/library behaviour. Those are later stories.

**Coding standards.** `<script setup lang="ts">`; `defineProps<{}>()`/`defineEmits<{}>()`; `interface` for object shapes; no `any` without justification; type hints on backend signatures; co-located `*.spec.ts`. [Source: docs/architecture/coding-standards.md; CLAUDE.md#Conventions]
