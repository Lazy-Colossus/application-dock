# Story 3.6: Edit or delete a note

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

_Added 2026-07-17 — not from an original FR. Epic 3 shipped add (3.1), view (3.1/3.3), and flip-visibility (3.2), but a note's text can't be corrected and a note can't be removed. This closes the note lifecycle: the author can edit a note's text and delete a note. Same author-only + path-privacy rules as the flip._

## Story

As a learner,
I want to fix the wording of a note I wrote, or remove one I no longer want,
so that our shared tips stay accurate and uncluttered.

## Acceptance Criteria

1. **Edit my own note's text.** Given a note **I authored**, when I edit its text (`PATCH /api/hotaru/notes/{note_id}?user=`, body `{ text }`), then the note's `text` updates in place in whichever file holds it (shared or my private) — `id`, `word_id`, `author`, `visibility`, `created_at` preserved — and the response is the updated `Note`. Text is validated exactly like create (trimmed, non-empty, ≤300 chars); empty/oversize → `422`.

2. **Delete my own note.** Given a note **I authored**, when I delete it (`DELETE /api/hotaru/notes/{note_id}?user=`), then it is removed from its file and disappears from everyone's view; the response is `204`. A word can end up with zero notes (calm empty state, per 3.1).

3. **Author-only (the one authorization rule).** Given a note I did **not** author (a partner's shared note I can see), when I try to edit or delete it, then it's rejected (**403**) and nothing changes. Given an unknown/invisible note id (incl. a partner's private note, never read for me), then it's **404**. Unknown `user` → **404**. (Same rules as the 3.2 flip.)

4. **Edit + flip compose (no regression to 3.2).** Given the extended `PATCH`, when the body carries **only** `visibility`, then it behaves exactly as Story 3.2 (move between files); when it carries **only** `text`, it edits in place; when it carries **both**, the note is edited and relocated in one call. The 3.2 flip and its tests keep working unchanged.

5. **Edit / delete from the notes UI.** Given the `WordNotesDialog` note list, when a note is one **I authored**, then it exposes **Edit** and **Delete** affordances (alongside the existing flip control); a partner's note shows none. Edit puts the note text into an inline editable field (reuse the composer's trimmed 300-char guard) with Save/Cancel; Delete asks for a single confirm, then removes it. Because the drill (3.4) and the inline library panel (3.5) both open this same dialog, edit/delete work there too — no extra wiring.

6. **Conventions + quality gate.** Backend: the edit/delete live in `notes_repo` (the only notes I/O) + `notes_service` (stdlib errors: `PermissionError`/`FileNotFoundError`/`ValueError`) + the router (HTTPException only: `403`/`404`/`422`/`204`). Frontend: store actions expose `loading`/`error`, HTTP via `useApi`. `pytest` + `npm test` green; `black`/`ruff` + `vue-tsc` + Prettier clean.

## Dev Notes

**This closes the note lifecycle, and the aggregate is already shaped for it.** Add (3.1), view (3.1/3.3), flip (3.2) exist; 3.6 adds edit-text + delete. The `notes_repo` move/rewrite machinery from 3.2 is 90% of what's needed — `set_visibility` already proves the add-before-remove crash-safe move and the author-only/`find` privacy path. Edit-in-place is the simpler sibling (`replace` in the same file); delete is `remove`. No new persistence model. [Source: repositories/notes_repo.py (find/set_visibility/add); services/notes_service.py; Story 3.2]

**Unify update under one PATCH (don't split text vs visibility into two endpoints).** Extending `UpdateNoteRequest` to optional `text` + optional `visibility` keeps a single, REST-clean "update a note" endpoint and one frontend store action per concern. Text-only → in-place rewrite (same file). Visibility change → move (reuse the 3.2 order). Both → edit the text then relocate. Crucially, the 3.2 contract (`PATCH {visibility}`) is a strict subset, so its behaviour and tests are unchanged — verify that explicitly. [Source: routers/hotaru.py PATCH /notes/{id}; schemas UpdateNoteRequest; Story 3.2 tests]

**Author-only + privacy are inherited, not re-invented.** `find(note_id, user)` reads the shared file then only the caller's own private file, so a partner's private note is structurally invisible → `404` (never `403`); a partner's *shared* note is visible but `author != user` → `403`. Edit and delete both gate on this the same way the flip does. `remove` must delete from the shared file if the id is there, else the caller's private file — never the partner's private file. [Source: notes_repo.find; Story 3.2 author-only; NFR-2]

**Validation mirrors create exactly.** Editing reuses the create rules: `text.strip()`, non-empty, `≤ MAX_NOTE_LENGTH` (300) — the same `ValueError → 422` the router already maps. Front-end edit reuses the composer's trimmed 300-char guard so the UI and server agree. [Source: notes_service.create_note; NoteComposer]

**Delete confirmation — one confirm, calm copy.** Match the custom-word delete UX (a single confirm, no scary modal). No undo needed for v1 (household scale); keep the copy plain ("Delete this note?"). [Source: LibraryPage word-delete flow; DESIGN.md voice]

**Edit/delete ride into the drill + inline panel for free.** Because 3.4 (mid-drill) and 3.5 (library row) both open the *same* `WordNotesDialog`, adding Edit/Delete to that dialog surfaces them everywhere notes appear. DrillPage must merge the edit/removal onto `current.notes` (like `onDrillFlipNote` merges a flip) so the card + presence cue stay correct without a refetch; the library panel reflects via the store (`notesFor`) reactively. [Source: DrillPage onDrillFlipNote; LibraryPage notes wiring; Stories 3.4/3.5]

**Scope (YAGNI).** Edit text + delete, author-only. **NOT** here: an "edited at" timestamp/marker (nice-to-have — add only if trivial), edit history/undo, rich text, bulk delete, editing another user's note. An `"edited"` whisper-tag is optional; skip unless it's a one-liner. [Source: epics-hotaru.md#Epic 3]
