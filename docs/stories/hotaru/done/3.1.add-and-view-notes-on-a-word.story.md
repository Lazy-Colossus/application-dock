# Story 3.1: Add and view notes on a word

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a learner,
I want to attach memory notes to a word and read existing ones,
so that I can capture and benefit from tips.

## Acceptance Criteria

1. **Add a note to a word.** Given a word, when I add a note (`POST /api/hotaru/words/{id}/notes?user=`, body `{ text, visibility }`), then it persists with its **text + author** (the active user) + a `created_at`, gets a stable id, and a word may carry **multiple** notes (FR-22).

2. **View a word's notes, privacy-filtered.** Given notes on a word, when the list loads for the active user (`GET /api/hotaru/words/{id}/notes?user=`), then it returns that word's **shared** notes **plus the active user's own private notes**, each **attributed** to its author; **another user's private notes are absent from the payload** (FR-24, NFR-2). Private notes are marked 🔒 in the UI; shared notes carry no badge.

3. **Shared vs private storage (path-as-privacy).** Given a note's visibility, when it's saved, then a **shared** note goes to `DATA_DIR/hotaru/notes_shared.json` and a **private** note to `DATA_DIR/hotaru/users/{author}/notes_private.json` — the same path boundary the vocab uses, so another user's private notes are never even read (NFR-2). _(Choosing shared/private at creation is included here so the privacy read is real + testable; **flipping** an existing note's visibility is Story 3.2.)_

4. **A place to read/add notes.** Given a word row in the Library, when I open its **Notes** action (from the ⋮ menu), then a notes view lists the word's notes (text + author + 🔒 on private, newest first) and offers an inline **add** field (text + a shared/private choice, defaulting shared). Calm, mobile-first, Neon-themed.

5. **Conventions + no regressions.** Backend: new `notes_repo` (the only notes file I/O) + `notes_service` (stdlib errors) + router endpoints (HTTPException only in the router); atomic writes. Frontend: a Pinia notes store exposing `loading`/`error`; HTTP via `useApi`. Empty note text → `422`; unknown user → `404`. `pytest` + `npm test` green; `black`/`ruff` + `vue-tsc` + Prettier clean.

## Dev Notes

**This is the first Epic-3 story — it stands up the whole notes aggregate.** Data files, repo, service, two endpoints, a notes store, and a notes view. Notes are the cooperative layer: shared tips both users see, private tips only the author sees. The **one hard rule** (NFR-2) is path-as-privacy: a private note lives under its author's directory and is *never read* for anyone else — enforced by the repo path, not a filter. [Source: epics-hotaru.md#Epic 3 / #Story 3.1; prd FR-22/FR-24; NFR-2]

**Mirror the vocab aggregate exactly — it's the proven pattern.** `notes_repo` is the notes twin of `vocab_repo`: a shared file at `hotaru/notes_shared.json` and a per-user `hotaru/users/{user}/notes_private.json`, both via `_storage.atomic_write_json`/`read_json` (default `[]`). `notes_service.list_for_word` = the notes twin of `vocab_service.list_words`' assembly: shared + the caller's own private, others' private never touched. Don't invent new persistence — copy the shape. [Source: repositories/vocab_repo.py (read_shared/read_private/write_*), services/hotaru_vocab_service.list_words, repositories/_storage.py; AR-3 (notes file layout), AR-4 (notes_repo)]

**Scope split with 3.2 (documented decision).** The epic puts "create with Shared/Private" in 3.2, but a note must be *stored* somewhere the moment it's created, and 3.1's AC2 (show own-private 🔒, hide others' private) can only be built + proven if private notes can exist. So **3.1 includes the shared/private choice at creation** (the storage split + the privacy read — the load-bearing NFR-2 work). **3.2 owns _flipping_ an existing note's visibility** (`PATCH /notes/{id}`, move between files, author-only) — a clean, bounded follow-up. Note this in the completion notes. [Source: epics-hotaru.md#Story 3.1 vs #Story 3.2]

**A dialog, not a new detail page (documented deviation).** UX-DR8 says "inline add in detail view", but there's no word-detail page yet and building one is out of proportion for 3.1. Reuse the **dialog** pattern (`WordTopicsDialog`): a `WordNotesDialog` opened from the row ⋮ menu is consistent, mobile-first, and lighter. If a full word-detail page is wanted later it can host the same NoteList/AddNote. [Source: WordTopicsDialog.vue; UX-DR8; EXPERIENCE.md]

**Teleported dialogs must hardcode colors.** Learned the hard way in the last batch: `q-dialog` teleports to `<body>`, outside `.hotaru-app`, so `--hotaru-*` CSS vars don't resolve and fall back (to the old forest green). `WordNotesDialog` must **hardcode** the Neon dusk palette — glass `rgba(20,18,52,0.98)` + blur, cream `#f1f0ff` / soft `#b3aede` text, violet `rgba(155,107,255,0.30)` borders, dark input `rgba(4,6,15,0.5)`, and `accent-color: #38f0e6` on any native checkbox. Copy `WordTopicsDialog.vue`'s (just-fixed) styles. [Source: WordTopicsDialog.vue post-fix; BulkTopicDialog.vue]

**Author attribution.** A note stores `author` = the user id (`dani`/`jake`). The dialog resolves it to a display name via the `users` list (from `useHotaruUserStore`, already loaded in the Library). Since the payload only ever contains shared notes + the caller's own private notes, every private note shown is the caller's own — 🔒 keys purely off `visibility === "private"`. [Source: routers/hotaru.py `_USERS`/`VALID_USER_IDS`; useHotaruUserStore]

**`created_at` + injected `now`.** Notes get a `created_at` (ISO) for ordering; the service takes `now: datetime | None = None` defaulting to `datetime.now(UTC)` so tests pass a fixed instant — the same clock-injection convention as `srs`/`hotaru_practice_service`. Use `from datetime import UTC, datetime` (ruff UP017). [Source: services/srs.py, hotaru_practice_service.py clock injection]
