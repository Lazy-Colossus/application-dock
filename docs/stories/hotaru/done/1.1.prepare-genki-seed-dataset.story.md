# Story 1.1: Prepare the Genki seed dataset (offline)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the project owner,
I want an offline tool that turns the raw Genki word list into a prepared, ID-stamped seed dataset,
so that the Hotaru app has canonical, drillable vocabulary content to ship (read-only at runtime).

## Acceptance Criteria

1. **Seed produced with stable IDs.** Given the raw source array (objects of `{hiragana, kanji, romaji, type, english, lesson, edition}`, with **no `id` field**), when `scripts/build_hotaru_seed.py` runs, then it writes `backend/app/hotaru_seed/vocab_seed.json` where every word has a `source` of `f"genki_{edition}"` (e.g. `genki_3`), a stable `id` of the form `"{source}-{lesson}-{seq}"` (`seq` = 1-based ordinal within each `(source, lesson)` group, zero-padded to width 4 — e.g. `genki_3-G-0007`), `kanji` normalized (`"" → null`), and the file carries a top-level integer `schema_version`.

2. **drill_caps computed correctly.** Given each word always has a reading (`hiragana`) and meaning (`english`) and may or may not have `kanji`, when the tool computes `drill_caps`, then every word includes `"r2m"` and `"m2r"`; `"k2r"` is present **iff** `kanji` is non-empty. (No `"listen"` cap in v1.)

3. **Deterministic + collision-safe.** Given the same raw input, when the tool runs twice, then it produces byte-identical IDs (deterministic ordering). Given two source rows that would mint the same `id`, when the tool runs, then it **fails loudly** with a clear error and writes nothing (no silent collision/overwrite).

4. **Field mapping is exact.** Given a source row, when it is transformed, then output fields are: `id` (minted), `source` ← `f"genki_{edition}"`, `reading` ← `hiragana`, `kanji` ← `kanji` (`""`→`null`), `romaji` ← `romaji`, `meaning` ← `english`, `pos` ← `type`, `lesson` ← `lesson`, `visibility` ← `"shared"` (constant for all seed words), `drill_caps` ← computed. The raw `edition` field is folded into `source` and is NOT emitted as a standalone field.

5. **Validated by tests.** Given `backend/tests/test_hotaru_seed.py`, when it runs against the produced `vocab_seed.json`, then it asserts: every word has `len(drill_caps) >= 2`; `"k2r" in drill_caps` ⇔ `kanji is not None`; all `id`s are unique; `schema_version` is present; re-running the build yields identical IDs.

## Dev Notes

**What this is.** An **offline, standalone Python script** — "step one" of the build, run manually (`python backend/scripts/build_hotaru_seed.py`). It is **NOT** part of the served FastAPI app, has **no** FastAPI/HTTP/runtime dependency, and produces a committed, read-only asset. [Source: architecture.md#Starter Template Evaluation, #Project Structure & Boundaries — "Offline boundary"]

**Why IDs are minted here.** The source has no IDs; downstream user-progress, notes, and topics reference words by `id`, so IDs must be **stable and assigned once, at prep time** (no runtime re-seed machinery, no ledger — per owner decision). Derive the id only from immutable locating fields (`source`, `lesson`, positional `seq`); never from editable `english`/`romaji`. [Source: architecture.md#Data Architecture — Word IDs; #Core Architectural Decisions]

**Canonical Word fields** (this story establishes the names that Story 1.4's Pydantic `Word` model in `schemas/hotaru.py` will formalize — match them exactly): `id, source, reading, kanji|null, romaji, meaning, pos, lesson, visibility, drill_caps[]`. Every word carries `visibility` (`shared|private`) for a consistent, total object shape; seed words are always `"shared"`. `kanji "" → None`. `DrillCap` values: `r2m`, `m2r`, `k2r`. [Source: architecture.md#Data Architecture; #Implementation Patterns — Schema & ingest rules]

**`source` field (every word).** Identifies origin: a textbook slug for seeded words (`genki_3` = Genki 3rd edition, derived `f"genki_{edition}"`) or a user id for user-added words (`user1`/`user2`, set in Stories 1.5/1.6). `source` **replaces** the earlier `edition` and `owner` fields: a word's origin and (for user words) ownership are both read from `source`. There is deliberately **no** separate "seeded vs user-added" boolean — it's derivable from `source` (and from storage location), so a flag would be redundant.

**drill_caps semantics** (so the drill never serves a card the data can't fulfill): `r2m`+`m2r` floor (reading+meaning always present); `k2r` iff kanji present. Empty-kanji words (e.g. ありがとう) **correctly** lack `k2r` — that is not an error. [Source: architecture.md#Data Architecture — drill_caps; epics-hotaru.md Story 1.1]

**Source shape & example** (lesson can be non-numeric, e.g. `"G"`):
```json
{"hiragana":"ありがとう","kanji":"","romaji":"arigatou","type":"expression","english":"Thank you.","lesson":"G","edition":3}
```
→ `{"id":"genki_3-G-0001","source":"genki_3","reading":"ありがとう","kanji":null,"romaji":"arigatou","meaning":"Thank you.","pos":"expression","lesson":"G","visibility":"shared","drill_caps":["r2m","m2r"]}`

**Determinism.** Sort within `(source, lesson)` group by `(hiragana, kanji_or_"", english)` so row order in the source file never changes IDs; re-running is idempotent.

**Output envelope.** `{"schema_version": 1, "words": [...]}`. The `schema_version` enables a `migrate(raw)→current` hook in `vocab_repo` (Story 1.4) since there's no DB to ALTER. [Source: architecture.md#Implementation Patterns — Schema & ingest rules]

**Coding standards.** Black + Ruff; type hints on public functions; `pathlib.Path` over `os.path`; f-strings; minimal comments (only non-obvious *why*). [Source: docs/architecture/coding-standards.md]

**Anti-patterns to avoid.** Do NOT: use array index as `id`; hash `english`/`romaji` into the id; write to `DATA_DIR` (the seed is a committed repo asset, not runtime-writable state); import from the FastAPI app or add AI fields (no AI in v1).
