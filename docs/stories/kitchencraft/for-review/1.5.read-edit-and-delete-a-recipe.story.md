# Story 1.5: Read, edit and delete a recipe

## Status

Ready for Review

## Story

As a cook,
I want to open a recipe to cook from it, correct it, or throw it away,
so that my collection stays accurate and useful at the stove.

## Acceptance Criteria

1. **Legible mid-cook.** Given a recipe with a multi-line body, when it is opened, then the body renders with its line breaks and blank lines intact, legible one-handed at phone width without pinch-zoom. (NFR-4, NFR-8)

2. **Edits persist.** Given an existing recipe, when any field is edited and saved, then the change persists and `updated_at` advances. (FR-4)

3. **A non-body edit never touches the body.** Given an edit that changes only fields other than the body, when it is saved, then the stored body is byte-identical to what it was before. (FR-5, NFR-3)

4. **Delete behind a confirmation.** Given a recipe the user wants gone, when delete is chosen, then a confirmation is required first, and on confirming the recipe disappears from the collection in one action; there is no undo and no trash. (FR-4)

5. **Unknown id is a 404.** Given a request for an unknown recipe id, when it reaches the API, then it returns 404 with `{ detail }`, translated from the service's `FileNotFoundError`. (NFR-2)

### Completion Notes

- **AC 3 is enforced by the update protocol, not by a guard.** The router sends `model_dump(exclude_unset=True)` and the service applies only the keys present, so an edit that never mentions `body` cannot rewrite it. A backend test edits five other fields at once and asserts the messy body is byte-identical afterwards.
- **`pre-wrap` is the rendering half of the verbatim contract.** The body is interpolated as text into a `div`, so a leading `- ` stays a hyphen and a space. A spec asserts no `<ul>`, `<li>` or `<strong>` appears and that `**not bold**` survives literally — there is no markdown pass and there must never be one.
- **`updated_at` advances only on a real change.** Re-saving identical values is not an edit; a test asserts the timestamp holds. This matters for Epic 4, which will re-run enrichment batches and must be idempotent (FR-20).
- **The confirmation has no escape or backdrop dismissal, by design** (UX-DR14). Escape and the backdrop close a *modal*; a confirmation requires an explicit choice. Worth flagging in review because it reads like an omission and is not one.
- The reading view **reads live from the store** rather than copying into local state, so a favourite toggled on the collection and an edit saved on the next screen are both reflected without a refetch.
- The "no undo" spec was first written as a regex over the whole page and caught the confirmation's own *"This can't be undone"* copy. Rewritten to assert the button set instead — the copy may say "undone", but no control may undo or restore.
- An unknown id renders *"That recipe isn't here."* rather than an empty frame — not specified in the spine, but the alternative is a blank reading view.

## Dev Notes

**The body is the hero** ([Source: DESIGN.md § Typography]): `recipe` at 18px/1.75 inside 62ch is a **hard floor** at every surface and breakpoint — never smaller, never compressed to fit more on screen. This is the whole answer to the PRD's mid-cook metric.

**Structure sits at the edges** ([Source: DESIGN.md § Layout & Spacing]) — above and below the body, never wrapped around it. Nothing frames the method.

**Confirmation discipline** ([Source: EXPERIENCE.md § Component Patterns → Modal]): escape and the backdrop close a modal but **never** a confirmation.

**No undo, anywhere** ([Source: EXPERIENCE.md § Interaction Primitives]) — the confirmation is the only safety net, by design.
