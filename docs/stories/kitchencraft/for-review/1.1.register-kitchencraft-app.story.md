# Story 1.1: Register KitchenCraft in the Application Dock shell

## Status

> **PARTLY SUPERSEDED 2026-09-23 by the shared household collection (`34b23f4`).** KitchenCraft
> data is no longer per user; one collection and one shopping list serve the
> household. The auth requirement this story set up still stands, unchanged:
> every route requires a signed-in caller. The "data is per-user" reason given
> for it in the notes is out of date.

Ready for Review

## Story

As a user,
I want KitchenCraft to appear as an app in the dock and open to its own home,
so that I can launch it like any other app in the platform.

## Acceptance Criteria

1. **Card renders on the landing page.** Given the dock landing page, when it renders the app registry, then a KitchenCraft card appears (label "KitchenCraft", Material icon `menu_book`) alongside the existing apps, and selecting it routes to `/kitchencraft`. (FR-1)

2. **Backend advertises the app.** Given `GET /api/apps`, when called, then the response includes a KitchenCraft `AppDescriptor` (`id: "kitchencraft"`, `label: "KitchenCraft"`, `icon: "menu_book"`, `route: "/kitchencraft"`).

3. **Self-contained module + mounted router.** Given the new app module, when the project is set up, then `src/apps/kitchencraft/` exists (the shell imports it only via `registry.ts`), a backend `routers/kitchencraft.py` is mounted under `/api/kitchencraft` behind `Depends(get_current_user)`, and `docs/stories/kitchencraft/{for-review,done}/` exist.

4. **No regressions.** Given the changed shell files, when the quality gate runs, then existing `pytest` / `npm test` stay green and `black`, `ruff` and `eslint` are clean.

### Completion Notes

- Registered via the platform's documented 4-step "add an app" flow, following Context-Switch Story 1.1 as the cleanest recent template. Icon is `menu_book` in **both** `registry.ts` and `shell.py`.
- **Four routes rather than one.** `EXPERIENCE.md` says "one route", but its own IA table lists Capture, Recipe view and Edit as separate surfaces, and the shell's back button needs real history entries. Read "one route" as "one registry entry"; sub-routes are the pragmatic reading and match every other dock app.
- **One deliberate shell change beyond the two-file flow:** the `app-bar--kitchencraft` header variant. KitchenCraft is the dock's first light-ground app and `DESIGN.md § Colors` is explicit that the dark shell must not bleed into it; leaving the Carbon bar would put a near-black strip above beige paper. Overriding Quasar's `color="grey-5"` needs `!important` because Quasar's `text-*` classes carry it — noted inline.
- Unlike Context-Switch 1.1, this router was **not** left endpoint-free: Story 1.2 landed in the same pass, so the CRUD endpoints arrived with it.

## Dev Notes

**This is the platform's documented "add a new app" flow** (CLAUDE.md → "Adding a new app"): (1) registry entry, (2) lazy route(s), (3) backend `_APPS` + router, (4) story folders.

**Icon consistency.** `menu_book` in both `registry.ts` and `shell.py` — archery historically differs between the two; do not repeat that.

**Auth.** Include `meta.requiresAuth: true` on every route: KitchenCraft data is per-user and must sit behind the dock's JWT auth (NFR-5).

**Coding standards.** Frontend `<script setup lang="ts">`, no `any` without justification; backend type hints on public signatures. [Source: docs/architecture/coding-standards.md; CLAUDE.md#Conventions]
