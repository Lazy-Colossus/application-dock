# Story 4.3: Apply bulk structured updates safely

## Status

Ready for Review

## Story

As the builder,
I want to apply inferred structure to many recipes in one run,
so that a collection of pasted text becomes filterable without anyone doing data entry.

## Acceptance Criteria

1. **Named fields and tags update; every body is byte-identical afterwards.** (FR-20, FR-5, NFR-3)

2. **A batch still lands after a rename**, because recipes are addressed by stable id and never by name. (FR-20)

3. **An unknown id fails, is reported, and the rest of the batch still applies.** (FR-20)

4. **Any interruption leaves every recipe in a valid state** — none half-written. (FR-20, NFR-1)

5. **An identical batch run twice is a no-op**: no duplicated tags, no churned timestamps. (FR-20)

6. **A field or tag marked user-set is left alone, and the skip is reported.** (FR-21)

### Completion Notes

- **The body is restored rather than trusted.** `_apply_batch` copies the body back from the pre-change snapshot before comparing, so no future field handler can touch it by accident. Belt and braces on the one asset NFR-3 calls irreplaceable.
- **AC 4 comes from the transaction, not from per-recipe writes.** The whole batch runs inside one `doc_transaction`, which writes once on a clean exit — so an interruption writes *nothing* rather than leaving some recipes updated and others not. A test asserts an invalid number leaves no partial mutation behind.
- **AC 5 falls out of AC 6.** A second run finds every field either already correct or user-set, so nothing changes and `updated_at` is never touched. Asserted directly, because a churned timestamp is the kind of thing that only surfaces months later.
- **A machine-set value is deliberately NOT protected from a later pass.** A guess is not a decision; only the user's own values are untouchable. There is a test for that, because the opposite reading is plausible and someone will assume it.
- **A hand-written ingredient list is never added to.** This is the one place the rule is "leave the whole field alone" rather than "leave the set values alone" — adding to a list the user wrote is editing their work, not filling a gap.
- **Verified against real data before being reverted.** The loop was run end to end against the dev collection: the dry run skipped a user-set `meal_type`, flagged an unknown id, and wrote nothing; the real run applied two recipes and marked them; a re-run reported 0 applied and 2 unchanged. The invented values were then reverted — `unconfirmed` is the exact inverse of what a pass added, which made the revert a clean operation rather than a guess.
