# Story 3.1: One shopping list, one tap away

## Status

> **PARTLY SUPERSEDED 2026-09-23 by the Notebook retheme (`798df7e`).** The
> "Beige Ledger" palette this story was written against is gone: `moss`, `ink`,
> `taupe`, `beige` and `danger` no longer exist as tokens. Every accessibility
> rule they carried survives under the new names — contrast is still measured,
> quiet text still never uses the hairline colour, and status is still never
> colour alone. The shopping-list button is still **chrome and not the page's primary action**, so it still must not take the filled treatment that marks the one thing you came to the screen to do. That fill is burgundy now rather than moss.

Ready for Review

## Story

As a cook,
I want a single shopping list I can open from anywhere in the app,
so that I can add to it or check it without losing what I was doing.

## Context

This story is the gate on Epic 3: it lands the document, the store and the modal
shell that Stories 3.2 (ticking), 3.3 (sending a recipe's ingredients) and 3.4
(add-versus-overwrite) all build on. None of them can start before it.

It deliberately ships **only** the list's existence, hand-entry and persistence.
Ticking, deleting, clearing and anything to do with recipes belong to the stories
that follow, and must not creep in here.

## Acceptance Criteria

1. **Reachable from every screen.** Given any KitchenCraft screen, when it renders, then a shopping-list button is present in the top-right corner — the collection, the capture screen, the reading view and the edit screen, without exception. (FR-14)

2. **A modal that returns you exactly where you were.** Given the user is mid-scroll on the collection or reading a recipe, when the shopping list is opened and then closed, then it opened as a modal over the current screen, and closing restored that screen with its scroll position and its filter state untouched. Opening the list never navigates. (FR-14)

3. **Hand-entry persists.** Given the shopping list, when the user types an item by hand and commits it, then it is added to the list and survives a refresh, a new session and another device. (FR-15)

4. **The empty list says so and offers the way in.** Given a user with an empty list, when they open it, then it reads *"The list is empty."* with the hand-entry row directly beneath it and focused — never a bare panel. (FR-15, UX-DR13)

5. **Exactly one list, and no list management.** Given the app, when a user looks for list management, then there is exactly one list per user and no surface anywhere for creating, naming, switching or deleting lists. (FR-14)

6. **Scoped to the user, written like every other document.** Given the persistence layer, when the list is stored, then it is scoped to the authenticated username — never taken from request input — and every read-modify-write goes through the repository's atomic writer with `key_lock` held. (FR-2, NFR-1, NFR-5)

7. **The modal opens before the fetch lands.** Given a cold load, when the shopping-list button is tapped, then the modal opens immediately and shows a row skeleton; it never waits on the request. (EXPERIENCE § State Patterns)

8. **A failed write reverts and says so in place.** Given a hand-entry that fails to save, when the write rejects, then the row reverts and one line appears at the head of the modal — *"Couldn't save that — check your connection."* No toast. (EXPERIENCE § State Patterns)

9. **Escape and the backdrop close it.** Given the shopping list is open, when escape is pressed or the backdrop is clicked, then it closes — unlike a confirmation, which requires an explicit choice and must stay as it is. (UX-DR14)

10. **Items are ordinary editable text.** Given an item on the list, when it is stored, then it is free text with no parsing, no quantity field and no link back to a recipe or an ingredient category — so `chicken thighs` can later become `2 packs chicken thighs`. (FR-16)

### Completion Notes

- **Both of the story's open questions were resolved in the build, not deferred.** The button lives in the app, not the dock's `MainLayout` — the spec says every *KitchenCraft* screen, which is narrower. And hand-entry commits one item per submit; a multi-line paste stays one item, because no AC asks for the split.
- **`PageBar.vue` answers the "four copies" risk the story flagged.** It carries the title, a slot for the page's own action, the shopping-list button — and it owns the modal and its open flag. Putting the flag in each page would have been four copies of the same state, and the modal belongs with whichever screen opened it.
- **`RecipePage` gained a titleless bar.** It had none at all; the recipe name below is already that screen's heading, so a second title would be a duplicate. This is the visible change to an existing surface most worth a look in review.
- **The list is its own document** at `DATA_DIR/kitchencraft/shopping/{username}.json`, under its own lock keyed on its own path. A test asserts a recipe write does not touch it, and another asserts the collection file is not created by a shopping write.
- **`ticked` is in the schema but has no behaviour.** Story 3.2 fills it. A modal spec asserts the rows carry no checkbox and no button, so ticking cannot creep in here unnoticed.
- **The optimistic add uses a `pending-` id** replaced by the server's, and a spec asserts no provisional id survives into the loaded list. On failure the row is removed rather than left looking saved.
- **The empty state is a line of type above the always-present hand-entry row**, not a bare panel and not a button — the entry row *is* the way in (UX-DR13).
- Four page specs now assert the button is present. That is the cheapest guard against AC 1 rotting as screens are added, and it is deliberately a separate `describe` in each file rather than one shared test.

## Dev Notes

**The modal must not be a route.** Every other surface in this app is a route, and
this one cannot be: AC 2's whole content is that the screen behind survives
untouched, and a route remounts it. This is the decision most likely to be made
wrong by reflex.

**One list, no management surface.** FR-14 is unusually explicit that there is no
create, name, switch or delete. The absence is the feature; do not add an
affordance "for symmetry" with the rest of the app.

**Nothing about ticking, clearing or recipes belongs here.** Those are 3.2 and
3.3. `ticked` appears in the schema only so the document shape settles once.

### Open Questions

- **Does the button belong in the KitchenCraft pages or the dock's `MainLayout`?** The UX spec says "every KitchenCraft screen", which is narrower than every dock screen. Keeping it inside the app is the reading that matches "self-contained app code", but it is worth confirming before four pages grow the same button.
- **Should hand-entry accept several lines pasted at once?** Not specified. The lean reading is one item per commit; a paste of five lines becoming five items is a plausible convenience that no AC asks for, so it stays out unless you say otherwise.
