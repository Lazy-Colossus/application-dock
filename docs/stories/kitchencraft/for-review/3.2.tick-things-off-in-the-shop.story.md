# Story 3.2: Tick things off in the shop

## Status

Ready for Review

## Story

As a cook at the shop,
I want to cross off what I have already picked up,
so that I can see at a glance what is left.

## Context

Story 3.1 landed the list, the modal and hand-entry, and put `ticked` on the
schema with no behaviour attached. This story fills it in, and adds the two
removals: one item at a time, and the whole list behind a confirmation.

The context is a phone held one-handed while the other hand holds a basket. That
is what makes the whole row the tick target and what makes "stays in place" load-
bearing: a list that reorders under a thumb mid-aisle is worse than no list.

## Acceptance Criteria

1. **Tap the row to tick.** Given an item on the list, when its row is tapped, then it is struck through with a filled checkbox, and it **stays exactly where it was** — not removed, not reordered, not moved to a "done" group. (FR-15)

2. **Tap again to untick.** Given a ticked item, when it is tapped again, then it returns to unticked and the strike-through goes. (FR-15)

3. **The whole row is the target.** Given a phone held one-handed, when the user reaches for an item, then the tick target is the whole row at no less than the app's touch minimum — not a small checkbox the thumb has to find. (NFR-4, UX-DR17)

4. **Delete is a separate trailing target.** Given any item, ticked or not, when its delete control is used, then that item alone is removed, and using it never toggles the tick. (FR-15)

5. **Clear is behind a confirmation.** Given a list with items, when clear is chosen, then a confirmation is required first; on confirming the list is emptied, and on cancelling it is left exactly as it was. (FR-15)

6. **No clear on an empty list.** Given an empty list, when the modal renders, then there is no clear control — there is nothing to clear, and an empty-state screen offering a destructive action reads as a mistake.

7. **The mark is a shape change, not a colour.** Given a ticked item, when it renders, then it carries both a filled checkbox and a strike-through in ink — never moss, and never colour as the only signal. (UX-DR17)

8. **A failed write reverts the row.** Given a tick, an untick or a delete that fails to save, when the write rejects, then that row returns to exactly what it was and one line appears at the head of the modal. No toast. (EXPERIENCE § State Patterns)

9. **Ticks survive the shop.** Given a ticked item, when the page is refreshed or the list is opened on another device, then the tick is still there — it is server state, not a view flag. (FR-15, NFR-1)

10. **Announced, not just drawn.** Given any row, when a screen reader reaches it, then it announces the item and whether it is ticked, and the delete control is separately named for that item.

  - [x] A quiet clear control in the modal's bar, rendered only when the list has items.

- [x] **Task 5: Tests** (AC: 1–10)

  - [x] Store: each action is optimistic against a never-settling promise; each reverts on rejection; `clearList` restores every item including ticks; `loading` stays false throughout.
  - [x] Modal: tapping a row toggles; tapping delete removes without toggling; the strike-through and the checkbox both appear; clear is absent on an empty list; clear asks first; cancelling changes nothing.

### Completion Notes

- **Story 3.1's own guards caught this story twice, which is what they were for.** A backend test pinned the shopping route set and failed when `/items/{item_id}` arrived; it was widened to the real surface while keeping the guarantee that matters — no `{list_id}` in any path. And a modal spec asserted the rows carried no checkbox and no button; it was replaced by real coverage rather than deleted.
- **`DELETE /shopping-list/items` is declared before `DELETE /shopping-list/items/{item_id}`**, so "items" is never matched as an id. A test asserts clear works with a populated list, which would fail as a 404 if the order were reversed.
- **The row is a `kc-row__main` button with delete as a trailing sibling** — the `RecipeRow` shape, which is what makes "delete never toggles the tick" structural rather than a handler that remembers to stop propagation. A spec asserts deleting emits no PUT.
- **A failed delete restores the item to its index**, not to the end. Position is the order the cook shops in, so putting it back in the wrong place would be a quieter version of the reordering this story forbids.
- **`clearList` snapshots the array before emptying**, so a failed clear restores every item with its ticks intact. Asserted.
- **Ticking is optimistic and outside `loading`**, like every other write in this store. Three actions now share that shape; none of them re-sorts.
- Clear is absent on an empty list. An empty screen offering a destructive action reads as a mistake, and there is nothing to confirm.

## Dev Notes

**"Stays in place" is the whole story.** Every instinct — sorting ticked items to
the bottom, hiding them, animating them away — is wrong here and explicitly
ruled out by the UX spec. The list a cook reads in an aisle must be the list they
built, in that order, with marks on it.

**Delete must not be reachable by a mistimed tap meant for the row.** It is a
separate trailing target for that reason, and a test asserts using it emits no
toggle.

**Clear is destructive and has no undo**, like recipe delete. It gets the same
confirmation component and the same plainness — no "are you sure?" theatrics.
