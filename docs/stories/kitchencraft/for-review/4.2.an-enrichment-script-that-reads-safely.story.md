# Story 4.2: An enrichment script that reads safely and changes nothing

## Status

Ready for Review

## Story

As the builder,
I want a script that reads the live collection and reports what it would change,
so that I can trust it before I ever let it write.

## Acceptance Criteria

1. **It goes through the repository layer** — its atomic write path and its per-file locking — rather than reading or rewriting JSON itself. (FR-19, NFR-1)

2. **Reaching the data is documented for dev and for production**, with the runbook checked in beside the script. (FR-19)

3. **A run with no explicit write flag writes nothing and reports what it would have changed.** (FR-19)

4. **An unknown `schema_version`, or a document that fails validation, stops the run** — non-zero, having changed nothing, saying what it found. (FR-19, NFR-3)

5. **A pass takes the same lock the app takes**, so neither a torn read nor a lost concurrent edit is possible. (FR-19, NFR-1)

### Completion Notes

- **No LLM integration was added, and none was needed.** The epic calls this an "LLM-assisted pass", which reads like an API client is required. It is not: the architecture decision is a script *driven from Claude Code*. The script reports, the agent infers, the script applies. No `anthropic` dependency, no API key, no model id enters the codebase. This was checked against the epic's own architecture note rather than assumed.
- **The dry run and the real run share `_apply_batch`.** A dry run using different code would be worth very little — it would describe a run that never happens. The only difference is whether the document was read inside a transaction that writes on exit.
- **AC 5 is satisfied by *where the script runs*, not by anything in the script.** `key_lock` is process-local, so the lock is only shared when the script runs inside the container alongside the app's workers. That is why the decision record exists and why the runbook leads with it rather than burying it.
- **The document is read once up front**, and a failure there aborts before any command runs. A half-understood document is not something to write back (NFR-3).
- **AC 1 is tested structurally**, by spying on `repo.doc_transaction`, rather than by trusting that the service happens to use it.
- Three exit codes, documented: `0` fine, `1` ran but a batch named an unknown id, `2` refused to run or the batch was malformed.

## Dev Notes

The runbook uses `docker compose cp` for **the report and the batch only**, never
for the data document. Copying the document out, editing it and copying it back
is not a read-modify-write under lock and would silently discard anything the app
wrote in between — the exact failure this story's AC 5 exists to prevent.
