# Story 2.1: Optional meal type, time, servings and source

## Status

Ready for Review

## Story

As a cook,
I want to record a few facts about a recipe when I feel like it,
so that I can later narrow my collection down to what fits tonight.

## Acceptance Criteria

1. **Each field set and cleared independently.** Given a recipe, when it is edited, then meal type (breakfast / lunch / dinner / snack / dessert / other), total time in minutes, servings and source can each be set and cleared independently, and clearing one leaves the others untouched. (FR-6)

2. **Numbers validated at the field.** Given a non-numeric or non-positive time or servings, when it is entered, then it is rejected at the field rather than at save, and the API rejects it with `{ detail }` if it arrives anyway. (FR-6)

3. **Absence renders as absence.** Given a recipe with none of these fields set, when it is displayed in the list or opened, then the missing fields are absent from the layout entirely — no "unknown" placeholders, no gaps implying the recipe is unfinished. (NFR-8)

### Completion Notes

- **Numbers are held as text on purpose.** Binding `v-model.number` to an `<input type="number">` would let the browser silently discard `4o`, leaving the user staring at an empty box with no explanation. Keeping the raw string means the field shows what they typed *and* why it is not a number yet — which is what "rejected at the field, not at save" actually requires (UX-DR15). A spec asserts the typed `4o` is still in the field.
- **Save is blocked while a field error stands.** UX-DR15 says "rejected on entry"; filtering keystrokes to digits was the alternative and reads as a broken keyboard. So: the message appears immediately, and Save is disabled with the reason already on screen. Not strictly "rejected on entry" — flagging it as the judgement call in this story.
- **Meal type is single-select**, and this is also what the filter does (Story 2.5). A recipe has one meal type; multi-select would let you build a guaranteed-empty state. Flow 5's "one selection or none" supports it.
- **The two numeric fields are unconstrained in the pydantic schema and checked in the service**, so `servings: 0` comes back as `{"detail": "servings must be a positive whole number"}` rather than pydantic's error array. AC 2 asks for `{ detail }`, and a test asserts `isinstance(detail, str)`. A non-*numeric* value still returns FastAPI's standard array — that is the platform-wide behaviour for every typed field in every dock app, and the frontend never sends one.
- **The absence rule is implemented as one helper returning `null`**, not as a template full of `v-if`s over four fields. `metaLine` and `metaParts` are the only places that decide, and specs assert no dash, "unknown", or dangling `·` can appear.
- **The contrast guard is real, not a comment.** `kitchencraft.tokens.spec.ts` reads the shipped `.sass` off disk, computes WCAG ratios from the declared hex values, and fails if `taupe` ever carries text (3.17:1) or `ink` lands on a moss fill (3.09:1). It also asserts the ink-on-moss ratio *still fails*, so a palette edit that made it pass would surface as a deliberate decision rather than silently.

## Dev Notes

**Meal types are verbatim from PRD FR-4 and are never re-worded, re-cased or re-ordered** ([Source: EXPERIENCE.md § Voice and Tone]). Render the array as-is.

**Validation happens at the field, not at save** ([Source: UX-DR15]): non-numeric time or servings is rejected on entry; a rejected save names which field is empty. Zero and negatives are rejected the same way; **empty is always valid**.

**The absence rule is the single most load-bearing behaviour in the app** ([Source: EXPERIENCE.md § The absence rule]). An empty field is not a gap, a placeholder, a dash, an "unknown", a greyed chip or a labelled empty slot. Nothing counts how much structure a recipe has.

**Contrast is measured, not assumed** ([Source: UX-DR4]): `ink` on moss is 3.09:1 and **fails**; text on a moss fill is `on-moss`. `taupe` is non-text only; quiet text is `taupe-ink`. This "needs a guard — a test or lint rule — not just a note".
