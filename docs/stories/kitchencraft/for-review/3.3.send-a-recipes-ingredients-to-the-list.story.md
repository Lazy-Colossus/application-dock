# Story 3.3: Send a recipe's ingredients to the list

## Status

> **AMENDED 2026-09-15 by Story 2.8.** AC 1's "specific where one exists, category
> where it does not" is void — an ingredient now reads as amount + unit + name, and
> the modal shows that line. The staple match moved from the category to the full
> text, and its open question about adjective specifics (`smoked`) is closed: the
> new model carries the quantity, so the list receives `2 tsp smoked paprika`.

Ready for Review

## Story

As a cook planning the week,
I want to push a recipe's ingredients onto my shopping list,
so that I can buy what I need without copying it out by hand.

## Context

Stories 3.1 and 3.2 built the list and the marks on it. This is the first thing
that fills it from somewhere other than the user's own typing.

Adding here is always a plain append. The add-versus-overwrite prompt for a list
that already has items is Story 3.4, and must not be anticipated here.

## Acceptance Criteria

1. **One checkbox per ingredient.** Given a recipe with ingredient tags, when "Add to shopping list" is chosen, then a modal lists one checkbox per ingredient, showing the **specific where one exists** and the bare category where it does not — the same rule the reading view follows. (FR-16, FR-7)

2. **Everything checked except the staples.** Given that modal, when it opens, then every ingredient is checked **except salt and black pepper**, which start unchecked and can be checked by the user. (FR-16)

3. **`pepper` is not a staple.** Given a recipe calling for `pepper` — the vegetable, which is its own category in the shipped vocabulary — when the modal opens, then it is checked like any other ingredient. Only `salt` and `black pepper` start unchecked.

4. **Nothing checked is a silent no-op.** Given the modal with nothing checked, when it is confirmed, then nothing is added, the modal simply closes, and there is no message and no post-add confirmation. (FR-16)

5. **Items arrive as ordinary text.** Given a confirmed add, when the items land on the list, then they are plain editable text carrying no link back to the recipe or the ingredient category — so `chicken thighs` can later be amended to `2 packs chicken thighs`. (FR-16)

6. **A recipe with nothing to send says so.** Given a recipe with no ingredient tags, when "Add to shopping list" is chosen, then it reads *"Nothing to send yet — this recipe has no ingredients listed."* with one line beneath — *"Add some on the edit screen and they can go to the list."* — and a quiet **Edit recipe**. No empty checkbox list. (FR-16)

7. **Told what happened, and left where they are.** Given a successful add, when it completes, then the user is told **how many items were added**, is offered a way through to the shopping list, is equally free to stay on the recipe, and is **never navigated automatically**. (FR-18)

8. **One write, not one per ingredient.** Given a confirmed add of several ingredients, when it reaches the server, then it is a single request and a single atomic write under one lock — not one request per checkbox. (NFR-1)

9. **Always an append, in checkbox order.** Given a list that already has items, when ingredients are added, then they are appended to the end in the order they appeared in the modal. The add-versus-overwrite prompt is Story 3.4 and does not exist yet.

10. **A failed add changes nothing.** Given a confirmed add that fails to save, when the write rejects, then no item appears on the list and the failure is reported the way every other write failure is.

### Completion Notes

- **The `pepper` trap is real and guarded.** The shipped vocabulary carries `pepper` (the vegetable), `salt` and `black pepper` as three separate categories. A substring or `includes` match against the staples would silently uncheck `pepper` and the cook would buy none. The match is exact, on the category, case-insensitively, with a test naming the trap.
- **The batch is one request and one write.** A backend test spies on `write_shopping_list` and asserts it is called exactly once for a four-item batch, so N ingredients cannot regress into N transactions.
- **The shopping list's open flag moved from `PageBar` into the store.** The bar is no longer the only thing that opens the list — "View list" after an add does too — and two components owning the same flag would be two sources of truth.
- **"View list" replaces this modal rather than stacking on it**: it closes the add modal and opens the list, which keeps modal depth at one level.
- **Nothing navigates automatically.** A test asserts that after a successful add the modal has emitted no `close` and the list is not open; the user reaches both only by choosing them.
- **The route-surface guard from 3.1 fired again** when `/items/bulk` arrived and was widened. `bulk` is declared before the parameterised routes so it is never read as an item id, with a test that would fail as a 404 if that order were reversed.
- Story 3.4's concerns were kept out deliberately: adding is a plain append, and the same text twice is two items. A backend test pins that so the merge cannot arrive early.

## Dev Notes

**The staple match is on category and must be exact.** `pepper` is a separate
category in the shipped vocabulary — the vegetable. A substring or `includes`
match would silently uncheck it, and the user would buy no peppers.

**"Never navigated automatically" is the point of AC 7.** The cook is reading a
recipe; the add is an errand, not a destination. Offer the way through, do not
take it for them.

**Adding is a plain append here.** Everything about a non-empty list — the
prompt, the overwrite, the case-insensitive dedupe — is Story 3.4.

### Open Questions

- **"Show the specific where one exists" produces poor shopping-list entries when the specific is an adjective.** Implemented exactly as FR-16 and AC 1 require, and a live run against the seeded collection shows the cost: `paprika` → `smoked` sends **"smoked"** to the list, and `chilli` → `dried` sends **"dried"**. Neither means anything in a shop. `chicken` → `thighs` sends **"thighs"**, which is weak for the same reason. The rule is right whenever the specific is a noun (`feta`, `new potatoes`, `red onion`) and wrong whenever it is a modifier, and nothing in the data distinguishes the two. Worth a decision: leave it (the user edits the text on the list, which FR-16 explicitly allows), or send `specific + category` where the specific does not already contain the category — which would give `smoked paprika` and `chicken thighs` but also `new potatoes potato`. **Not changed here**, because AC 1 is unambiguous and this needs a ruling, not a guess.
- **The staples list is not configurable**, and EXPERIENCE.md lists "a configurable staples list" as explicitly not-in-v1. Hard-coded in the modal with a test; if it ever needs to move server-side it should move with a story, not by accident.
