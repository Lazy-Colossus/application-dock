# Story 1.3: Capture a recipe from a name and pasted text

## Status

Ready for Review

## Story

As a cook,
I want to save a recipe by giving it a name and pasting the text,
so that I can keep something I found without filling in a form.

## Acceptance Criteria

1. **Fast open.** Given the capture screen, when it opens, then focus is in the body text area, and a paste-plus-save completes in no more than three interactions. (NFR-7)

2. **A name and a body are enough.** Given a name and a body and no other field, when the recipe is saved, then it persists and appears in the collection; no other field is required and none blocks saving. (FR-3)

3. **Rejection names the field.** Given an empty name, or an empty body, when a save is attempted, then it is rejected and the message names which one is missing — and no other validation can block a save. (FR-3)

4. **The verbatim body contract.** Given a body pasted with mixed bullet characters, blank lines and site boilerplate, when it is saved and read back, then it is byte-identical apart from trimmed leading/trailing whitespace; internal line breaks and blank lines survive exactly. (FR-5, NFR-3)

5. **HTTP boundary and store discipline.** Given the frontend, when it talks to the API, then it does so only through `useApi`, and the Pinia store exposes `loading` / `error`, setting `loading` in a `try/finally` and routing failures into `error.value`.

### Completion Notes

- **The name reads first; the body takes focus.** The recipe name is the top field on the page, and the body textarea below it holds focus on open, so the flow is paste → tap up to the name → Save: three interactions (NFR-7). This matches Flow 1's own beat sheet, which says "she taps **up** to the name field" — i.e. the name sits above the body. Two specs pin it: one asserts the field order, one asserts focus still lands in the body despite that order, so neither can regress silently.
- **Only two things can reject a save, on both sides of the wire.** The capture screen sends exactly `{ name, body }` — a spec asserts the payload keys — so no optional field can appear between a paste and a saved recipe.
- **Trim at the ends only.** `create_recipe` does `name.strip()` / `body.strip()` and nothing else: no bullet normalisation, no list detection, no blank-run collapsing. The backend test asserts the mixed bullets (`-`, `*`, `•`, `–`), the shouted `ONION`, the `\n\n\n` run and the trailing `Print Recipe` all survive.
- **Copy is verbatim from the spine.** Initially written with `&rsquo;` entities, which render as a curly apostrophe and failed the assertions against the spine's straight-quoted strings; the templates now carry the straight apostrophe so the shipped copy matches the spec character for character.
- On success the user lands back on the **collection**, per Flow 1's climax ("the collection reappears with `pumpkin dal` at the top"), not on the new recipe.
- `createRecipe` rethrows *and* sets `error` — the screen needs to know it failed in order to keep the paste on screen, and the store still owns the message.

## Dev Notes

**The verbatim body contract is the app's whole point** ([Source: EXPERIENCE.md § The verbatim body contract]). Nothing may reformat, re-wrap, normalise bullets, detect lists or render markdown. On save, **only leading and trailing whitespace is trimmed**.

**All HTTP through `src/composables/useApi.ts`** — no raw `fetch`/`axios` in components or stores. It throws `ApiError` with `.status` and `.detail`.

**Pinia contract** (CLAUDE.md): stores expose `loading` and `error`; every async action sets `loading` in a `try/finally` and routes errors into `error.value`, never a bare `console.error`.

**Validation copy is specified verbatim** ([Source: EXPERIENCE.md § State Patterns → Capture]) — do not paraphrase, and do not add an exclamation mark.
