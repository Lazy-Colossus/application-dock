# Story 2.2: Free tags with suggestions

## Status

Ready for Review

## Story

As a cook,
I want to label recipes with my own words,
so that I can group them the way I actually think about them.

## Acceptance Criteria

1. **Existing tags offered first.** Given the tag input, when the user types, then tags already present elsewhere in their collection are offered before a new one is created. (FR-9)

2. **Casing converges.** Given tags entered as `Chicken` and `chicken`, when they are stored, then they resolve to a single normalised tag; the two never coexist as separate tags. (FR-9)

3. **A new tag is still accepted.** Given a value that matches nothing existing, when the user commits it, then it is accepted as a new tag. (FR-9)

### Completion Notes

- **The vocabulary is derived on read, not indexed.** `_tag_vocabulary` walks the recipes each time. At personal scale the walk is free, and an index is one more thing that can fall out of step with the recipes it describes. A test asserts that removing a tag from its last recipe removes it from the vocabulary — which an index would have to be told to do.
- **First casing in wins.** `_resolve_casing` returns the casing already in the vocabulary; a new value keeps what was typed. So `chicken` then `Chicken` yields one `chicken`, and there is no separate canonicalisation table to maintain.
- **On update, the fold runs against the *other* recipes' tags.** Folding against a vocabulary that still contains this recipe's own old value would let a recipe pin its own casing forever and make deliberate re-casing impossible.
- **The typeahead is one component with a namespace prop**, shared with Ingredients (Story 2.3). The namespace wall (FR-8) is therefore structural: the two fields pass two different lists and share nothing else. `TagsField` passes `allowCoin: false`, which is the whole behavioural difference — a free tag needs no ceremony; coining is reserved for ingredient categories, which the pantry filter depends on.
- **Arrow-Up from nothing highlighted goes to the *last* row**, not the first. Found while writing the spec: the original modulo arithmetic landed on row 0 from `-1` in both directions. Fixing it means one press of Up reaches the new-category row at the foot of the Ingredients list — a real improvement, not just a test fix.
- Suggestion ordering is most-used-first, which the spine marks `[ASSUMPTION]` since the PRD does not order suggestions. `orderByUsage` keeps vocabulary order as the tiebreak.

## Dev Notes

**Typeahead behaviour** ([Source: UX-DR6]): suggests from its own namespace **only**; case-insensitive match on any substring (`chi` offers `chicken` and `chickpeas`); existing values always rank above the new-category row; six suggestions then scroll; **no spinner** — the namespace is already loaded. The highlighted row takes a moss focus ring, **never a fill**.

**Vocabulary converges on one casing** ([Source: FR-9]) — `Chicken` and `chicken` must never coexist.

**Tags and Ingredients never share a namespace** ([Source: FR-8]) — a value typed into one never lands in the other's.

### Project Structure Notes

- `TypeaheadInput.vue` is shared by `TagsField` and `IngredientsField`; it holds no knowledge of either namespace, only of the list it is handed.
- Built from native elements rather than Quasar inputs: every visual is bespoke in the token layer, and the repo's vitest setup stubs Quasar components globally, so native markup keeps the specs meaningful.
