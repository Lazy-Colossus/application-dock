# Story 2.5: Filter by meal type, tag and pantry ingredients

## Status

> **PARTLY SUPERSEDED 2026-09-15 by Story 2.8.** The **pantry-ingredient half was
> removed** with the category vocabulary. Meal type and tag filtering, the
> combining rule, the visible result count and the zero-result state all still
> stand and are still built.

Ready for Review

## Story

As a cook deciding what to make,
I want to narrow my collection by what kind of meal it is and what I have in the house,
so that I can pick something without reading every recipe.

## Acceptance Criteria

1. **AND across ingredient categories.** Given two ingredient categories selected, when the list is filtered, then only recipes carrying both categories are shown, regardless of what else those recipes require. (FR-12)

2. **Matching is on category, never on specific.** Given a recipe tagged `cheese` → `feta`, when the user selects the `cheese` category, then the recipe matches. (FR-7, FR-12)

3. **Filters combine and clear individually.** Given filters of different kinds, when several are active, then meal type, tags and ingredients combine, each is individually clearable, and the number of matching recipes is visible. (FR-12)

4. **Zero results offer to clear.** Given a filter combination that matches nothing, when it is applied, then the empty state offers to clear the filters. (FR-12)

5. **Nothing implies completeness.** Given any pantry filter result, when it is presented, then no wording implies the user can fully cook the listed recipes — the filter matches ingredients, it does not check completeness. (FR-12)

### Completion Notes

- **Meal type is single-select, deliberately diverging from "AND within a kind".** `EXPERIENCE.md § Filter bar: Active` says AND applies "across kinds and within a kind", but a recipe holds exactly one meal type, so ANDing two meal types could only ever return zero — a state the UI would let the user build and then have to explain. Tapping another replaces it; tapping the selected one clears it. **This is the one place the implementation reads against the letter of the spine, and it is the thing most worth a second opinion in review.** AND semantics are honoured in full for tags and ingredients, where values genuinely accumulate.
- **UX-DR11 is enforced by tests, not just by careful writing.** Two negative assertions — one in the composable spec, one across the whole collection page — fail if `can make`, `can cook`, `you have`, `tonight`, `%`, `complete`, `fridge` or `pantry` ever appears. The wording *is* the requirement here, because the PRD's counter-metric is the user ceasing to trust the filter.
- **The pantry filter defaults to categories in use.** Opening on all 105 shipped categories would be a wall of chips, and filtering by one nothing calls for can only return zero. Flow 2 says the filter "opens on the seeded category vocabulary plus everything his collection has accrued", so the full list sits one quiet tap away behind "Show every category". Reading this as a reasonable middle rather than a contradiction — worth confirming.
- **`reasons` counts each filter alone**, which is the whole point of UX-DR12: two categories that match one recipe together each report their own larger count, so the user learns *which* filter is doing the excluding. A test pins that the combined count and the individual counts differ.
- **Favourites-only on its own gets its own reading** (*"7 favourites"*) and its own empty state; combined with anything else it falls back to the zero-result breakdown, because "No favourites yet." would be a lie when the meal-type filter is what excluded them.
- The disclosure buttons are `<button>` elements styled as `label-caps`, so the section labels stay screen-reader-navigable with `aria-expanded` rather than being decorative text with a click handler.

## Dev Notes

**The pantry filter never implies completeness** ([Source: UX-DR11; EXPERIENCE.md § The pantry filter never implies completeness]). The verb is always *call for* or *use*. Write *"6 of 42 recipes call for chicken + onion"*, never *"6 recipes you can make"*. The filter's own label is **Ingredients**, never "What's in my fridge". No match percentage, no "2 of 9 ingredients" ratio, no completeness bar, no tick, no sort by closeness to cookable. See the write-this/never-this table in the spine.

**The zero-result state explains why** ([Source: UX-DR12]) — each active filter with its own count, each line clearing that one filter.

**Filters are additive and independently clearable** ([Source: EXPERIENCE.md § Interaction Primitives]) — "Nothing clears anything else."

**A chip that is a control takes moss when selected; a chip merely displaying a value never does** ([Source: UX-DR5]).

**Colour is never the sole signal** ([Source: UX-DR17]) — every moss control states its state in its accessible name, and the visible result count changes with it.
