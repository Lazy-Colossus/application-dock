# Story 3.4: Adding to a list that already has items

## Status

Ready for Review

## Story

As a cook,
I want to decide whether new ingredients join my existing list or replace it,
so that I never lose a list I was still shopping from.

## Context

The last story of Epic 3, and the only one that can destroy something the user
built. Story 3.3 made adding a plain append; this makes it a decision — but only
when there is something to lose.

## Acceptance Criteria

1. **An empty list is never interrupted.** Given an empty shopping list, when a recipe's ingredients are added, then they are added silently — no prompt, no question, no extra tap. (FR-17)

2. **A non-empty list asks.** Given a list that already holds items, when a recipe's ingredients are added, then the user is asked, with the count named: *"The list already has {n} items."* Primary **Add to the list**, danger **Replace the list**, quiet **Cancel**. (FR-17)

3. **Add merges without duplicating.** Given the user chooses add, when the items are merged, then an item already on the list is not added again, matched case-insensitively. (FR-17)

4. **The count reported is what actually landed.** Given a merge that skipped duplicates, when the result is reported, then it names the number of items genuinely added, not the number sent. (FR-18)

5. **Overwrite asks a second time.** Given the user chooses replace, when they choose it, then a **second, explicit confirmation** is required before anything is discarded. (FR-17)

6. **The second confirmation replaces the prompt in place.** Given the overwrite confirmation, when it appears, then it **replaces** the add-vs-overwrite prompt rather than layering on top of it — the single stated exception to modals stacking one level deep. (UX-DR14)

7. **Overwrite discards everything, ticks included.** Given the user confirms the overwrite, when it completes, then the previous contents are gone — ticked items too — and the list holds exactly what was sent. (FR-17)

8. **Cancelling changes nothing.** Given either prompt, when the user cancels, then the list is exactly as it was: same items, same order, same ticks, and no request was made. (FR-17)

9. **One write, whichever path.** Given a merge or an overwrite, when it reaches the server, then it is a single request and a single atomic write under one lock. (NFR-1)

10. **Hand-entry is untouched.** Given the user types an item by hand that already exists on the list, when it is committed, then it is added as a second item. De-duplication belongs to the recipe merge, not to typing: a cook who types `milk` twice may well want two.

## Tasks / Subtasks

- [x] **Task 1: Backend** (AC: 3, 4, 7, 9)
  - [x] `AddShoppingItemsRequest` gains `mode: "merge" | "overwrite"`, defaulting to `merge`.
  - [x] `merge` skips any text already on the list **and** any repeated within the batch, case-insensitively; returns only the items actually created, so the caller can report an honest count.
  - [x] `overwrite` discards every existing item, ticked included, and writes the batch.
  - [x] Both run in one `shopping_transaction`.
  - [x] `POST /shopping-list/items` (hand-entry) is left alone — it still never de-duplicates.
- [x] **Task 2: Frontend — the store** (AC: 3, 4, 7, 8)
  - [x] `addItems(texts, mode)`; `mode` reaches the request unchanged.
  - [x] Optimistic as before, reverting the whole batch on failure. For an overwrite the revert must restore the **previous list**, ticks included.
- [x] **Task 3: Frontend — the prompt** (AC: 1, 2, 5, 6, 8)
  - [x] `AddToListModal` grows a step between the checkboxes and the result, shown **only** when the list is non-empty.
  - [x] The overwrite confirmation replaces the prompt in place — same modal, different content — never a stacked `ConfirmModal`.
  - [x] Cancel from either step returns to the checkbox list with the selection intact, so the user can adjust rather than start again.
  - [x] The list must be loaded before the modal can know whether to ask: fetch it on open if it has not been fetched.
- [x] **Task 4: Tests** (AC: 1–10)
  - [x] Backend: merge skips existing case-insensitively; merge skips within-batch repeats; merge returns only what it created; overwrite discards ticked items; overwrite on an empty list is a plain add; both are one write; hand-entry still duplicates freely.
  - [x] Store: mode reaches the request; an overwrite that fails restores the previous list with its ticks.
  - [x] Modal: no prompt on an empty list; the prompt names the count; add merges; replace asks again; the second confirmation replaces rather than stacks; cancel from either step makes no request and keeps the selection.

### Completion Notes

- **The count became honest, and that caught a weak test.** `addItems` now returns what the *server* created rather than what was sent. Two existing 3.3 specs had been mocking an empty response and still asserting a count of 3 — they were passing on a number the component made up. Both were corrected, and the modal spec's mock now echoes what it was given.
- **Merge de-duplicates against the list *and* within the batch**, so the result can never hold a case-insensitive duplicate whichever way one arrives. A ticked duplicate is left ticked rather than revived as a fresh unticked row — asserted, because that is the version a cook would notice mid-shop.
- **`mode` defaults to `merge`** on the schema, deliberately: a caller that forgets to choose should not be the one that empties a list.
- **The overwrite confirmation is not a `ConfirmModal`.** UX-DR14's single stated exception says it *replaces* the add-vs-overwrite prompt rather than stacking, and `ConfirmModal` renders its own backdrop. A spec asserts exactly one `[role="dialog"]` and no `confirm-backdrop`, so a well-meaning refactor toward the shared component would fail.
- **Cancel returns to the checkboxes with the selection intact.** The ACs only require the list to be unchanged; where the user lands was a judgement call. A test unchecks an ingredient first, so it proves the selection survives rather than merely that the step changed.
- **An empty overwrite empties the list** — `mode: overwrite` with no texts is the one path where a blank batch is not a no-op. Guarded on both sides.
- **The optimistic view mirrors the server's merge** rather than guessing differently: a provisional row is skipped for anything already on the list, case-insensitively, so the list does not flash a duplicate that then vanishes.
- Hand-entry is untouched and still duplicates freely. A test pins that, because the merge rule sits one function away and would be easy to generalise by accident.

## Dev Notes

**Cancel returns to the checkboxes, not out of the modal.** The acceptance
criteria only require that the list is unchanged; where the user lands is a
judgement call. Returning to the selection they had built is the kinder answer —
cancelling a question about *how* to add should not throw away *what* they chose
to add.

**The count must be honest.** A merge that sends six and adds four has to say
four. Reporting six would be a small lie that the user can immediately catch by
looking at the list.

**Overwrite is the only destructive act in Epic 3 that is not behind
`ConfirmModal`** — because UX-DR14's one stated exception says this confirmation
*replaces* the prompt rather than stacking on it, and `ConfirmModal` renders its
own backdrop.
