# Story 1.4: Browse the collection

## Status

Ready for Review

## Story

As a cook,
I want to see all my recipes in one scannable list,
so that I can find the one I want to cook.

## Acceptance Criteria

1. **Scannable list, newest first.** Given a collection with recipes, when the collection screen renders, then recipes are listed creation-date descending, each showing its name. The optional meal type and total time arrive with Story 2.1 and are surfaced in this list at that point. (FR-10)

2. **Empty collection prompts.** Given a user with no recipes, when the collection screen renders, then it prompts them to capture their first recipe rather than showing a blank screen. (FR-10)

3. **Per-user isolation.** Given two different authenticated users, when each opens the collection, then neither sees any recipe belonging to the other. (FR-2, NFR-5)

4. **Date ordering only.** Given this story, when ordering is implemented, then it sorts by creation date only — favourites-first ordering arrives with Story 2.6 and is explicitly out of scope here.

### Completion Notes

- **The whole collection is loaded once, bodies and all.** Search and filtering are client-side over the loaded collection (NFR-6), and full-text search needs the bodies anyway, so a projection would have to be undone in Story 2.4.
- **AC 4 was honoured in the story, then superseded in the same pass.** `_collection_order` was written favourites-first from the outset because Story 2.6 landed alongside; the date-only leg is what this story owns, and the backend test for it (`test_the_collection_is_newest_first`) passes because no recipe in that fixture is favourited. Story 2.6 carries the favourites-first assertions.
- **Ordering is duplicated deliberately, once per side.** The server sorts, and `format.ts` `sortRecipes` mirrors it, so toggling a favourite re-orders the loaded list without a refetch and without moving the scroll position (Story 2.6). A spec asserts `sortRecipes` does not mutate its input.
- The index tiebreak in `_collection_order` is not cosmetic: without it, two recipes with identical `created_at` strings fall back to stable-sort insertion order, which is *ascending* — the opposite of what the row order should be.
- `loaded` (not `loading`) gates the empty state, so a failed first fetch shows the error line rather than "No recipes yet."

## Dev Notes

**Empty states are never a bare panel** ([Source: EXPERIENCE.md § State Patterns]): type, rule and spacing carry them, and the copy is specified verbatim. The empty collection deliberately shows **no** search field and **no** filter bar.

**Recipe row visuals** ([Source: DESIGN.md § Components → Recipe row]): transparent background, 1px taupe rule below, 64px minimum, name in `body`/ink, no card and no chevron.

**Client-side filtering is sanctioned** ([Source: epics NFR-6]) — "search and filter stay instant at personal scale (hundreds of recipes); client-side filtering over the loaded collection is acceptable."

**Per-user scoping comes from the JWT** — the username is never taken from request input.
