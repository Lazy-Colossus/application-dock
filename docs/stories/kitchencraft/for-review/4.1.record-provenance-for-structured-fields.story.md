# Story 4.1: Record provenance for structured fields

## Status

Ready for Review

## Story

As the builder,
I want to know which structured values a user set by hand and which a machine inferred,
so that an enrichment pass can fill gaps without ever overwriting a deliberate choice.

## Acceptance Criteria

1. **Both carried decisions are recorded in writing, before implementation.** The provenance mechanism and the means of reaching the data volume from the host are both written down first — these are the decisions the rest of Epic 4 depends on. (PRD §8)

2. **Origin is recorded and survives a round trip.** A structured field or tag carries its origin, and the record survives a read-write cycle. (FR-21)

3. **A user edit marks the field user-set, whatever it was before.** (FR-21)

4. **Recipes predating this story default to user-set** — the safe default, since the only writer so far has been the user. (FR-21, NFR-3)

### Completion Notes

- **The decision record is the deliverable of AC 1**, and it closes both of the PRD's carried open questions. It is at `docs/planning-artifacts/architectures/kitchencraft-enrichment-2026-09-15.md`.
- **Provenance keeps the shipped shape.** `unconfirmed: list[str]` has been on `Recipe` since Story 1.2; the decision here was to confirm it rather than replace it, with the three rejected alternatives written down — a parallel `machine_set` object, a separate provenance document, and per-field `{value, origin}` wrappers.
- **The shape records the exception, not the rule.** `unconfirmed` lists machine-set keys; absence means user-set. That is why **AC 4 needs no migration at all** — an untouched recipe carries `[]`, which already means "all of this is the user's", and is true.
- **`_drop_marks` already satisfied AC 3** and was left alone. What was missing was anything that *writes* a mark, which is Story 4.3's job.
- **The rating is outside the mechanism entirely**: never marked, never written by a pass. It is a judgement only the cook can make (Story 2.7), and a test pins that a batch containing `rating` does not apply it.

## Dev Notes

The second decision — running **inside the container** — is not a convenience.
`key_lock` is a process-local registry, so a host-side process and the app's
workers would not contend at all. Story 4.2's AC 5 ("it takes the same lock the
app takes") is only satisfiable in-process, which makes this decision a
prerequisite rather than a deployment detail.
