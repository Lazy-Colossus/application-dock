# Story 1.2: Per-user recipe store — repository, schemas, service

## Status

Ready for Review

## Story

As the platform,
I want a JSON file per user with an atomic-write repository and typed schemas,
so that every user's recipes are stored, isolated and safe from concurrent writes.

## Acceptance Criteria

1. **Empty document on first read.** Given `repositories/kitchencraft_repo.py`, when a user's document is read and they have no file yet, then it returns an empty document (`{ schema_version, recipes: [] }`) rather than erroring; the repo is the only module touching the filesystem, and every write goes through the shared atomic writer with `key_lock` held across each read-modify-write. (NFR-1, NFR-2)

2. **Recipe schema with a stable id.** Given `schemas/kitchencraft.py`, when models are defined, then a `Recipe` carries a stable id (`r-` + `{uuid8}`), `name`, `body`, ISO-8601 `created_at` and `updated_at`, and nullable structured fields; the top-level document carries `schema_version` and a `migrate()` runs on read so later schema bumps are handled.

3. **Path safety and no user in the payload.** Given the per-user filename, when it is derived from the authenticated username, then it is validated as a bare filename so a crafted username cannot escape the app's directory, and no `user` field is accepted in any request path or body. (FR-2, NFR-5)

4. **Layering holds.** Given the service layer, when it operates on the document, then it raises stdlib exceptions (`FileNotFoundError` for an unknown recipe, `ValueError` for invalid input) and never raises `HTTPException`; the router performs that translation. (NFR-2)

### Completion Notes

**Three architecture gaps from the epic were closed here.**

1. **Stable recipe id** (Gap 1): `r-` + `uuid4().hex[:8]`, minted rather than derived, so it survives a rename — Epic 4 addresses recipes by id and never by name (FR-20). Mirrors the Context-Switch `l-`/`t-` convention.
2. **Vocabulary storage** (Gap 2): the shipped seed is a committed read-only file (`app/kitchencraft_seed/`, Hotaru precedent), and a user's *coined* categories live in their own document as `KitchencraftDoc.categories`. The effective vocabulary is seed ∪ coined ∪ in-use, unioned on read. **No separate index file** — at personal scale the walk is free, and an index is one more thing that can drift from the recipes.
3. **Per-field provenance** (Gap 3): one uniform mechanism, `Recipe.unconfirmed: list[str]`, holding keys like `"meal_type"` or `"tag:cheap"`. The schema lands here as the epic directs; the UI treatment is Epic 4's Story 4.1, so **nothing writes into it yet** — an update only drops keys it invalidates.

**`migrate()` rejects an unknown future version** rather than passing it through, unlike the Context-Switch pass-through. The body is the irreplaceable asset (NFR-3): reading a newer shape and writing it back could silently drop fields.

**Partial updates need a sentinel.** `UpdateRecipeRequest` is all-optional and the router passes `model_dump(exclude_unset=True)`, so an explicit `null` clears a field and an absent key leaves it alone — the distinction FR-6 needs, and what keeps a meal-type edit from touching the body.

`total_time_minutes` and `servings` are deliberately **unconstrained in the schema** and checked in the service, so a bad value reaches the client as a `{ detail }` string rather than pydantic's error array.

## Dev Notes

**Strict 3-layer, never skip a layer** (CLAUDE.md → Architecture): `routers/` HTTP only, `services/` business logic raising stdlib exceptions, `repositories/` the only code touching the filesystem.

**Reuse the shared primitives, do not re-implement them:** `app/core/storage.atomic_write_json` (unique temp file per write) and `app/core/locks.key_lock` (per-path reentrant lock). Story 1.8 consolidated three drifted copies of the atomic writer — do not add a fourth.

**Locking is in-process and that is correct here** — production runs one uvicorn with no `--workers`. See the module docstring in `app/core/locks.py` for when that stops being true.

**Tests** use `tmp_path` + `monkeypatch` on `settings.data_dir`; `settings.data_dir.mkdir()` runs at import time, which is why the fixture patches the settings object rather than the env var.
