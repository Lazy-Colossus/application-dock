# Story 2.2: Live propagation over SSE

## Status

Draft

## Story

**As** a member of a note,
**I want** other members' changes to appear on my screen while I have the note open,
**so that** we are looking at the same scratchpad in real time.

## Acceptance Criteria

1. **Authenticated stream.** Given `GET /api/shared-notes/notes/{note_id}/events?token=…`, when a member connects (token in the query because `EventSource` cannot send an `Authorization` header), then it opens a `text/event-stream`; a bad/absent token is `401` and a non-member is `404` (same as a non-existent note). (FR-10, NFR-2)

2. **Content event.** Given any content write (title or body) to a note, when it persists, then a `note.changed { rev, actor }` event is emitted on a process-local event bus to every open member — including `actor` (the username who wrote it) and the new `rev`. (FR-10)

3. **Membership event.** Given a member is added or removed, when it persists, then a `members.changed { members }` event reaches the note's current members, and a **removed** member additionally receives `note.closed { reason: "removed" }`. (FR-11)

4. **Delete event.** Given the owner deletes the note, when it persists, then all members receive `note.closed { reason: "deleted" }` and the stream ends. (FR-11)

5. **Client channel — ignore my own echo.** Given the client `useNoteEvents` composable, when a `note.changed` arrives whose `actor` is me or whose `rev` I already hold, then it is ignored (no refetch); otherwise the store refetches the note. (FR-10)

6. **No clobbering live typing.** Given a `note.changed` from another member while I am actively editing the body, when the store applies the incoming version, then it does not discard text I have typed since my last save — it applies the server body while preserving my un-flushed local edits per the documented reconciliation (record the strategy in the Dev Agent Record; last-write-per-save at the field level is acceptable). (NFR-4, NFR-5)

7. **Tests.** Given the suite, when it runs, then `pytest`/`npm test` stay green and formatters/linters are clean; backend tests cover the bus emit on write/membership/delete and the stream auth matrix (member / non-member / bad token); frontend tests cover the `useNoteEvents` echo/`rev` guard and the refetch path.

## Dev Notes

**Mirror Listies' live layer.** Listies Story 5.2 established this exact pattern for this platform: an in-process `asyncio` bus + a `?token=`-authenticated `text/event-stream`, coarse `*.changed { rev, actor }` events that drive a client **refetch** rather than delta/CRDT replay. Reuse that shape rather than inventing one. Single-worker deployment is assumed (per CLAUDE.md); a multi-worker bus is out of scope. [Source: docs/planning-artifacts/epics-listies.md#Epic 5]

**Echo suppression via `actor` + `rev`.** The writer's own `EventSource` will receive its own `note.changed`; the client ignores an event whose `actor` is itself or whose `rev` it already applied. This is what keeps my own save from triggering a redundant refetch (FR-10).

**Reconciliation is coarse.** On an accepted `note.changed`, refetch the full note. If I have un-flushed body edits, do not silently throw them away — the simplest acceptable policy is last-write-per-save (my next save wins, or I keep typing on top of the applied server body); a nicer policy may show a "note updated by {actor}" cue. Do not build OT/CRDT. (NFR-5)

**Removed/deleted closes the view.** A removed member and every member on delete get `note.closed`; the editor closes with an explanatory message rather than failing on the next save. The user-facing polish (home reactions, roster live update) is Story 2.3 — this story delivers the events and the editor-closing behaviour.
