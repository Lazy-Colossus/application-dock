# Story 2.1: Sharing lifecycle (backend)

## Status

Draft

## Story

**As** a note's owner,
**I want** to share it with chosen dock users and add or remove members,
**so that** the people I choose edit one shared note with me.

## Acceptance Criteria

1. **Share / add members.** Given a note I own, when I `POST /api/shared-notes/notes/{note_id}/share` with `{ usernames: [...] }`, then those usernames are unioned into `members` and the updated member list is returned; the note now resolves for each of them. Re-posting with more usernames unions them (idempotent for already-members). (FR-8)

2. **Remove a member.** Given a note I own, when I `DELETE /api/shared-notes/notes/{note_id}/share/{username}`, then that user is removed from `members` and can no longer access the note; the **owner cannot be removed** (attempting it is `422 {detail}`). (FR-8)

3. **Owner-only management.** Given a note I am a member of but do **not** own, when I attempt share / add-member / remove-member / delete, then the API rejects it with `403 {detail}` — only the owner manages membership and deletes the note. (FR-9)

4. **Unknown target user.** Given a share request naming a username that does not exist on the platform, when submitted, then it is rejected with `422 {detail}` (validated against `auth_service.list_usernames()`), and no partial membership change is persisted. (FR-8)

5. **Isolation.** Given a share / member endpoint for a note the caller cannot access (not a member), when called, then it returns `404 {detail}` — identical to a non-existent note, never revealing it exists. (NFR-2)

6. **Rev bump.** Given a membership change, when it persists, then `updated_at` is stamped (membership changes need not bump the content `rev`, but MUST be observable to Story 2.2 — record the chosen signal in the Dev Agent Record).

7. **Tests.** Given the suite, when it runs, then existing `pytest` stays green, formatters/linters are clean, and new tests cover: union on share, remove-member access loss, owner-cannot-be-removed, owner-only guards (403 for member), unknown-user rejection with no partial write, and the non-member `404`.

## Dev Notes

**No storage change.** A note is already its own file with `owner`/`members`/`rev` from Story 1.2, and the resolver from Story 1.3 already gates access by membership. This story only adds membership *mutation* and the owner guard — nothing about how a note is stored changes.

**Resolve before you guard.** Every share/member route resolves the note through the membership resolver first, so a caller who is not a member gets a `404` (note "does not exist" to them) and never a `403` that would leak the note's existence (NFR-2). The `403` is reserved for a *member* who is not the *owner* attempting to manage.

**Validate before writing.** Check every target username against `auth_service.list_usernames()` before mutating `members`, so a batch containing one bad name changes nothing (AC-4). [Source: docs/stories/listies/5.1.shared-storage-and-sharing-lifecycle.story.md]

**Owner is permanent.** The owner is always `members[0]` and cannot be removed; ownership transfer is out of scope. To fully un-share, the owner removes every other member (the note becomes members-of-one again) — there is no separate "stop sharing" state because there is no private/shared duality here.

**Signal for the live layer.** Story 2.2 needs to emit a `members.changed` (and `note.closed` for the removed member) when membership changes. Decide now whether that is driven by the same event bus call or a bumped `rev`; keep membership writes on the same code path content writes use so 2.2 only adds the emit.
