# Story 2.3: Sharing UI and live membership

## Status

Draft

## Story

**As** a user,
**I want** to manage who a note is shared with and see the roster and shared state in the app,
**so that** sharing is something I do from the UI, live.

## Acceptance Criteria

1. **Collaborators affordance.** Given a note I own, when I open its collaborators panel/dialog from the note page, then I can add members (picking from dock users) and remove members, wired to the Story 2.1 endpoints through `useApi`; a non-owner member sees the roster **read-only**. (FR-8, FR-9)

2. **Add members.** Given the share dialog, when I pick one or more dock users and confirm, then `POST /api/shared-notes/notes/{note_id}/share` is called and the roster updates; the picker lists platform users (from the existing users source) excluding current members. (FR-8)

3. **Remove a member.** Given the roster, when I (as owner) remove a member and confirm, then `DELETE /api/shared-notes/notes/{note_id}/share/{username}` is called and they drop from the roster; the owner is not removable in the UI. (FR-8)

4. **Home distinguishes shared state.** Given the home list, when it renders, then a note shared **with** me shows the owner's name and a "shared with you" cue, and a note I own that has other members carries a "shared" indicator. (FR-12)

5. **Live membership on the home.** Given I am added to or removed from a note while the app is open, when the `members.changed` / `note.closed` event arrives, then a newly-shared note appears in my home and a removed/deleted note drops from it (using the live channel from Story 2.2). (FR-11)

6. **Live roster / editor close.** Given the owner removes a member or deletes the note, when the change lands, then the affected members' open editors close with an explanatory message, and an open owner's roster reflects the removal live. (FR-11)

7. **Tests.** Given the frontend suite, when it runs, then `npm test` stays green, ESLint/Prettier are clean, and specs cover: owner add/remove flow, non-owner read-only roster, home shared-with-me vs shared-by-me rendering, and the live add/remove reactions (`useApi` and the events channel mocked).

## Dev Notes

**This is the user-facing cap on Epic 2.** The endpoints (Story 2.1) and the live channel + editor-closing behaviour (Story 2.2) already exist; this story is presentation and wiring — the share dialog, the home badges, and reacting to membership events on the list.

**Owner vs member in the UI.** Gate the add/remove controls on the note's `can_manage` (owner-only, from the GET response). The backend already enforces `403` for a non-owner (Story 2.1) — the UI gate is convenience, not the boundary.

**Home liveness is coarse.** The home need not hold an `EventSource` per note; reacting to membership by refetching the list when the app regains focus or when an open note's events indicate a roster change is sufficient at this scale. If a lightweight home-level signal is added, keep it simple — no per-note streams on the list.

**User picker source.** Reuse the platform's existing users source (the same one Listies sharing uses / `auth_service.list_usernames()` behind an endpoint); do not add a new users store.

**Contract.** All HTTP via `useApi`; `{detail}` errors through `ApiError`; store keeps `loading`/`error`. [Source: CLAUDE.md#Frontend]
