# Story 1.3: Create, list, rename, edit and delete a note (backend)

## Status

Draft

## Story

**As** a user,
**I want** an API to create a note, list the notes I can see, open one, change its title and body, and delete one I own,
**so that** the note loop works end-to-end before any UI is built.

## Acceptance Criteria

1. **Create.** Given `POST /api/shared-notes/notes` with `{ title }`, when called, then a note file is created with an `n-{uuid8}` id, `body = ""`, `owner = me`, `members = [me]`, `rev = 0`, and the created note is returned; a blank/whitespace title is rejected with `422 {detail}`. (FR-3)

2. **Access resolver.** Given any single-note operation for `note_id`, when it runs, then the service loads the note only if I am in its `members`; otherwise it raises `FileNotFoundError`. A non-member gets the identical `404` as a non-existent note. (FR-2, NFR-2)

3. **List.** Given `GET /api/shared-notes/notes`, when called, then it returns the notes where I am a member, each summarised as `{ id, title, owner, shared, updated_at }` (`shared` is true when `members` has more than one), ordered by `updated_at` descending. (FR-4)

4. **Get one.** Given `GET /api/shared-notes/notes/{note_id}`, when I am a member, then it returns the full note with `title`, `body`, `owner`, `members`, `rev`, and `can_manage` (true only for the owner); when I am not a member it returns `404 {detail}`. (FR-2)

5. **Update.** Given `PUT /api/shared-notes/notes/{note_id}` with `title` and/or `body`, when I am a member, then the supplied fields are written, `rev` is incremented and `updated_at` stamped, and the updated note is returned; a blank title is rejected with `422`; the body may be any string including `""`. (FR-5, FR-6)

6. **Delete is owner-only.** Given `DELETE /api/shared-notes/notes/{note_id}`, when I am the owner, then the note file is removed; a non-owner member gets `403 {detail}`; a non-member gets `404 {detail}`. (FR-7, FR-9)

7. **Exception mapping.** Given the router, when the service raises, then `FileNotFoundError → 404`, `ValueError → 422`, and `PermissionError → 403`, each as `{detail}`; no `HTTPException` is raised below the router. (NFR-3)

8. **Tests.** Given the suite, when it runs, then existing `pytest` stays green, formatters/linters are clean, and new tests cover create, the resolver access matrix (owner / member / non-member → 404), list ordering + `shared` flag, update + `rev` bump, blank-title rejection, and owner-only delete (403 vs 404).

## Dev Notes

**No `user` in the wire contract.** The caller comes from `get_current_user`; `owner`/`members` are derived, never accepted from the client (FR-2). A create body carries only `title`; an update body only `title`/`body`.

**`can_manage` is owner-only.** Only the owner sees `can_manage: true`; it gates the delete and (in Epic 2) membership management. Members edit `title`/`body` but cannot delete or manage sharing (FR-9). The delete guard lives in the service as `PermissionError`, mapped to `403` in the router.

**Last-write-per-save.** An update replaces the given fields wholesale — there is no field-level merge of the body. This is the accepted concurrency model (NFR-5); Story 2.2's live channel reconverges open views.

**List by scanning.** `list_notes` uses the repo's `list_notes_for(user)` — enumerate note files, filter by membership. Acceptable at this platform's scale (JSON files, small user counts); do not add an index or a database.

**Scope discipline.** No membership mutation endpoints (Story 2.1) and no SSE (Story 2.2). Sharing already *works at the data level* because a note is its own file with `members`; this story just never adds anyone but the owner.
