# Story 3.1: The bottom tab bar, and creating a tab

## Status

Draft

## Story

**As** a user,
**I want** a bar at the bottom of the sheet holding its tabs, with a way to add a new one,
**so that** one sheet can hold several related tables.

## Acceptance Criteria

1. **Bottom-anchored bar.** Given an open sheet, when it renders, then a tab bar is anchored at the **bottom** of the screen showing every tab in `order` as a chip; the active tab's chip is filled, the others outlined. The bar stays put while the grid scrolls. (FR-12)

2. **Switch tabs.** Given the tab bar, when I select another tab, then the grid switches to that tab's columns and rows without a page reload or refetch (the sheet payload already holds every tab), and the bar reflects the new selection.

3. **Sort resets on switch.** Given an active sort, when I switch tabs, then the sort resets — a sort belongs to the tab being viewed. (see Story 2.6)

4. **Create a tab.** Given the tab bar, when I use its `+` control and enter a name and columns, then `POST /api/listies/sheets/{sid}/tabs` creates a tab with a `tb-{uuid8}` id at the end of the tab order, its own columns (each with a fresh `c-{uuid8}` id) and no rows, and the grid switches to it. (FR-12)

5. **Create validation.** Given a submission with a blank tab name, zero columns, a blank column name, a duplicate column name, or an unknown type, then the client disables submit and the API rejects it with `422` `{detail}`.

6. **Duplicate tab names.** Given a tab name already used in this sheet, when submitted, then it is accepted — tabs are identified by id, and the bar shows both — but the client hints at the collision.

7. **Many tabs.** Given more tabs than fit the bar's width, when it renders, then the bar scrolls horizontally and the active chip is scrolled into view. (NFR-1)

## Dev Notes

**The whole sheet is already loaded.** `GET /sheets/{id}` returns every tab with its rows (Story 2.1), so switching tabs is local state — no request. If sheets ever grow big enough for that to hurt, the fix is a per-tab fetch behind the same store action, not a change to the UI.

**`activeTabId` already exists.** Story 2.1 put it in the store and rendered the first tab; this story adds the UI that changes it. No refactor should be needed.

**Bottom bar, deliberately.** The tab switcher lives at the bottom of the screen (the user's explicit ask), framing the grid the way a spreadsheet's sheet tabs do. [Source: FR-12]
