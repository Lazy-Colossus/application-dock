# Story 2.9: Filter rows by a column

## Status

Ready for Review

## Story

**As** a user,
**I want** to filter the rows by a specific column — text, number, date or a place group —
**so that** I can narrow a long tab down to just the rows I care about right now, without deleting or reordering anything.

## Acceptance Criteria

1. **Opening a filter — no collision with sort or the menu.** Given a column header, when I open its menu (the `expand_more` chevron, Story 2.5) and choose **"Filter…"**, then a type-aware filter editor opens for that column. The header **name** click stays owned by sort (Story 2.6) and the chevron stays the deliberate way in — a filter is never opened by a plain header click, so neither affordance swallows the other.

2. **Text — contains.** Given a `text` column, when I filter it with a search term, then a row is kept when its cell **contains** that term, case-insensitively; an empty term is no filter (all rows kept).

3. **Number — comparison.** Given a `number` column, when I filter it, then I can choose **equals**, **greater than**, **less than**, or a **between** range (min/max inclusive), and only rows whose numeric cell satisfies the chosen predicate are kept.

4. **Date — comparison.** Given a `date` column, when I filter it, then I can choose **on**, **before**, **after**, or a **between** range (inclusive), compared chronologically on the `YYYY-MM-DD` value; only rows whose date satisfies the predicate are kept.

5. **Place group — select groups.** Given a `place_group` column (Story 4.6), when I filter it, then I pick **one or more groups** to keep, each shown as its colour swatch + name (resolved from the tab's `place_groups` by id), plus a selectable **"Ungrouped"** option; a row is kept when its group **id** is in the chosen set, and a row whose cell is `null` — or holds a dangling id no longer in `place_groups` — is kept only when "Ungrouped" is chosen. With no groups selected the filter is inactive (all rows kept).

6. **Place — by name.** Given a `place` column, when I filter it, then it filters by the place snapshot's **name** as a case-insensitive substring — consistent with how `place` sorts by name (Stories 4.2 / 4.6). A row with no place in that column is not kept while the filter is active.

7. **Empties are excluded.** Given any active filter except a `place_group` "Ungrouped" selection, when a row's cell in that column is empty (`null`), then the row is **not** kept — "no value" cannot satisfy a contains/comparison predicate. (The one deliberate exception is AC 5's "Ungrouped".)

8. **Multiple filters combine with AND.** Given filters on more than one column, when rows render, then a row is kept only if it satisfies **every** active filter (logical AND across columns); one filter per column at a time.

9. **Filtering is a pure view — nothing is persisted.** Given any filter, when it is applied, then **no request is made** and stored `order`, `cells` and the tab document are untouched — the filter produces a display list of row ids, exactly like sort (Story 2.6). It resets when the tab or sheet changes.

10. **Filter then sort.** Given both a filter and a sort are active, when rows render, then the filter runs **first** (it decides which rows are shown) and the sort orders the survivors: the display order is `sort(filter(storedOrder))`. Editing a cell does not re-filter or re-sort the visible rows — the id list is recomputed only when the filter or sort **spec** changes, so a row never jumps or vanishes out from under the cursor mid-edit.

11. **Ghost row and new rows while filtering.** Given an active filter, when the grid renders, then the trailing ghost row is still shown and still materialises a real row on typing; a newly added row **appends** to the end of the display order (it is not re-filtered into or out of view) until the filter is changed or re-applied — mirroring sort's "new rows append" rule.

12. **Clearing and an active indicator.** Given at least one active filter, when the toolbar renders, then a **"Filters" indicator** (beside "Map"/"Groups" in `listies-sheet__toolbar`) shows how many columns are filtered and offers **clear-all**; each column's filter editor also has its own **clear**. Given no active filter, then no indicator shows.

13. **Pure and tested.** Given the predicates, when they are implemented, then they live in `apps/listies/filter.ts`, unit-tested per type — text contains, number ops, date ops, `place`/`place_group` matching, `null` handling, and multi-column AND combos.

## Dev Notes

**A filter is a view, exactly like a sort.** It produces a display list of row ids and never touches the file or the API — stored `order`, `cells` and the document are authoritative and untouched. This is the same contract Story 2.6 states for sort ("nothing is written… the sort is a view"); this story adds a second view that composes with it. There is **no new endpoint** — filtering is entirely client-side. [Source: docs/stories/listies/for-review/2.6.sort-rows-by-column.story.md; frontend/src/apps/listies/sort.ts]

**Frozen display order, so nothing jumps.** As with sort, the id list is recomputed only when the filter or sort *spec* changes — not on a keystroke. If we re-filtered live, the row being edited could vanish the instant its cell stopped matching, which is worse than sort's "row jumps" problem. The existing `displayRowIds` machinery and its rows-changed watcher in `SheetGrid.vue` already give this behaviour for sort; filtering slots into the same recompute. [Source: frontend/src/apps/listies/components/SheetGrid.vue#L341-L402]

**Compose, don't fork: `sort(filter(storedOrder))`.** Filter decides *which* rows show; sort decides their order. Run filter first, then hand its survivors to `sortRowIds`. Keeping them as two pure functions over the same `storedOrder` means each is independently testable and neither re-implements the other. [Source: frontend/src/apps/listies/sort.ts#sortRowIds]

**Type-aware predicates, mirroring the comparators.** `filter.ts` echoes `sort.ts`'s type dispatch: number compares numerically, date compares the `YYYY-MM-DD` string chronologically, text/place compare the name case-insensitively, and `place_group` resolves the cell's **id** against the tab's `place_groups`. Reusing `isPlace()` for the place-name path keeps it consistent with how `compareValues` already sorts a place by name. [Source: frontend/src/apps/listies/sort.ts#compareValues; frontend/src/apps/listies/types.ts#isPlace]

**Empty means "not this row" — with one deliberate exception.** A `null` cell has no value to contain or compare, so an active filter excludes it. The single exception is a `place_group` "Ungrouped" selection, which is precisely a filter *for* the absence of a group — and it must also catch a **dangling** id (a group deleted out from under the cell), matching 4.6's rule that a dangling id "reads as ungrouped, not an error". [Source: docs/stories/listies/4.6.place-group-column-and-pin-colours.story.md#AC-3]

**Don't collide with sort-on-click or the column menu.** The header does two things already: a name click cycles the sort (2.6) and the chevron opens `ColumnHeaderMenu` (2.5). The filter is a **third** action, so it rides inside the menu the chevron already opens (a new "Filter…" mode beside Rename / Change type / Delete) rather than inventing a new header click. This keeps "a plain click sorts, the menu is opened deliberately" intact. [Source: frontend/src/apps/listies/components/SheetGrid.vue#L27-L66; frontend/src/apps/listies/components/ColumnHeaderMenu.vue]

**place_group depends on 4.6, but degrades gracefully.** The `place_group` type only exists once 4.6 lands (it adds the type, the `Tab.place_groups` field and the group id cell). Until then no column has that type, so the filter editor simply never renders its group branch — but this story still `depends_on` 4.6 because the group-filter acceptance criteria (AC 5) cannot be met or tested without it. The text/number/date/place branches stand on 2.1 alone. [Source: docs/stories/listies/4.6.place-group-column-and-pin-colours.story.md]

**The toolbar indicator follows the Groups-button pattern.** A "Filters" chip lives in `listies-sheet__toolbar` beside "Map" (and "Groups" from 4.6), shown only when a filter is active, carrying the count and clear-all — the same "toolbar affordance above the split" placement 4.6 chose for its Groups button. [Source: frontend/src/apps/listies/pages/SheetPage.vue#L34; docs/stories/listies/4.6.place-group-column-and-pin-colours.story.md#AC-6]

### Completion Notes

- **Built on Story 4.6 first.** 2.9 declared `depends_on: [2.1, 4.6]`, and 4.6 (the `place_group` column) was only a Draft, so it was implemented end-to-end first; this story then filters that type in full (no descope).
- **A filter is a pure view, exactly like a sort — nothing is written.** `filter.ts` holds `FilterSpec` (a discriminated union), `matchesFilter`, `isActive`, `filterRowIds` (AND across active filters, input order preserved, never mutated) and `activeFilterCount`; all pure and unit-tested (19 tests). No new endpoint, no store write — a test asserts a narrowing filter emits no `commit-cell`.
- **Composes with sort as `sort(filter(storedOrder))`.** `SheetGrid` filters first, then orders the survivors, recomputing the display id list **only** when the filter or sort *spec* changes — never on a cell edit — so a row never vanishes or jumps mid-edit (tested by editing a filtered cell and asserting the row stays put).
- **The append rule needed a real fix, not just reuse.** The rows-changed watcher used to treat "any row not already in `displayRowIds`" as new — which, once a filter hides rows, wrongly re-appended the hidden ones on the next row change. It now judges "new" against the *previous* row set (the watch's old value), so a genuinely-new row appends to the end of the filtered view while hidden rows stay hidden (AC 11, tested).
- **The filter rides the column menu, colliding with neither sort nor the menu.** A "Filter…" item in `ColumnHeaderMenu` (Story 2.5's chevron menu) opens a type-aware editor — contains for text/place, an op + value/range for number/date, a group multi-select with swatches + "Ungrouped" for `place_group`. Emits `FilterSpec | null`; the header **name** still cycles sort untouched. The editor pre-fills from the currently-applied filter.
- **Filters are owned by `SheetPage`** (a controlled `filters` prop to `SheetGrid`), so the "Filters (n)" chip + clear-all live naturally in `listies-sheet__toolbar` beside Map/Groups, shown only when ≥1 filter is active. Filters reset when the tab changes, like the sort and the map ticks. A per-column `▾` header mark shows which columns are filtered.
- **`place`/`place_group` handling matches 4.6.** `place` filters by the snapshot's **name**; `place_group` matches by group **id**, with "Ungrouped" catching both an empty cell and a **dangling** id (a deleted group) — consistent with 4.6's "dangling id reads as ungrouped".
- **Signature note.** `filterRowIds(rows, filters, groups?)` takes the tab's groups (needed to detect a dangling id) rather than the `columns` shown in the story sketch — the `FilterSpec.kind` already carries the per-column type, so `columns` was unnecessary. Added `activeFilterCount` for the toolbar badge.
