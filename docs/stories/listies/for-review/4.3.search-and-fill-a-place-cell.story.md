# Story 4.3: Search Google and fill a place cell

## Status

Ready for Review

## Story

**As** a user,
**I want** to type a place name into a cell and pick the real place from Google,
**so that** filling in a location takes one search rather than a copy-paste of coordinates.

## Acceptance Criteria

1. **Search in place.** Given a place cell, when I click it, then it opens a search field in place, pre-filled with the current place's name if it has one and with the text selected. (FR-16)

2. **Debounced search.** Given the search field, when I have typed at least two characters, then after a debounce (~300ms) the client calls `GET /api/listies/places/search` through `useApi` and shows a result list beneath the cell — name in full, address muted. Fewer than two characters searches nothing. (NFR-6)

3. **Pick a result.** Given the result list, when I move through it with ↑/↓ and press Enter (or click a result), then the chosen place is written through the ordinary row-cells `PUT` as a whole place object and appears in the grid immediately, with the same optimistic-then-reconcile-or-roll-back behaviour as every other cell. (FR-16, NFR-5)

4. **Local bias.** Given the column already holds places, when a search is issued, then it passes `near` as the centroid of those places, so results are local to what is already in the column.

5. **Honest states.** Given a search that is loading, returns nothing, or fails, when it renders, then the cell shows a loading indicator, a "no places found" line, or the error message — never a silent empty dropdown.

6. **Clearing.** Given a filled place cell, when I clear it, then it is stored as `null` and renders as `—`.

7. **Esc.** Given the result list is open, when I press Esc, then the list closes, the cell keeps its previous value, and nothing is sent — consistent with every other editor. (FR-8)

8. **Keyboard grammar holds.** Given a place cell, when I Tab or Enter out of it without picking a result, then movement behaves exactly as it does for other cells and no half-typed query is stored. (FR-8)

9. **Unconfigured.** Given maps are not configured, when a place cell is opened, then it is read-only and says maps are not configured, rather than offering a search that cannot work. (FR-20)

10. **Stale responses.** Given two searches in flight, when the earlier one resolves last, then its results are discarded — the list always reflects the latest query.

## Dev Notes

**One write path.** Selecting a place goes through the same `PUT .../rows/{rid}` cell commit as typing a number — the payload is just an object. No place-specific endpoint. [Source: Story 2.2]

**Debounce is a cost control, not polish.** Every keystroke that reaches `/places/search` is a billable upstream call on a cache miss. Debounce plus the two-character minimum plus the server-side cache are what keep this cheap. [Source: NFR-6]

**Don't hijack the keyboard.** The result list owns ↑/↓ and Enter only while it is open; Tab, and Enter with no list, must behave exactly as they do in every other cell so the grid's movement rules stay uniform. [Source: Story 2.3]

### Completion Notes
- **`PlaceCell`** owns the search: a field pre-filled with the current place's name, a 300ms debounce, a two-character minimum, a result list with name and muted address, arrow-key highlighting that stops at the ends, Enter/click to pick, Esc to cancel, a clear button only when there is something to clear, and its own loading / empty / error states.
- **A search never gates the sheet.** `searchPlaces` sets `searching`, never `loading`, and **rethrows instead of writing to `error`** — a failed search belongs beside the cell, not in a banner across a sheet that is otherwise fine. Both are asserted.
- **Stale responses are dropped.** Each search takes a ticket and only the newest may write results; a slow first response cannot overwrite a fast second one. The test overtakes a 500ms response with an immediate one and asserts the stale name never appears.
- **Under the two-character minimum, anything in flight is abandoned** — not just left to land later. Deleting back to one character invalidates the ticket, so a late response cannot repopulate a list the user has cleared.
- **The result list fires on `mousedown`, not `click`**, so picking a place survives the input blurring underneath it. My first test used `click` and failed; the production behaviour was right and the test was corrected, with the reason recorded in the test itself.
- **The grid's keyboard contract is unchanged**, which took one specific fix: the grid commits the focused cell before moving (Story 2.3), and `parseCell` refuses free text for a place column — so Tab out of a place cell would have been treated as an invalid entry and **trapped the cursor**. `commit()` is now a no-op for a place column that simply ends the edit. There is a test that calls `commit()` directly and asserts no commit, no invalid state, and a clean exit.
- **Searches are biased to the column.** The page passes `store.placeCentroid` into the grid, which asks it only for place columns; the centroid is the mean of the places already in that column, rounded to six decimals. So "cafe" in a column of Lisbon cafés means Lisbon cafés.
- **A cross-boundary assumption got pinned on both sides.** My test expected `%20` for a space; `URLSearchParams` emits `+`. The code was right, so I fixed the expectation *and* added a backend test that `?q=caf+%26+bar` arrives as `caf & bar` in the upstream body — otherwise the two halves only agree by luck.
- **With maps unconfigured the cell explains itself** and searches nothing, rather than offering a box that cannot work.
- **Suites:** backend **765** passed (was 764), frontend **1043** passed plus the one pre-existing `hotaru/LibraryPage` failure. `black`, `ruff`, ESLint, Prettier, `vue-tsc` all clean.

### Follow-up: the results were invisible

Reported after the keys went in: "when searching we can't see the search results/bar".

Reproduced in the browser with live keys. Search was working perfectly — 20 results came back — but
the list rendered **inside the grid cell**, which is `overflow: hidden` and about 24px tall. The
dropdown was 224px tall starting at y=196 in a cell ending at y=198: all but 2px was clipped away.
The table's own scroll container would have clipped it too, near the bottom of the grid.

Fixed by teleporting the dropdown to the body and positioning it `fixed` against the input's
bounding rect, re-measured on scroll (capture phase, so the grid's own scroller counts) and on
resize. Verified live afterwards: the list renders in full outside the table, picking a result
stores the place with real coordinates, and the dropdown closes.

Two notes from doing it:
- The results were Tokyo-biased because the column already held "Tokyo" — the centroid bias from
  this story working on real data.
- **Vue Test Utils does not remove teleported content on unmount.** The first run showed 8 results
  where 2 were expected, because four earlier tests' lists were still in `document.body`. The specs
  now clean them up explicitly; without that, every body assertion in the file is quietly wrong.

**Still open, deliberately not guessed at:** the inline invalid-value message (`.grid-cell__error`)
sits in the same `overflow: hidden` cell and may be clipped in a single-line row. I could not
reproduce it — the row I measured was 49px tall because a place cell wraps to two lines, so the
message happened to fit — and I would rather fix it against a real reproduction than blind.
