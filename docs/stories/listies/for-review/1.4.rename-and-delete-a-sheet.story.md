# Story 1.4: Rename and delete a sheet

## Status

Ready for Review

## Story

**As** a user,
**I want** to rename a sheet or delete one I no longer need,
**so that** I can keep my set of sheets tidy.

## Acceptance Criteria

1. **Rename.** Given a sheet, when I rename it via `PUT /api/listies/sheets/{sheet_id}` with `{ name }`, then the name updates in my file and everywhere it is shown. (FR-5)

2. **Rename validation.** Given a rename to a blank or whitespace name, when submitted, then the client disables submit and the API rejects it with `422` `{detail}`.

3. **Delete with confirmation.** Given a sheet, when I choose delete and confirm, then `DELETE /api/listies/sheets/{sheet_id}` removes the whole sheet — its tabs, columns and rows — from my file and it disappears from the home. The destructive action always requires an explicit confirmation first. (FR-5)

4. **Unknown id.** Given a rename or delete for a sheet id that isn't in my file, when requested, then the API returns `404` `{detail}` — which also covers another user's sheet id, since the file comes from the token, not from input. (FR-2)

5. **Delete returns no body.** Given a successful delete, when it responds, then it is a `204` with no body and the store removes the sheet from `sheets` without a refetch.

## Dev Notes

**PUT, not PATCH.** `useApi` exposes `get`/`post`/`put`/`del` only; the platform uses `PUT` for partial updates (Hotaru and Context-Switch precedent). [Source: CLAUDE.md#Frontend, `backend/app/routers/context_switch.py`]

**404 as the isolation boundary.** Never distinguish "not yours" from "doesn't exist" — the lookup is inside the caller's own document, so an id belonging to someone else is simply absent. [Source: FR-2, NFR-2]

**Scope discipline.** Sheet-level rename/delete only. Tab rename/delete is Story 3.3.

### Completion Notes
- **Backend:** `PUT /sheets/{id}` (trims, rejects blank with 422, rejects a body with nothing to update with 422, 404 for an unknown id) and `DELETE /sheets/{id}` (204, empty body). `UpdateSheetRequest` is all-optional so a later story can add a field without a new endpoint.
- **Frontend:** `renameSheet` / `deleteSheet` on the store mutate `sheets` locally on success rather than refetching, and route failures into `error` without throwing (unlike `createSheet`, which rethrows because the caller must not navigate). The home page gained per-row edit/delete controls, an inline rename field, and an inline "Delete this sheet?" confirmation, matching the Context-Switch precedent. A row click does not open the sheet while that row is mid-rename or mid-confirm.
- **Two test-quality problems found and fixed, both worth recording:**
  - The store spec shared one `SUMMARY` object across cases; the successful-rename test mutated it, so the failure-path test then saw the *renamed* value and failed. Replaced with a `summary()` factory — the store legitimately mutates the summary it holds, so tests must not share one instance.
  - The home-page `q-btn` stub emitted `click` with no event argument, so `@click.stop` threw `Cannot read properties of undefined`. Real `q-btn` passes the event; the stub now does too. The nine red tests were a faithful stub bug, not a component bug.
- **Vacuous reds, noted for honesty:** three of the 404 tests (`rename_unknown`, `delete_unknown`, `another_users_sheet_id`) passed before the routes existed, because an undefined path also 404s. They only became meaningful once the routes were added; the other ten failed properly.
- **Suites:** backend **605** passed (was 592). Frontend **710** passed with the one pre-existing `hotaru/LibraryPage` failure unchanged. `black`, `ruff`, ESLint, Prettier clean.
