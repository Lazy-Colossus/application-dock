# Story 2.2: Edit cells inline with type-aware editors

## Status

Ready for Review

## Story

**As** a user,
**I want** to click a cell and type into it, with the editor matching the column's type,
**so that** filling the sheet in feels direct.

## Acceptance Criteria

1. **Click to edit.** Given a cell, when I click it, then it enters edit mode in place with an editor matching the column type — a plain input for `text`, a numeric input for `number`, a date picker for `date` — pre-filled with the current value and its text selected. (FR-7)

2. **Commit persists only what changed.** Given a cell in edit mode, when I commit it (blur, Tab or Enter), then `PUT /api/listies/sheets/{sid}/tabs/{tid}/rows/{rid}` sends only that row's changed cells; the service merges them into the stored `cells` (leaving other keys untouched) and stamps `updated_at`. (FR-7)

3. **Optimistic and non-blocking.** Given a commit, when the request is in flight, then the grid already shows the new value and stays fully interactive; on success the store reconciles with the response; on failure the cell reverts to its previous value and the message surfaces via the store's `error`. (NFR-5)

4. **Client-side type validation.** Given a value that does not fit its column's type (e.g. `abc` in a number column, `31/02/2026` in a date column), when I try to commit, then the cell is marked invalid inline and nothing is sent; the API also rejects a bad value with `422` `{detail}` as a backstop.

5. **Clearing a cell.** Given a filled cell, when I commit an empty value, then it is stored as `null` — not `0`, not `""` — the key is pruned from `cells`, and it renders as the muted `—`.

6. **Esc reverts.** Given a cell in edit mode, when I press Esc, then the cell reverts to its previous value, leaves edit mode, keeps focus, and nothing is sent.

7. **No accidental writes.** Given a cell I open and leave unchanged, when I commit, then no request is sent at all.

## Dev Notes

**Optimistic is the point.** The grid must never wait on the network to show a typed value — that is what makes it feel like a spreadsheet rather than a form. The rollback path is the part to test hardest. [Source: NFR-5]

**One coercion implementation.** Client-side `parseCell` and server-side `coerce_value` follow the same documented table; the server is the authority, the client is there so the user finds out immediately. [Source: spec#Data model]

**Merge, don't replace.** `PUT .../rows/{rid}` merges the provided `cells` keys. A payload never has to carry the whole row, so two cells committed in quick succession can't clobber each other.

**Scope discipline.** Mouse-driven editing only. Tab/Enter/arrow movement and the ghost row are Story 2.3 (the `commit` contract here is what 2.3 hooks into).

### Completion Notes
- **Backend:** `PUT .../rows/{rid}` merges only the provided keys. The whole payload is validated **before** anything is applied, so a rejected update leaves the row byte-identical (there is a test for a payload that mixes one good cell with one bad one). A key set to empty removes it from `cells`; `0` survives as a value.
- **Frontend:** `parseCell` joins `formatCell` in `coerce.ts`; `commitCell` writes optimistically and rolls back on failure. `commitCell` deliberately **does not touch `loading`** — gating the page spinner on a keystroke is exactly what NFR-5 forbids; there is a test asserting `loading` stays false while a commit is in flight.
- **A design change the tests forced, worth reading.** I first used a native `type="number"` input. Two problems surfaced as reds: Vue auto-casts `v-model` on a number input so the draft stops being a string, and — the real one — **a native number input silently discards anything it cannot parse**. Typing `12abc` would have quietly *cleared* the cell instead of warning, making AC 4's inline rejection unreachable. Number columns now use `type="text"` with `inputmode="decimal"` so we own the validation and can explain it. Dates keep the native `type="date"` picker, which is a genuine gain and enforces ISO; `parseCell` stays as the backstop for both.
- **An invalid entry keeps the editor open** rather than closing and dropping what was typed — losing the user's entry to tell them it was wrong would be the worst of both.
- **No accidental writes:** committing an unchanged cell emits nothing, so tabbing through a row sends no requests.
- **TDD:** 12 backend tests red first; then `parseCell` (12 red), `commitCell` (8 red), `GridCell` editing (14 red), and the grid/page wiring (3 red) in turn.
- **Suites:** backend **629** passed (was 617). Frontend **784** passed plus the one pre-existing `hotaru/LibraryPage` failure. `black`, `ruff`, ESLint, Prettier clean.
