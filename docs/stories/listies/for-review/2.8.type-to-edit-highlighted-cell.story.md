# Story 2.8: Type to edit a highlighted cell

## Status

review

## Story

**As** a user,
**I want** to just start typing when a cell is highlighted and have my keystroke begin editing that cell,
**so that** entering data feels like a spreadsheet — I don't have to click in or press a separate key before I can type.

## Acceptance Criteria

1. **A printable keystroke on a highlighted cell enters edit mode.** Given a cell that is **focused/highlighted but not in edit mode** (the keyboard or a click has landed on it, but there is no text cursor in it yet), when I press a single printable character, then the cell enters edit mode immediately and that character becomes the cell's content — no prior click or Enter needed. (FR-7, FR-8)

2. **Type-to-edit replaces existing content.** Given a highlighted `text` or `number` cell that already holds a value, when I start typing, then the typed character **replaces** the old content (spreadsheet convention — the same as Excel / Google Sheets, where typing over a selected cell overwrites it) rather than appending to it, and the caret sits after the typed character ready for more input.

3. **The typed character actually appears.** Given type-to-edit has begun, when the editor opens, then the character I pressed is already in the input (it is not swallowed by the transition into edit mode), and continuing to type extends it normally.

4. **The value commits like any other edit.** Given a cell entered via type-to-edit, when I commit it (blur, Tab, or Enter), then it persists through the ordinary `commit` → `commit-cell` path from Story 2.2 — optimistic apply, reconcile on success, roll back with the error surfaced on failure — with no new write path. An invalid value for the column type (e.g. a letter typed into a `number` cell) is handled exactly as a typed-in edit is today: it stays in the editor with the inline error rather than being sent (Story 2.2). (NFR-5)

5. **Navigation and command keys do NOT trigger type-to-edit.** Given a highlighted cell not in edit mode, when I press a **non-printable** key — Arrow keys, Enter, Tab, Shift-Tab, Escape, Home, End, Page Up/Down, Backspace, Delete, or a function key — then type-to-edit does **not** fire and that key keeps its current Story 2.3 behaviour: arrows move focus, Enter commits-and-moves-down, Tab / Shift-Tab commit-and-move, Escape leaves edit mode.

6. **Modifier combinations do NOT trigger type-to-edit.** Given a highlighted cell not in edit mode, when I press a key while holding Ctrl, Cmd (Meta), or Alt — e.g. Ctrl+C, Cmd+V, Ctrl+A — then type-to-edit does **not** fire and the browser/OS shortcut is left alone; a bare Shift+letter (a capital letter) **does** type-to-edit, since it produces a printable character.

7. **Existing ways of entering edit still work.** Given the current grid behaviour, when I click a highlighted cell, then it still enters edit mode seeded with the cell's existing value (unchanged from Story 2.2); type-to-edit is an *additional* entry path, not a replacement, and it does not change click-to-edit or the keyboard grammar of Story 2.3.

8. **The trailing ghost row participates.** Given the highlighted cell is in the trailing empty "ghost" row (Story 2.3), when I start typing, then it enters edit mode with the typed character, and committing it materialises a real row carrying that value exactly as typing into the ghost row does today.

9. **Date and place cells enter cleanly, without a bogus seeded string.** Given a highlighted `date` or `place` cell, when I press a printable key, then it enters edit mode and opens that column's editor (the date input / the place search) rather than injecting a raw character into a picker that cannot use it — type-to-edit seeds the free-text editors (`text`, `number`); the specialised editors just open. This keeps the `commit()` no-op contract those columns rely on (Story 4.3) intact so the cursor is never trapped.

## Dev Notes

**Focus vs. edit is already the model.** The grid distinguishes a *highlighted* cell (`nav.focused`, rendered with `grid-cell--focused`) from an *editing* cell (`nav.editing`, which mounts the `<input>`). Type-to-edit is exactly the transition from the first state to the second, driven by a keystroke instead of a click — so it belongs in the grid's central `onKeydown`, alongside the existing Tab/Enter/Escape/arrow handling, not in a new listener. [Source: frontend/src/apps/listies/components/SheetGrid.vue; frontend/src/apps/listies/composables/useGridNavigation.ts]

**Keyboard handling is centralised.** All grid keys are handled by `onKeydown` on the `.sheet-grid__scroll` container, which already early-returns unless `nav.focused.value` is set and switches on `event.key`. Printable characters currently fall through the `default` branch and do nothing — that is the seam to fill. The check must be `event.key.length === 1 && !event.ctrlKey && !event.metaKey && !event.altKey`: named keys like `"ArrowRight"`, `"Enter"`, `"Tab"`, `"Escape"` are all longer than one character, so length-1 cleanly excludes them, and excluding the modifiers keeps Ctrl+C / Cmd+V shortcuts working (AC 5, 6). A bare Shift is fine — `event.key` for Shift+`a` is `"A"`, a printable length-1 string. [Source: frontend/src/apps/listies/components/SheetGrid.vue#onKeydown]

**Seeding replaces, per spreadsheet convention.** Today the cell's `editing` watcher seeds `draft` from the stored value: `draft.value = props.value === null ? "" : String(props.value)`, then `inputEl.select()`. Click-to-edit must keep that (AC 7). Type-to-edit instead wants the draft to *become* the single typed character — overwriting existing content the way Excel / Google Sheets do when you type over a selected cell (AC 2) — with the caret at the end rather than a select-all. Expose a seam on the cell (a `seedDraft(char)` method via `defineExpose`, reached through the grid's existing `cells` map, or a transient prop the watcher honours) rather than duplicating the editor. [Source: frontend/src/apps/listies/components/GridCell.vue#watch-editing]

**One write path, again.** A type-to-edit commit is an ordinary commit: `GridCell.commit()` → `parseCell` → `emit('commit')` → the grid's `@commit="emit('commit-cell', …)"` → `commitCell` in the store, optimistic then reconciled. No new endpoint, no date/number special-casing, and invalid input stays in the editor with its inline error exactly as a typed-in edit does today. [Source: frontend/src/apps/listies/components/GridCell.vue#commit; frontend/src/apps/listies/stores/useListiesStore.ts#commitCell]

**Don't seed the pickers.** The `date` editor is a native `<input type="date">` and the `place` editor is a search box (`PlaceCell`, Story 4.3) — neither can meaningfully accept a raw seeded character, and `place` deliberately makes `commit()` a no-op so Tab-out is not treated as an invalid entry. For those types, type-to-edit should only *open* the editor (`nav.beginEdit()`), not inject text, preserving that contract. [Source: frontend/src/apps/listies/components/GridCell.vue; frontend/src/apps/listies/components/PlaceCell.vue]

**Ghost row is free.** The trailing ghost row's cells are already focusable and editable and route their `@commit` to `materialise`, which appends a real row. Because type-to-edit reuses the same edit-then-commit flow, typing into the highlighted ghost cell materialises a row with no extra handling. [Source: frontend/src/apps/listies/components/SheetGrid.vue#materialise]
