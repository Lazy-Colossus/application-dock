# Story 3.2: Create a tab by copying another tab's columns

## Status

Ready for Review

## Story

**As** a user,
**I want** a new tab to be able to start with the same columns as an existing tab,
**so that** I don't have to rebuild the same setup by hand.

## Acceptance Criteria

1. **Copy the setup.** Given the create-tab dialog in a sheet that already has a tab, when I choose "same columns as…" and pick a tab, then `POST .../tabs` with `{ name, copy_columns_from }` creates the new tab with copies of that tab's columns — same names, types and order — but **fresh `c-{uuid8}` ids**, and **no rows**. (FR-13)

2. **A snapshot, not a link.** Given a tab created by copying, when I later rename, retype, reorder or delete a column in either tab, then the other tab is unaffected.

3. **Unknown source.** Given a `copy_columns_from` naming a tab that isn't in this sheet, when submitted, then the API returns `404` `{detail}`.

4. **Mutually exclusive.** Given a request supplying both `copy_columns_from` and explicit `columns`, when submitted, then it is rejected with `422` `{detail}`; supplying neither is also a `422`.

5. **Dialog shape.** Given the create-tab dialog, when the sheet has at least one other tab, then it offers a choice between "define columns" (the `ColumnBuilder`) and "same columns as…" (a tab picker defaulting to the currently active tab); with no other tab, only the builder is shown.

6. **Preview.** Given "same columns as…" with a tab selected, when the dialog renders, then it previews the column names and types that will be copied, so the choice is visible before submitting.

## Dev Notes

**Fresh ids matter.** Cells are keyed by column id (AR-5). Reusing the source tab's column ids would make two tabs share keys and turn a later retype into an action at a distance. The copy is structural only.

**Why not share a column set?** Shared columns would make "each tab owns its columns" (FR-13) a lie the first time someone edits one. The snapshot is the whole point — convenience at creation, independence afterwards.

### Completion Notes
- **Backend:** `CreateTabRequest` gained `copy_columns_from` and made `columns` optional; the service enforces **exactly one** with a single `(columns is None) == (copy is None)` check, so both and neither are the same 422.
- **Fresh column ids on every copy**, with a test asserting the two id sets are disjoint. This is the crux: cells are keyed by column id, so reusing the source's ids would make two tabs share keys and turn a retype in one into an action at a distance in the other.
- **Snapshot, not a link — proven both ways.** One test renames a column in the source and asserts the copy is unchanged; another *deletes* a source column and asserts the copy still has all three. A structural copy that shares nothing afterwards.
- **A real rendering bug found by a test.** Switching the dialog's mode back from "copy" to "define" threw `Cannot read properties of null (reading 'nextSibling')` — Vue's fragment anchors do not survive swapping two multi-root `<template>` branches. Each branch now has a single root element. The test that caught it (`returns to defining columns when the mode is switched back`) exists precisely because I wrote a case for going *back*, not just forward.
- **The dialog offers copying only when there is something to copy from**, defaults the source to the first tab, and previews the exact column names and types plus "and no rows" — the choice is visible before submitting.
- **Store:** `createTab` and `createTabFrom` now share one `postTab` helper, so the two shapes cannot drift in how they append the tab and activate it.
- **Suites:** backend **685** passed (was 676) — 9 new. Frontend **924** passed plus the one pre-existing `hotaru/LibraryPage` failure. `black`, `ruff`, ESLint, Prettier clean.
