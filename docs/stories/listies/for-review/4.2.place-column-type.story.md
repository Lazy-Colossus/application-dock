# Story 4.2: The `place` column type

## Status

Ready for Review

## Story

**As** a user,
**I want** a column whose cells hold a real location,
**so that** a row can be somewhere I intend to go rather than just its name.

## Acceptance Criteria

1. **A fourth type.** Given column creation or a retype, when the type list renders, then `place` appears alongside text / number / date — offered only when `maps-config` reports `enabled`. (FR-15, FR-20)

2. **Schema.** Given `schemas/listies.py`, when a place cell is validated, then a `Place` model (`place_id`, `name`, `address`, `lat`, `lng`) is accepted for a `place` column and rejected for any other column type; a scalar written into a `place` column is a `422`. (AR-7)

3. **Backward compatible.** Given a document written before places existed, when it is read, then it validates unchanged — the union widened additively, so `schema_version` stays `1`. (AR-7)

4. **Coercion.** Given a retype touching a place column, when applied, then `place` → `text` keeps the place's `name`; `place` → `number` / `date` blanks to `null`; anything → `place` blanks to `null`; and Story 2.5's "this will empty N cells" warning covers all three. (FR-10)

5. **Grid rendering.** Given a place cell, when it renders, then it shows a 📍 glyph with the place name on the first line and the address muted beneath; an empty place cell shows the same muted `—` as every other type.

6. **Sorting.** Given a sort on a place column, when applied, then rows compare by place **name** with the text comparator and empties last. (FR-11)

7. **Latitude / longitude sanity.** Given a place payload with `lat` outside ±90 or `lng` outside ±180, when validated, then it is rejected with `422`.

## Dev Notes

**Additive, so no migration.** Old documents contain no place columns and no object cells, so widening the union changes nothing on disk. `migrate()` stays a pass-through and `schema_version` stays `1`. [Source: AR-7]

**Snapshot, not a reference.** The cell keeps what Google returned at the time. Nothing is re-fetched later, so a sheet still reads correctly if the key is removed, and an "open in Google Maps" link is derived from `place_id` without a call. [Source: NFR-6]

**Scope discipline.** The type, its storage, its rendering and its sorting. Searching to *fill* a place cell is 4.3.

### Completion Notes
- **Schema:** `Place` (`place_id`, `name`, `address`, `lat`, `lng`) with `lat`/`lng` bounded to the real world, `ColumnType` gained `"place"`, and `CellValue` widened to include it. Purely additive — a document written before places has no place cells, so `schema_version` stays `1`, asserted by a test that validates a pre-places document.
- **The write path stays strict, the document stays lenient.** `coerce_value` accepts a `Place` (or its dict form) *only* in a place column and rejects a place in any scalar column — otherwise `str(place)` would have quietly stored `"place_id='ChIJ…' name=…"`. There is an explicit guard for that, because it is the kind of thing that silently produces garbage rather than an error.
- **Pydantic's `ValidationError` is a `ValueError` subclass**, so a malformed place would already have become a 422 — but with a message naming every failing field. `_as_place` catches it and raises a short one instead.
- **Retype rules:** place → text keeps the **name** (a special case in `_reparse`, which otherwise uses `str(value)`); place → number/date blanks; anything → place blanks, since a place cannot be reconstructed from a string. Each direction is tested on both sides of the wire — the server rules and the client's `countBlankedByRetype` warning agree.
- **No backend guard on creating a place column when maps are unconfigured.** Keys can come and go; data should not depend on them. An existing place column keeps reading if the key is removed — which is also why a place is stored as a snapshot rather than re-fetched. The *offering* of the type is gated in the UI.
- **`columnTypes.ts` is now the single list of offered types**, shared by the column builder, the header menu and the add-column popup. Previously each had its own copy of the three-item array; adding a fourth type to three places independently was an obvious way to let them drift.
- **The store loads `/maps-config` once per session, and fails silently.** Maps are optional: if that request fails, an error banner over a sheet that works perfectly well would be noise. Tested.
- **A type-checking debt of my own, cleaned up.** `vue-tsc` is a project dependency but no script ran it and no CI invokes it, so it had gone unseen: **13 type errors, all 13 in `src/apps/listies`** — every other app was clean. Fixed all of them (a genuinely wrong `ComponentPublicInstance` generic in `SheetGrid.vue`, plus conditional-object unions and `WrapperLike.props` in my specs), added `src/test-utils.ts` for the one cast Vue Test Utils forces, and added an `npm run typecheck` script so it cannot rot silently again.
- **Suites:** backend **764** passed (was 743) — 21 new. Frontend **1001** passed plus the one pre-existing `hotaru/LibraryPage` failure. `black`, `ruff`, ESLint, Prettier and now `vue-tsc` all clean.
