# Story 2.6: Sort rows by a column

## Status

Ready for Review

## Story

**As** a user,
**I want** to click a column header to sort the rows by it,
**so that** I can see the list in the order that's useful right now.

## Acceptance Criteria

1. **Cycle on click.** Given a column header, when I click it repeatedly, then the sort cycles none → ascending → descending → none, and the header shows the current direction; sorting by a different column replaces the previous sort (one sort at a time). (FR-11)

2. **Type-aware comparison.** Given an active sort, when rows render, then the comparison is numeric for `number`, chronological for `date`, and locale-aware case-insensitive for `text`; ties keep their previous relative order (stable sort).

3. **Empties last.** Given rows with `null` in the sorted column, when sorted, then those rows come last in **both** directions.

4. **Editing doesn't move rows.** Given an active sort, when I edit a cell, then the row does not jump: the display order is a list of row ids recomputed only when the sort spec changes. (FR-11)

5. **New rows append.** Given an active sort, when I add a row (button or ghost row), then it appends at the end of the display order until the sort is changed or re-applied.

6. **Nothing is persisted.** Given any sort, when it is applied, then no request is made and stored `order` is untouched — the sort is a view. It resets when the tab or sheet changes.

7. **Pure and tested.** Given the comparator, when it is implemented, then it lives in `apps/listies/sort.ts` and is unit-tested per type including `null`s, ties and both directions.

## Dev Notes

**Why a frozen display order.** Live re-sorting on every keystroke makes the row you are editing jump out from under the cursor. Computing an id list when the sort *spec* changes gives spreadsheet-like behaviour (sort is an action, not a live filter) and is trivially testable. [Source: spec#Interaction design]

**Sort never writes.** Stored `order` stays authoritative; nothing about sorting touches the file or the API. Row-reordering by drag is explicitly out of scope for v1.

**Two things a header does.** A plain click sorts; the menu (2.5) is opened by its own affordance. Don't let one swallow the other.

### Completion Notes
- **`sort.ts`** holds `compareValues` and `sortRowIds`, both pure and fully covered (15 tests): numeric for `number`, chronological for `date`, locale-aware case-insensitive for `text`, ties stable, and the input array never mutated.
- **Empties last in both directions, deliberately implemented outside the direction flip.** `compareValues` always puts empty last, and `sortRowIds` applies the descending sign only when *neither* side is empty. Negating the whole comparator — the obvious shortcut — would float empty rows to the top on a descending sort, which is not what "empty sorts last" means. There is a test for each direction.
- **A frozen display order, not a live computed.** `displayRowIds` is recomputed only when the sort spec changes; a cell edit leaves it alone, so the row being typed into never jumps. A test edits a sorted cell and asserts the order is unchanged. Added rows append to the end of the view; deleted rows are spliced out; neither re-sorts what is on screen.
- **The sort resets when the tab changes** — a sort belongs to the tab being looked at (this also pre-wires Epic 3's tab switching).
- **Header click vs header menu stay separate:** clicking the name cycles the sort, the chevron opens the column menu, so one never swallows the other.
- **Nothing is written.** A test asserts that sorting emits no `commit-cell` and no `move-column`; the stored `order` is untouched.
- **Suites:** frontend **891** passed plus the one pre-existing `hotaru/LibraryPage` failure; backend unchanged at **664** (frontend-only story). ESLint and Prettier clean.
