# Story 3.4: Sheet layout fixes and tab colour

## Status

Ready for Review

## Story

**As** a user,
**I want** the tab bar always on screen, a row always ready for input, room to name a new column, and tabs I can visibly edit and colour,
**so that** the sheet is usable with real amounts of data rather than only with a few rows.

## Acceptance Criteria

1. **The tab bar stays on screen.** Given more rows than fit, when the sheet renders, then the bar sits at the bottom of the viewport and the grid scrolls inside its own box. (revises FR-12)
2. **A row is always ready.** Given the last row is filled and becomes real, when it does, then a fresh empty row sits beneath it and the cursor follows down into it. (revises FR-8)
3. **Room to name a column.** Given several columns, when adding one, then the name field opens in a popup; data columns are a fixed width and the table scrolls horizontally. (revises FR-10, NFR-1)
4. **The tab menu is discoverable.** Given a tab chip, when it renders, then a visible control opens rename / colour / delete — no right-click. (revises FR-14)
5. **Tab colour.** Given the menu, when a preset colour is picked or cleared, then `PUT .../tabs/{id}` persists `#rrggbb` or `null`, the chip is tinted and the grid header takes the accent. (FR-21)
6. **Additive schema.** Given a document written before colours, when it is read, then it validates unchanged and `schema_version` stays `1`.

### Completion Notes

Reported by the user after using the app. All four were real; one was a feature that had shipped but was unreachable.

- **1 — the tab bar.** It had `position: sticky; bottom: 0`, but sat in normal page flow after a grid with its own `max-height: 70vh` scroller, so it landed wherever the content ended. Sticky cannot pin to the viewport when the page itself grows. Fixed properly: `SheetPage` gives `q-page` a **definite height** via Quasar's `style-fn` (`height: calc(100vh - offset)` rather than the default `min-height`), then header / body / bar is a flex column and the grid takes the slack with `min-height: 0`. `fillViewport` is a pure function and is unit-tested directly.
- **2 — the always-ready row.** The ghost row already existed (Story 2.3) and worked. Two things made it not feel that way: it was inside the 70vh inner scroller so it was often below the fold (fixed by #1), and after typing in it the cursor **stayed on the row that had just become real**, so entry appeared to stall. Focus now follows down into the fresh ghost, in the same column. Guarded by a test that a row arriving from anywhere *else* does not move focus.
- **3 — the cramped add-column input.** The form lived in a `width: 1%` trailing header cell. Data columns are now a fixed `12rem` with `table-layout: fixed` and `width: max-content`, so the table scrolls sideways instead of compressing, and the add-column **form moved into a popup** where its width is its own business.
- **4 — "we need the ability to edit tabs".** Rename and delete shipped in Story 3.3 — on `<q-menu context-menu>`, which is **right-click only**. That is not a missing feature, it is an undiscoverable one, and the report is the evidence. Each chip now carries a visible caret; clicking it opens the menu without switching tabs (asserted).
- **Tab colour** (new, approved during triage): `Tab.color` is optional and additive, so `schema_version` stays `1` — there is a test that validates a pre-colour document. The API distinguishes an **omitted** colour ("leave it alone") from `""` ("clear it"), which is why `recolourTab(null)` sends an empty string; both directions are tested, as is "renaming leaves the colour alone".

**Two test-quality problems found and fixed along the way:**
- My first popup tests passed while `q-menu` was *unresolved* — Vue renders an unknown component as a plain element with its children, so the assertions were weaker than they looked. Added a stub that honours `v-model`, so a closed popup is genuinely absent, and asserted that too.
- A pre-existing warning from Story 1.3: a `q-select` stub with a native `<select>` root and no declared props made Vue warn on every render (`options` is read-only on a real select element). Fixed there and avoided in the new stubs.

**Not verified in a browser.** The dev servers run, but I could not log in (`jake` / `tmp123` → "Invalid credentials"), so items 1–3 are verified by unit tests and CSS reasoning rather than by looking at them. They are layout changes; a browser pass is worth doing before this is called Done.

**Suites:** backend **710** passed (was 698), frontend **963** passed plus the one pre-existing `hotaru/LibraryPage` failure. `black`, `ruff`, ESLint, Prettier clean; no Vue warnings in the Listies suites.
