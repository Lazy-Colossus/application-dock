# Story 2.4: Delete a row

## Status

Ready for Review

## Story

**As** a user,
**I want** to remove a row I no longer want,
**so that** the sheet stays accurate.

## Acceptance Criteria

1. **Delete with confirmation.** Given a row, when I choose delete from its row control and confirm, then `DELETE /api/listies/sheets/{sid}/tabs/{tid}/rows/{rid}` removes it from my file and it disappears from the grid. (FR-9)

2. **Order preserved.** Given remaining rows, when one is deleted, then they keep their relative order (stored `order` values stay monotonic; no reshuffle).

3. **Unknown id.** Given a delete for a row id that isn't in that tab, when requested, then the API returns `404` `{detail}`.

4. **Focus survives.** Given the deleted row held focus, when it is removed, then focus moves to the same column of the following row (or the previous row if it was the last), never into nothing.

5. **Sorted view.** Given a delete while a sort is active, when the grid re-renders, then the row is removed from the display order and the rest are not re-sorted. (see Story 2.6)

6. **No confirm, no delete.** Given the confirmation dialog, when I dismiss it, then no request is sent.

## Dev Notes

**Confirmation is required.** Deleting a row destroys data with no undo in v1 — same bar as deleting a sheet (1.4). [Source: platform convention, Story 1.4]

**Focus after delete.** Getting this wrong strands the keyboard user; it is an explicit AC because it is easy to skip.

### Completion Notes
- **A real bug caught by a test written for AC 2.** Deleting leaves gaps in `order`, and `create_row` was minting `order = len(tab.rows)` — so deleting row 0 of three and then adding a row produced **two rows with `order == 2`**, and the grid's sort would have shown them in an arbitrary, unstable arrangement. The test (`test_a_row_added_after_a_delete_still_sorts_last`) passed vacuously while DELETE 405'd, then went red the moment delete worked. Fixed to `max(order) + 1`. This is precisely the bug that only appears after a delete, i.e. exactly what "keep the remaining order intact" was hiding.
- **Backend:** `DELETE .../rows/{rid}` → 204, 404 for an unknown row or another user's sheet. Survivors keep their relative order; no renumbering, so nothing else shifts under the user.
- **Frontend:** the grid grew a trailing actions column with an inline confirm — the same "destructive actions confirm first" bar as sheets (1.4) — and only one row can be confirming at a time. The ghost row has no delete control.
- **Focus survives a deletion:** `clampToGrid` already ran on a row-count change (Story 2.3), so focus on a vanished last row lands on the new last row rather than pointing at nothing. Covered by a test that shrinks the tab while a cell in the removed row is focused.
- **Two earlier tests updated, not weakened:** they scraped every `<td>` in a row, which now includes the non-data actions cell. They now scope to `GridCell` components, which is what they were actually asserting about.
- **Suites:** backend **635** passed (was 629). Frontend **833** passed plus the one pre-existing `hotaru/LibraryPage` failure. `black`, `ruff`, ESLint, Prettier clean.
