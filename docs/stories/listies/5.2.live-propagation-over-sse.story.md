# Story 5.2: Live propagation over SSE

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a member of a shared sheet,
I want to see other members' edits appear on my screen the moment they happen,
so that we are truly editing one live document together, not taking turns and refreshing.

This story makes shared sheets **live**. Story 5.1 already made a sheet a shared document that
multiple members edit through the API and maintains a `rev` counter on every content write. Here we
add a server push channel (SSE) and the client wiring so a change by one member reconciles onto every
other member's open view within a moment. **Depends on Story 5.1.** The sharing UI (Story 5.3) builds
on the client wiring introduced here.

## Context & Design Decisions

- **Server-Sent Events (SSE), not polling.** When a member writes, the server pushes a notification
  to every other member subscribed to that sheet; their client reconciles immediately.
- **Coarse events + refetch, not delta replay.** The server emits `sheet.changed { rev }` and the
  client refetches the sheet, rather than pushing per-field deltas the client must merge. It is
  dramatically simpler, robust against a missed event (a newer `rev` always triggers a full resync),
  and fast enough over SSE to feel live. Optimistic local writes (existing `commitCell` behaviour)
  keep the actor at zero latency; remote members see the change on the next event.
- **In-process event bus.** Production runs as a **single** container / uvicorn process (per
  CLAUDE.md), so all subscribers and writers share one process — a process-local `asyncio` bus is
  sufficient and correct. It would not fan out across multiple workers/replicas without an external
  broker; that is out of scope (YAGNI).

## Acceptance Criteria

### The event bus and emission

1. **Given** a member commits any content write to a shared sheet (row/cell/column/tab; and the
   owner-only delete-sheet)
   **When** the write is persisted (Story 5.1 bumps `rev`)
   **Then** the service publishes `{ type: "sheet.changed", sheet_id, rev, actor }` to the bus, where
   `actor` is the writing member's username and `rev` is the new revision (FR-24).

2. **Given** the owner changes membership or ends a sheet's life (add/remove member, stop sharing,
   delete)
   **When** it is persisted
   **Then** the service publishes `members.changed { sheet_id, members }` on add/remove, and
   `sheet.closed { sheet_id, reason }` (reason `removed` / `unshared` / `deleted`) targeted so an
   affected member's open view can react (FR-26).

3. **Given** the event bus module
   **When** it is exercised
   **Then** `subscribe(sheet_id) -> Queue`, `unsubscribe(sheet_id, queue)`, and
   `publish(sheet_id, event)` behave correctly with multiple subscribers per sheet; queues are
   bounded and a stalled subscriber is dropped/marked stale rather than growing without bound (a
   dropped client resyncs on reconnect) (NFR-4).

### The SSE endpoint

4. **Given** `GET /api/listies/sheets/{sheet_id}/events`
   **When** an authenticated member subscribes
   **Then** it returns `text/event-stream`, registers the subscriber for that sheet, streams events
   as SSE frames until the client disconnects, and **unsubscribes in a `finally`** on disconnect
   (FR-24).

5. **Given** the SSE endpoint
   **When** the caller is a non-member, unauthenticated, or presents a bad token
   **Then** it returns `403` / `401` and opens no stream — identical membership gating to every other
   sheet route (FR-2, NFR-2).

6. **Given** `EventSource` cannot send an `Authorization` header
   **When** the client subscribes
   **Then** the token is accepted as a `?token=` query parameter on **this endpoint only** and
   validated with the **same** decode/verify logic as the bearer path (factor it so both share one
   implementation) (FR-24).

7. **Given** an idle stream behind a proxy
   **When** no events flow for a while
   **Then** the server sends periodic keep-alive comment frames (`: ping`) so the connection is not
   dropped, and streaming is not defeated by response buffering/compression (FR-24).

### Client reconciliation

8. **Given** I have a shared sheet open
   **When** another member changes it
   **Then** my client receives `sheet.changed`, and because its `rev` is newer than my stored `rev`
   **and** its `actor` is not me, it refetches the sheet and re-renders — within a moment, without
   any action from me (FR-24).

9. **Given** my own optimistic write just landed
   **When** the resulting `sheet.changed` event arrives with `actor === me` (or a `rev` I already
   hold)
   **Then** my client **ignores** it — no redundant refetch, no flicker over the value I already
   applied (FR-24, NFR-5).

10. **Given** a live refetch lands while I am working
    **When** it re-renders
    **Then** it preserves my `activeTabId`, my sort spec, and map session state (map open/closed,
    on-map ticks) — all view-only state that is never persisted — and does **not** discard a cell I
    am mid-edit (FR-11, FR-17, FR-18, NFR-5).

11. **Given** the test suite
    **When** it runs
    **Then** no test opens a real network socket for SSE: the bus is unit-tested and the endpoint is
    tested with FastAPI `TestClient` reading a bounded number of frames and asserting auth/membership
    gating; the client composable is tested against a mocked `EventSource`; existing `pytest` /
    `npm test` stay green and linters are clean (NFR-4).

  - [ ] New `backend/app/services/listies_events.py`: process-local pub/sub keyed by `sheet_id`,
        backed by an `asyncio.Queue` per subscriber. API: `subscribe`, `unsubscribe`, `publish`.
        Bounded queues; drop-and-mark-stale on overflow. Module docstring states the single-worker
        assumption. This is service-layer infra — **not** the FS layer, **not** HTTP.

- [ ] **Task 2 — Emit events from the service** (AC: 1, 2)
  - [ ] In `listies_service.py`, after each committed shared content write, `publish` a
        `sheet.changed { sheet_id, rev, actor }`. Thread the acting username through (it is already
        the `current_user` the operations receive).
  - [ ] On `remove_member` / `stop_sharing` / `delete_sheet` (shared), publish `members.changed` or
        `sheet.closed { reason }` as appropriate so affected members react live.

- [ ] **Task 3 — SSE endpoint** (AC: 4, 5, 6, 7)
  - [ ] Route `GET /sheets/{sheet_id}/events` in `routers/listies.py` returning a `StreamingResponse`
        (media type `text/event-stream`): authenticate from `?token=`, verify membership (else
        403/404), subscribe, yield SSE frames from the queue, and unsubscribe in `finally` on
        disconnect. Emit `: ping` keep-alives on an interval.
  - [ ] Factor JWT verification out of `get_current_user` (or add a helper) so the query-param path
        reuses it. Keep `?token=` auth to this one endpoint; do not touch other routes.
  - [ ] Verify the SPA is still served and the stream is exempt from any buffering/compression that
        would defeat streaming.

- [ ] **Task 4 — Client subscription + reconciliation** (AC: 8, 9, 10)
  - [ ] New `frontend/src/apps/listies/composables/useSheetEvents.ts` wrapping `EventSource` — the
        **one** justified exception to "all HTTP via `useApi`" (`useApi` is `fetch`-based and cannot
        open a stream; isolate `EventSource` here so nothing else touches it). Open
        `/api/listies/sheets/{id}/events?token={jwt}` (token from `useAuthStore`), expose typed
        `onChanged` / `onMembersChanged` / `onClosed`, and clean up on unmount.
  - [ ] `useListiesStore`: parse and hold `owner`, `members`, `shared`, `rev`, `canManage` for
        `currentSheet` (from the Story 5.1 response shape). Add the subscription lifecycle: subscribe
        when a **shared** sheet opens, tear down on close/navigation.
  - [ ] On `sheet.changed` with `rev > store.rev` **and** `actor !== me`, refetch the sheet
        preserving `activeTabId`, sort spec, and map/tick session state (AC-10), without stomping an
        in-flight cell edit. Ignore own-`actor` / already-held-`rev` events (AC-9). Wire
        `onMembersChanged`/`onClosed` into store state for Story 5.3 to render (this story may leave
        their UI minimal — a console-free no-op or a basic redirect on `sheet.closed`).

- [ ] **Task 5 — Tests** (AC: 11)
  - [ ] Backend: bus subscribe/publish/unsubscribe (incl. multiple subscribers, overflow/stale
        handling); event emission on each shared write and on lifecycle changes; SSE endpoint via

  - [ ] Frontend: `useSheetEvents` with a mocked `EventSource`; store reconciliation (ignores own

## Dev Notes

### Read before writing code

- `backend/app/services/listies_service.py` — Story 5.1's resolver/`save()` write path is where the
  `publish` call hangs; the acting username flows in as `current_user`.
- `backend/app/routers/listies.py` — where the SSE route and its `?token=` auth live; mirror the
  existing membership gating.
- `backend/app/core/dependencies.py` — `get_current_user`; factor its JWT verify so `?token=` reuses
  it rather than forking the logic.
- `frontend/src/composables/useApi.ts` — the fetch-only boundary and the rationale for isolating SSE
  in `useSheetEvents.ts`.
- `frontend/src/stores/useAuthStore.ts` — source of the JWT for the `?token=` query param.
- `frontend/src/apps/listies/stores/useListiesStore.ts` — the optimistic `commitCell` pattern is the
  template for how a live refetch must **not** stomp an in-flight edit.
- `frontend/src/apps/listies/pages/SheetPage.vue` — where the subscription lifecycle hangs.

### SSE authentication without a header

`EventSource` cannot set `Authorization`. Accept the JWT as `?token=` on the events route **only**,
validated with the same decode/verify as `get_current_user`. A token in a URL is more exposure-prone
than a header (it can land in logs); keep it to this one endpoint and note it in the Dev Agent
Record. Do not move other endpoints to query-param auth.

### In-process bus — single-worker constraint

The bus holds `asyncio.Queue`s in memory. It works because production is one process (CLAUDE.md). It
would not fan out across workers/replicas — that needs an external broker, out of scope now.
Document the assumption in the module docstring.

### Why coarse events

Emit `sheet.changed { rev }` and refetch, not per-field deltas: simpler, robust to missed events (a
newer `rev` always fully resyncs), and fast enough to feel live. The actor sees zero latency from
their own optimistic write; remote members reconcile on the event.

### Platform conformance (NFR-4)

3-layer separation (router owns the `StreamingResponse`; the bus is service-layer infra; no FS access
added outside the repo); `useApi` remains the sole fetch boundary with `useSheetEvents` the one
documented SSE exception; the store keeps routing failures into `error`.
