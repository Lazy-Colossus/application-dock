# Story 5.1: Shared storage and the sharing lifecycle (backend)

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Listies user,
I want to share a sheet I own with other dock users so we all edit one shared document,
so that a plan we build together is a single source of truth rather than a copy each of us drifts
out of sync.

This is the **backend foundation** of Epic 5 (Live Collaboration). It makes a sheet a *shared*
document that multiple users can resolve and edit through the existing API. Liveness (SSE push,
Story 5.2) and the sharing UI (Story 5.3) build on top of it. After this story, sharing works
end-to-end **via the API**; other members' edits are seen on the next fetch, not yet live.

## Context & Design Decisions

- **Permission model — flat editor.** The **owner** (creator) shares/unshares, manages the member
  list, and is the only one who can delete the sheet. **Every member** (owner included) can edit all
  content: rows, cells, columns, tabs. No read-only viewers.
- Everything else about Listies is inherited, not rebuilt: 3-layer backend, `useApi` boundary, JWT
  auth, per-user JSON files, atomic writes.

### The core architectural change: shared sheets get their own file

Today every sheet is embedded in its owner's per-user document at
`DATA_DIR/listies/users/{username}.json`, and the filename is derived from the JWT username so a
user can only ever touch their own file (NFR-2). That isolation is exactly what makes collaboration
impossible as-is: a second person's requests resolve to *their* file, which does not contain the
sheet.

**Resolution:** a sheet is either **private** (embedded in the owner's user doc, as today) or
**shared** (promoted to its own file). Sharing *moves* the sheet out of the owner's user doc into a
shared store keyed by sheet id:

```
DATA_DIR/listies/shared/{sheet_id}.json
```

The shared file wraps the existing `Sheet` with collaboration metadata:

```jsonc
{
  "schema_version": 1,
  "sheet": { /* the existing Sheet object, unchanged shape */ },
  "owner": "alice",
  "members": ["alice", "bob", "carol"],   // owner is always a member
  "rev": 42,                              // bumped on every content write; consumed by Story 5.2
  "created_at": "2026-09-04T…Z",
  "updated_at": "2026-09-04T…Z"
}
```

- **Share** (owner, private → shared): remove the `Sheet` from the owner's user doc, write it to
  `shared/{sheet_id}.json` with `owner = caller`, `members = [caller, …invited]`.
- **Add member** (owner, already shared): union the usernames into `members`.
- **Remove member** (owner): drop from `members`. Removing the last non-owner leaves the sheet
  shared-with-only-owner; it does **not** auto-demote — demotion is only via explicit "stop sharing",
  so the behaviour is predictable.
- **Stop sharing** (owner, shared → private): move the `Sheet` back into the owner's user doc, delete
  the shared file. Distinct from *delete*, which discards the sheet entirely.

The owner's user-doc `schema_version` stays **1** — this is purely subtractive for that file (a
shared sheet simply is no longer in its `sheets` list); a user with no shared sheets is byte-for-byte
unaffected.

### Resolving a sheet id on every request

Because `sheet_id` may now live in one of two places, the service grows a single resolution point
used by **every** existing sheet/tab/column/row operation:

1. Look in the **caller's own user doc** — a private sheet they own.
2. Else look in the **shared store** for `shared/{sheet_id}.json` where the caller is in `members`.
3. Else → `FileNotFoundError` (router → 404). A non-member gets the identical 404 as a stranger, so
   sharing never leaks the existence of a sheet.

Resolution returns a small **sheet context** — the `Sheet`, a `save()` that writes back to the right
file, and (when shared) the metadata. Existing operations mutate the `Sheet` and call `save()`; the
context hides *which* file it came from, so the ~15 existing service functions do not each learn
about two storage backends. On a shared-sheet content write, `save()` **bumps `rev`**.

## Acceptance Criteria

### Sharing lifecycle (owner, via API)

1. **Given** a sheet I own
   **When** I `POST /api/listies/sheets/{sheet_id}/share` with `{ usernames: [...] }`
   **Then** the sheet is promoted to `shared/{sheet_id}.json` with `owner = me` and
   `members = [me, …usernames]`, and is removed from my user doc; the response reports the sheet as
   shared with its member list. Re-posting with more usernames **unions** them into `members`
   (FR-22).

2. **Given** a shared sheet I own
   **When** I `DELETE /api/listies/sheets/{sheet_id}/share/{username}`
   **Then** that user is removed from `members` and can no longer access the sheet; removing the last
   non-owner is allowed and leaves the sheet shared-with-only-owner (FR-22).

3. **Given** a shared sheet I own
   **When** I `DELETE /api/listies/sheets/{sheet_id}/share`
   **Then** the sheet is demoted back into my user doc as a private sheet and the shared file is
   deleted — the sheet itself is **not** deleted (FR-22).

4. **Given** a shared sheet I am a member of but do **not** own
   **When** I attempt share / add-member / remove-member / stop-sharing / **delete** on it
   **Then** the API rejects it with `403 {detail}` — only the owner manages membership and deletes
   the sheet (FR-23).

5. **Given** a request naming a target username that does not exist on the platform
   **When** submitted to the share endpoint
   **Then** it is rejected with `422 {detail}` (validated against `auth_service.list_usernames()`),
   and no partial membership change is persisted (FR-22).

### Editing and listing a shared sheet (all members)

6. **Given** a sheet shared with me (as owner or member)
   **When** I call `GET /api/listies/sheets` and `GET /api/listies/sheets/{sheet_id}`
   **Then** it appears in my sheet list summarised with `shared: true` and the `owner`'s name, and
   the full-sheet response carries `owner`, `members`, `shared: true`, `rev`, and
   `can_manage` (true only for the owner). A private sheet reports `shared: false` and omits member
   data (FR-23, FR-25).

7. **Given** a shared sheet
   **When** any member adds/edits/deletes a row, edits a cell, or adds/renames/retypes/reorders/
   deletes a column, or adds/renames/recolours/deletes a tab (owner-only exception: **delete sheet**)
   **Then** every existing Listies operation works exactly as on a private sheet — same endpoints,
   same coercion (`coerce_value`/`recoerce_column`), same last-tab/last-column guards — but the write
   targets the shared file and bumps its `rev` (FR-23).

8. **Given** two members editing the same shared sheet
   **When** they both write
   **Then** each operation is an independent read-modify-write of the shared file with an atomic
   replace, so neither corrupts the file; last write of a given field wins (see the concurrency note
   in Dev Notes) (NFR-3).

### Isolation

9. **Given** any sheet/tab/column/row/share endpoint
   **When** it is called for a `sheet_id` the caller cannot access (not their private sheet and not a
   shared sheet they are a member of)
   **Then** it returns `404 {detail}` — identical to a non-existent id, never revealing the sheet
   exists (FR-2, NFR-2).

10. **Given** the test suite
    **When** it runs
    **Then** existing `pytest` stays green, formatters/linters are clean, and new tests cover the
    shared store, resolver access matrix, sharing lifecycle, owner-only guards, and the `rev` bump
    (NFR-4).

## Dev Notes

### Read before writing code (UPDATE targets, not NEW)

- `backend/app/services/listies_service.py` — **the** file this story reshapes. Every operation is
  currently `read own doc → find sheet → mutate → write own doc`. Insert the resolver so
  read/write targets either the user doc or a shared file. Preserve all private-sheet behaviour
  (empty-is-null, cell-keyed-by-column-id, order-past-max, retype coercion, last-tab/last-column
  guards). Do **not** duplicate coercion — it must run identically for shared sheets.
- `backend/app/repositories/listies_repo.py` — mirror `_validate_username`, `_atomic_write_json`,
  and empty-doc-on-missing for the shared store.
- `backend/app/routers/listies.py` — exception→HTTP mapping; you add `PermissionError → 403` and the
  three share routes. Keep new routes unambiguous (note the existing `/columns/order` before
  `/columns/{column_id}` trick).
- `backend/app/routers/auth.py` — `auth_service.list_usernames()` is the source of truth for
  validating share targets.

### Concurrency — a known, accepted limitation at this scale

Each shared write is an independent read-modify-write of `shared/{sheet_id}.json` with an atomic
`os.replace`. That prevents a *corrupt* file but not a lost *concurrent field update*: two writes in
the same instant → whoever replaces second overwrites the first's unrelated change. Operations are
fine-grained and confined to co-editors of one sheet, so the window is small; Story 5.2's live event
reconverges views. Acceptable for this platform's scale (JSON files, small user counts, no DB).
Reference `docs/stories/application-dock-general/1.8.concurrency-safe-json-persistence.story.md` as
the foundational follow-up; do not invent locking or add a database here.

### rev now, events later

Maintain `rev` in this story (bump on every shared content write) even though nothing consumes it
yet — Story 5.2 uses it to drive live reconciliation. Keeping it in the write path here means 5.2
only adds the bus and the emit call, not a second pass over every operation.

### Platform conformance (NFR-4)

3-layer separation (routers translate exceptions; services raise stdlib exceptions +
`PermissionError`; repo is the only FS code); snake_case JSON, direct serialization, `{detail}`
errors, ISO-8601 timestamps; every route behind `Depends(get_current_user)`.
